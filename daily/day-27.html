한 줄 요약
PyArrow로 작은 Parquet를 만들고 마지막 8 bytes에서 footer length를 역산한 뒤, metadata가 가리키는 row group·column chunk offsets와 statistics를 실제 file ranges에 연결한다. Footer가 잘리면 body bytes가 남아도 reader는 안전한 scan plan을 확정할 수 없음을 확인한다.

2. 왜 중요한가

“Parquet는 필요한 column만 읽는다”를 방어하려면 footer에서 column chunk range를 찾는 control path와 그 range를 실제로 읽어 page를 decode하는 data path를 구분해야 한다. Statistics가 row group을 제외하고 projection이 columns를 제외한 뒤에야 읽을 ranges가 정해진다.

File size만 보고 remote range를 추측하면 dictionary page, page header, nested levels, footer를 빠뜨릴 수 있다. 반대로 column chunk 전체를 매번 읽으면 안전하지만 page index가 줄 수 있는 추가 pruning을 활용하지 못한다. Metadata가 약속하는 단위와 API가 실제 노출하는 단위를 확인해야 한다.

완료 조건: Writer close 뒤 끝 magic·footer length·footer parse·row count·schema·statistics를 검증하고 immutable object version을 snapshot에 등록해야 publish 성공이다. Body write가 끝났다는 사실만으로는 부족하다.

4. CS 내부 동작

4.1 Footer-first은 random I/O를 계획으로 바꾼다

Reader는 마지막 8 bytes로 footer 위치를 찾고 metadata를 먼저 읽는다. 이 작은 control read가 없으면 schema도 column chunk 위치도 알 수 없어 body를 안전하게 해석할 수 없다. Remote storage에서는 보통 HEAD 1회, tail range 1회, metadata range 1회가 시작 비용이 되며 tail read 크기에 따라 둘을 합칠 수 있다.

4.2 Offset은 byte ownership 경계다

dictionary_page_offset가 있으면 chunk 시작 후보는 그것이고, 없으면 data_page_offset다. total_compressed_size는 해당 column chunk가 file에서 차지하는 compressed bytes를 계획하는 데 쓰인다. 모든 offset·length는 0 ≤ start ≤ end ≤ footerStart를 overflow-safe하게 검증한다.

4.3 Statistics는 row-group 제거의 증거다

오늘 id를 0~3, 4~7, 8~11 세 row groups로 쓴다. Predicate id BETWEEN 4 AND 7이면 min/max가 겹치는 RG1만 후보가 된다. Statistics가 missing·truncated·type semantics 불명확이면 skip하지 않고 읽어야 correctness를 보존한다.

4.4 Public metadata API와 page parser는 다르다

PyArrow의 FileMetaData→RowGroupMetaData→ColumnChunkMetaData는 chunk offsets·sizes·encodings·statistics를 노출한다. 이것만으로 모든 page header 경계를 완전히 나열하는 API라고 가정하지 않는다. Page-level 관찰이 필요하면 page index 또는 format-aware parser를 사용하고 임의 byte pattern search를 경계로 착각하지 않는다.

4.5 Nested column은 primitive leaf로 보인다

Top-level tags: list<string>은 metadata의 primitive path tags.list.element로 나타난다. 그 chunk에는 string values뿐 아니라 definition/repetition levels가 함께 들어 있다. Parent name만 보고 chunk 수를 세면 projection cost와 schema가 어긋날 수 있다.

4.6 CPU·I/O·cache trade-off

작은 row group은 pruning·retry·parallelism을 정밀하게 하지만 footer와 task/request 수가 늘어난다. 큰 row group은 sequential read·compression이 좋아질 수 있지만 selective query가 더 많은 bytes를 읽는다. 인접 chunks를 한 range로 합치면 request latency는 줄지만 over-read가 늘어난다. 측정치는 transferred bytes, requested ranges, decompressed bytes, decoded values, CPU time으로 분리한다.

5. 실무 설계 판단

결정판단 기준과 이유
Row-group sizeSelectivity, projected width, task memory, object latency, retry unit, compression을 대표 workload에서 함께 측정한다.
Tail fetch sizeFooter size distribution p99와 request latency를 보고 마지막 8B+metadata를 한 요청에 담을지 결정한다. Hard-coded 64KiB를 계약으로 보지 않는다.
Range coalescingGap bytes와 추가 request latency를 비교한다. Request 수 감소가 over-read·cache pollution보다 큰 경우만 합친다.
Statistics trustWriter version·logical type·column order·NaN/null·truncated bound를 검증하고 untrusted면 read fallback한다.
ObservabilityListed/opened files, footer bytes/latency, selected RGs/chunks, requested/transferred/decompressed bytes, rows output, CPU를 단계별 기록한다.
CompatibilityFormat version, data page version, codec, logical/nested schema, writer/reader pair를 golden files로 round-trip한다.

Best practice·anti-pattern·edge case·version 차이

  • Best: File size, footerStart, row-group/column ranges를 half-open interval [start,end)로 로그한다.
  • Best: Metadata 계획과 실제 read metrics를 비교해 예상 대비 over-read를 찾는다.
  • Best: Close 후 다른 reader process로 reopen validation하고 checksum/version과 함께 publish한다.
  • Anti-pattern: file_offset 하나만 모든 chunk 시작으로 가정하거나 raw bytes에서 magic-like pattern을 page 경계로 추측한다.
  • Anti-pattern: Footer가 없는데 body pages를 salvage해 정상 dataset에 조용히 포함한다.
  • Anti-pattern: total_byte_size와 remote transferred compressed bytes를 같은 metric으로 비교한다.
  • Edge: Dictionary page가 있으면 data_page_offset보다 앞에서 chunk가 시작한다.
  • Edge: Metadata-only file, encrypted footer/column metadata, external file_path는 일반 local single-file 가정과 다르다.
  • Version: Format version과 data page version은 별도 knob다. Writer default를 기억에 의존하지 말고 metadata·명시적 options로 확인한다.
  • Engine: PyArrow public metadata API가 보여 주는 page-index/bloom 세부는 version별로 다를 수 있으므로 없는 속성을 format 부재로 단정하지 않는다.

6. 장애 대응

증상End magic/Thrift parse 실패, footer length가 file보다 큼, offset range 416/EOF, 특정 RG/column만 decode 오류, metadata row count와 결과 불일치, selective read가 full read와 다름, request·over-read 급증.
먼저 수집할 증거/지표Object URI/version/ETag/size/checksum, first/last magic, raw last 8B, footerStart·serialized size, schema/created_by/format version, row-group/column offsets·sizes·stats·encodings, range request/response headers, reader build, full/selective hashes.
가능한 가설Partial publish/truncated footer, stale object size/cache, mixed object versions across ranges, little-endian parse bug, length overflow, wrong dictionary/data offset choice, corrupt page header/payload, unsupported codec/version, bad statistics pruning, wrong nested path.
안전한 첫 조치Reader-visible snapshot에서 file을 quarantine하고 version을 고정한다. Predicate/page pruning을 끈 full row-group read로 범위를 좁히며 raw tail·metadata·failing chunk bytes를 보존한다.
rollback/복구Last-known-good snapshot으로 rollback한다. Source rows에서 새 immutable object를 write→close→reopen→count/schema/stats/hash 검증하고 atomic manifest/snapshot으로 교체한다. Bad object는 증거로 격리한다.
하지 말아야 할 조치Footer length/offset 수동 patch, bad object overwrite, failed file/row group skip 후 성공 처리, stats 무조건 신뢰, cache 전체 삭제로 증거 소실, source 검증 없는 salvage를 하지 않는다.

7. 40분 통합 실습: metadata에서 실제 ranges까지

사전 조건: 이 저장소 root, Docker Desktop, docker compose build 1회. Image는 Python 3.12와 고정된 pyarrow==20.0.0을 사용한다.

실행 전 예측: 12 rows를 row_group_size=4로 쓰면 RG는 몇 개인가? Predicate id 4~7은 어느 RG만 남기는가? File 끝 8 bytes 중 footer length는 어느 4 bytes인가? 끝 6 bytes를 자르면 body가 남아 있어도 metadata read가 성공할까?

최소 명령: 처음이면 docker compose build, 이후 아래 한 block을 실행한다.

docker compose run --rm lab python - <<'PY' from pathlib import Path import shutil, struct, tempfile import pyarrow as pa import pyarrow.parquet as pq tmp = Path(tempfile.mkdtemp(prefix="day27-")) path = tmp / "lab.parquet" bad = tmp / "truncated.parquet" try: table = pa.table({ "id": pa.array(range(12), type=pa.int64()), "group": ["A"]*4 + ["B"]*4 + ["C"]*4, "payload": [f"value-{i:02d}" for i in range(12)], "tags": pa.array([ None, [], ["a"], ["a","b"], ["b"], None, [], ["c"], ["c","d"], [], None, ["e"] ], type=pa.list_(pa.string())) }) pq.write_table( table, path, row_group_size=4, compression="NONE", use_dictionary=True, write_statistics=True, version="2.6", data_page_version="2.0", data_page_size=256 ) raw = path.read_bytes() assert raw[:4] == b"PAR1" and raw[-4:] == b"PAR1" footer_len = struct.unpack("<I", raw[-8:-4])[0] footer_start = len(raw) - 8 - footer_len assert 4 <= footer_start < len(raw) - 8 pf = pq.ParquetFile(path) md = pf.metadata print("file_size=", len(raw), "footer_start=", footer_start, "footer_len=", footer_len) print("format=", md.format_version, "created_by=", md.created_by) print("rows=", md.num_rows, "row_groups=", md.num_row_groups, "primitive_leaves=", md.num_columns) print("schema=", md.schema) chosen = [] chunk_ranges = [] for rg_i in range(md.num_row_groups): rg = md.row_group(rg_i) id_stats = rg.column(0).statistics if id_stats.min <= 7 and id_stats.max >= 4: chosen.append(rg_i) for col_i in range(rg.num_columns): col = rg.column(col_i) start = (col.dictionary_page_offset if col.dictionary_page_offset is not None else col.data_page_offset) end = start + col.total_compressed_size assert 4 <= start < end <= footer_start chunk_ranges.append((rg_i, col.path_in_schema, start, end)) print("RG", rg_i, "rows", rg.num_rows, "id_minmax", (id_stats.min, id_stats.max)) print("chosen_by_id_4_7=", chosen) projected = pf.read_row_group(chosen[0], columns=["id", "tags"]) print("projected_rows=", projected.num_rows, "projected_columns=", projected.column_names) print("first_ranges=", chunk_ranges[:4]) # Failure injection: footer length와 end magic 일부를 제거한다. bad.write_bytes(raw[:-6]) try: pq.read_metadata(bad) except Exception as exc: print("EXPECTED_CORRUPTION=", type(exc).__name__) else: raise AssertionError("truncated footer was accepted") assert md.num_row_groups == 3 and chosen == [1] assert projected.column("id").to_pylist() == [4,5,6,7] assert any(p == "tags.list.element" for _,p,_,_ in chunk_ranges) finally: shutil.rmtree(tmp) print("cleanup_exists=", tmp.exists()) PY

예상 관찰: Row groups는 3개이고 id min/max는 (0,3), (4,7), (8,11)이다. RG1만 선택되고 projected result는 id·tags 4 rows다. Nested leaf path tags.list.element와 실제 chunk ranges가 출력된다. Footer를 자른 file은 metadata read에서 corruption 예외가 나며 cleanup은 False다.

실패 주입·자주 나는 오류·cleanup

  • 실패 주입: End 6 bytes를 제거해 metadata length와 PAR1 일부를 잃게 한다. Body column pages가 남아도 file-level map을 신뢰할 수 없다.
  • 오류: PyArrow output의 exact byte sizes/offsets는 library build에 따라 달라질 수 있다. 불변식과 상대 관계를 검증한다.
  • 오류: total_byte_size는 row group의 uncompressed column data 합이고 file/range compressed bytes와 같지 않다.
  • 오류: Nested parent tags와 primitive metadata path tags.list.element를 혼동하지 않는다.
  • 오류: Statistics가 없으면 None.min처럼 접근하지 말고 READ fallback 정책을 적용한다.
  • Cleanup: Script의 finally가 container 내부 임시 directory를 지우고 --rm이 container를 제거한다.

8. 놓치기 쉬운 함정

  1. Footer metadata는 body 뒤에 있어 마지막 8 bytes에서 역방향으로 찾는다.
  2. File 존재·body write와 successful publish는 같은 상태가 아니다.
  3. Row group은 logical horizontal partition이고 column chunk가 연속 byte I/O 단위다.
  4. Dictionary page가 있으면 chunk start는 data page보다 앞이다.
  5. Chunk range와 개별 page boundaries는 같은 정보가 아니다.
  6. Statistics는 no-match 증명에만 쓰며 untrusted면 읽는다.
  7. Nested top-level column은 여러 primitive leaf paths가 될 수 있다.
  8. Format version, data page version, codec support는 서로 다른 축이다.
  9. Object storage ranges는 같은 immutable version/ETag에 묶어야 한다.
  10. 측정은 planned bytes, transferred bytes, decompressed bytes를 분리한다.

9. 대기업 기술 면접 질문

Q1. Object storage의 Parquet에서 SELECT id WHERE id BETWEEN 4 AND 7 read path를 설계하세요.

좋은 답변 구조: Immutable object version·size를 고정한다 → tail 8B와 footer range를 읽는다 → schema·RG stats를 parse한다 → no-overlap RG를 제외한다 → id chunk의 dictionary/data offsets와 size를 검증한다 → adjacent ranges/request latency를 최적화한다 → page decode·actual predicate → request/bytes/rows evidence와 failure fallback을 설명한다.

Q2. Row-group size를 16MiB와 512MiB 중 어떻게 선택합니까?

좋은 답변 구조: Dataset size, columns/projected width, predicate selectivity, target task concurrency/memory, object request latency, codec throughput, retry SLO를 수치 가정한다 → pruning granularity 대 compression/sequential I/O·footer/task cost를 모델링한다 → 대표 queries에서 transferred/decompressed bytes·CPU·P95·cost를 비교한다 → skew/large nested row edge와 rollback 기준을 둔다.

Q3. Footer가 잘린 file 1개가 production snapshot에 보입니다. 대응하세요.

좋은 답변 구조: Snapshot/object version을 고정하고 quarantine한다 → tail magic·length·size/checksum·writer job logs를 보존한다 → partial publish와 mixed-version range 가설을 확인한다 → last-good snapshot rollback → source rows로 immutable rewrite·reopen validation·count/hash 대사 → atomic snapshot 교체 → temp/staging·commit marker·alert 개선을 설명한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Optional·repeated·required가 max definition/repetition level에 주는 영향은?
  2. Null list·empty list·null element는 어떤 정보로 구분하는가?
  3. D=max D인 record와 physical value consumption 관계는?

오늘 내용 확인 3문제

  1. 마지막 8 bytes로 footerStart를 계산하는 식을 쓰라.
  2. Predicate·projection이 row groups와 column chunks를 제거하는 순서를 설명하라.
  3. Partial publish를 정상 완료로 오인하지 않기 위한 writer·reader 불변식은?

짧은 정답·채점 기준

어제 1Optional은 max D+1, repeated는 max D+1·max R+1, required는 둘 다 늘리지 않는다.
어제 2Leaf path의 definition level threshold로 ancestor가 어디까지 존재하는지 구분한다.
어제 3D=max D일 때만 values stream에서 하나를 소비하며 그 수가 physical values count와 맞아야 한다.
오늘 1footerStart = fileSize - 8 - littleEndianUInt32(last8[0:4])이며 last4는 PAR1이다.
오늘 2Footer→RG statistics로 horizontal partitions 제거→projection으로 primitive leaf chunks 선택→offset ranges 읽기→page decode·actual predicate 순서다.
오늘 3Close 후 end magic·footer parse·ranges·schema/count/checksum을 reopen 검증하고 atomic snapshot commit 전에는 reader에 노출하지 않는다.

채점: 각 2점, 총 12점. 10점 이상 통과. Footer control path, chunk data path, byte-range 비용과 partial publish 복구를 수치로 연결하면 면접 Level 3다.
