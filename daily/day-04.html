FILE FORMAT · WEEK 1 / DAY 04

row/column layout을 종이에 배치

Byte locality에서 Parquet row group까지 · 예상 학습 40분 + 실습 30분

한 줄 요약
Row layout은 한 record의 field를 이웃 byte에 두어 단건 전체 조회에 유리하고, column layout은 같은 field의 값을 모아 projection scan·encoding·compression·vectorization에 유리하다. Parquet와 ORC는 둘 중 하나만 고르는 대신 row group/stripe로 행을 나누고 그 안을 columnar하게 저장해 병렬성·locality·pruning의 균형을 잡는다.

1. 선수 용어 사전

Row / Record한 개 entity의 field 묶음. 예: 한 사용자의 id, age, score. Logical row와 실제 byte 배치는 구분해야 한다.
Column여러 row에서 같은 의미와 type을 가진 field의 집합. 같은 type·분포가 모여 있어 encoding/compression에 유리하다.
LayoutLogical value를 byte offset에 배치하는 규칙. Field order, width, alignment, null 표현, block 경계까지 포함한다.
ProjectionQuery가 전체 schema 중 필요한 column만 선택하는 것. SELECT age가 예다.
Predicate / SelectivityPredicate는 age > 30 같은 조건, selectivity는 전체 중 조건을 통과하는 비율이다. 1%면 매우 선택적이다.
Locality곧 사용할 byte가 storage block·memory·CPU cache에서 가까이 모여 있는 성질. 가까우면 불필요한 전송과 cache miss가 줄어든다.
Cache lineCPU cache가 memory에서 한 번에 가져오는 고정 크기 묶음. 크기는 architecture에 따라 다르므로 오늘 계산에서는 예시로 64byte를 가정한다.
Vectorization같은 type의 여러 값을 batch로 처리해 function-call/object overhead를 줄이고 SIMD 같은 CPU 병렬 명령을 활용하는 실행 방식.
Row group / Column chunk / PageParquet 계층. File은 row group들, row group은 column마다 하나의 contiguous column chunk, column chunk는 encoding/compression 단위인 page들로 구성된다.

2. 왜 중요한가: Query 비용은 “읽은 row 수”가 아니라 “움직인 byte”에서 시작한다

100개 column, row당 1KB, 1억 row인 table에서 단 하나의 8byte column 평균만 계산한다고 하자. 압축·metadata를 잠시 무시하면 row-oriented full scan은 약 100GB를 만질 수 있지만, 순수 column projection은 약 0.8GB만 필요하다. 반대로 특정 primary key 한 건의 100개 field를 읽을 때 column layout은 여러 column 영역을 찾아야 하고, row layout은 한 record 주변의 연속 byte로 끝낼 수 있다.

면접 계산 습관: scanned bytes ≈ selected row groups × selected columns의 compressed bytes. Columnar라는 이름만으로 빠르다고 말하지 말고 projection 비율, predicate pruning, compression ratio, page/index I/O, decode CPU, object-store request 수를 숫자로 가정한다.

Layout은 storage만의 문제가 아니다. Disk/object storage가 준 byte는 OS page cache와 user buffer를 거쳐 CPU cache에 들어온다. Query가 사용하지 않을 field까지 같은 cache line에 섞이면 memory bandwidth와 cache capacity를 낭비한다. 같은 type이 연속이면 branch와 object pointer를 줄여 batch decode·vectorized filter가 쉬워진다.

3. 아키텍처: 같은 3개 row를 두 방식으로 배치

Rowid · 4Bage · 2Bscore · 4B
R11012780.5
R21024191.0
R31032775.5
① Row layout
[101|27|80.5] [102|41|91.0] [103|27|75.5]
↕ row 전체 point read는 이웃 byte · age scan은 10B마다 건너뜀
② Column layout
id:[101,102,103] · age:[27,41,27] · score:[80.5,91.0,75.5]
↕ age scan은 6B 연속 · row 전체는 세 영역을 조립
③ Hybrid analytical layout
Row group 1: id chunk | age chunk | score chunk → 각 chunk 안에 pages
  1. Writer가 row group 경계를 소유한다. 들어온 row를 일정 row/byte 규모까지 buffer하고 column별 value·null을 모은다.
  2. Column encoder가 같은 type의 분포를 본다. Age의 반복 27은 dictionary/RLE 후보가 되고, 정렬된 id는 delta encoding 후보가 된다.
  3. Page가 encode/compress 상태를 확정한다. Page header에는 encoding과 크기 같은 decode 정보가 있고 data는 독립적인 압축 단위가 된다.
  4. Footer/control path가 위치를 기록한다. Row group과 column chunk offset·size·statistics를 기록해 reader가 data path의 필요한 byte만 range read하게 한다.
  5. Reader가 footer → pruning → projection 순으로 계획한다. 조건 statistics로 row group/page를 버리고, 남은 row 범위의 필요한 column chunk/page만 읽는다.
  6. Vectorized batch로 값을 복원한다. Decode된 column vectors에 predicate를 적용하고 selection vector로 다른 projected column의 동일 row를 맞춘다.

4. CS 내부 동작

4.1 Offset 계산: fixed-width가 쉬운 이유

위 row width는 4 + 2 + 4 = 10byte다. Zero-based row i의 시작은 row layout에서 i × 10이다. Age는 각 row 시작에서 4byte 뒤이므로 i × 10 + 4다. Column layout에서 row count가 N이면 age column 시작은 id 영역 뒤인 4N, row i의 age는 4N + 2i다.

String처럼 variable-width field가 들어오면 고정식만으로 다음 value를 찾을 수 없다. Length prefix, offset array, delimiter 중 하나가 필요하다. Columnar engine은 variable data와 offset/null bitmap을 별도 buffer로 두어 vector의 row index를 유지하는 경우가 많다.

4.2 Cache line과 memory bandwidth

64byte cache line을 가정하고 row가 64byte인데 query가 각 row의 8byte counter만 합산하면, row layout은 유용한 8byte를 위해 64byte를 가져와 87.5%를 쓰지 않을 수 있다. Counter만 연속한 column layout은 한 cache line에 8개 값을 담는다. 다만 이는 단순 모델이다. Hardware prefetch, compression decode, alignment, NUMA, batch size가 실제 성능을 바꾸므로 profiler와 benchmark로 확인한다.

AoS vs SoA: Application memory에서도 Array of Structures(row-like)와 Structure of Arrays(column-like)가 같은 trade-off를 가진다. OLTP entity update는 AoS가 자연스럽고, analytical filter/aggregation과 SIMD는 SoA가 유리한 경우가 많다.

4.3 Parquet의 정확한 계층

File여러 row group과 끝의 file metadata. Reader는 footer에서 column chunk 위치를 찾는다.
Row groupRow의 논리적 horizontal partition. 각 column마다 정확히 하나의 column chunk를 가진다. 병렬 scan과 pruning의 큰 단위다.
Column chunk특정 row group의 특정 column data. File 안에서 contiguous하며 I/O 단위가 된다.
PageColumn chunk 내부의 encoding/compression 단위. Page header와 encoded values를 가진다.

Row group이 크면 column chunk가 커져 sequential I/O와 compression에 유리하지만 writer buffer memory, retry 손실 범위, selective query의 최소 read 범위가 커질 수 있다. Page가 작으면 page skipping이 세밀하지만 header/index overhead와 scheduling/seek가 증가한다. 공식 권장값은 출발점일 뿐 object storage·engine·row 폭·query workload로 재측정한다.

4.4 Metadata pruning은 정답 필터가 아니다

Row group age min=20, max=45라면 age > 60 query에서 안전하게 전체 group을 건너뛸 수 있다. 하지만 min/max가 조건을 만족할 가능성을 보여도 실제 matching row가 있다는 보장은 없다. Statistics는 false positive는 허용하되 false negative로 필요한 data를 버리면 안 되는 보수적 pruning 도구다.

Predicate column과 projected column은 다를 수 있다. Reader가 age page에서 matching row positions를 찾은 뒤 score의 대응 row만 읽으려면 row index/offset index와 row alignment가 필요하다. Parquet page index의 ColumnIndex는 값 범위, OffsetIndex는 row index와 page 위치를 연결한다.

4.5 ORC의 stripe도 같은 문제를 푼다

ORC body는 독립적으로 처리 가능한 stripe들로 나뉘고, stripe 안에는 index, column data streams, stripe footer가 있다. File tail은 schema·stripe 위치·statistics를 제공한다. 이름과 세부 구조는 Parquet과 다르지만 “큰 row 묶음 안에서 column data를 분리하고 metadata로 필요한 범위를 찾는다”는 설계 목표는 비슷하다.

4.6 Data path, control path, 상태 전이

단계소유자·불변식·성공 조건
S0 BufferingWriter가 row count와 column buffer를 소유. 모든 column의 logical row count가 같아야 한다.
S1 Page sealedPage encoder가 value count·null·compressed size를 확정. 일부 page 성공은 file 성공이 아니다.
S2 Row group sealed각 column chunk의 row count가 동일하고 offsets/statistics가 확정.
S3 File finalizedFooter·length·magic이 durable. Reader가 metadata에서 모든 chunk를 찾아 검증 가능.
S4 PublishedChecksum·schema·row count 검증 후 manifest/table snapshot이 atomic하게 새 file을 참조.

5. 실무 설계 판단

판단Best practice와 이유
WorkloadPoint read/update와 wide row materialization이면 row store, 대규모 projection/aggregation이면 columnar를 우선 검토한다. Hybrid/serving copy도 비용에 포함한다.
Row group sizeTarget file size, writer memory, task parallelism, predicate selectivity, object request 비용을 함께 benchmark한다. 하나의 전역 숫자를 모든 table에 복사하지 않는다.
Sort / Cluster자주 쓰는 selective predicate의 값 범위를 row group/page에 모아 min/max pruning을 강화한다. Write shuffle·skew·maintenance 비용을 같이 측정한다.
StatisticsNull, NaN, truncated string bounds, collation, timezone을 specification/engine별로 검증한다. 민감한 min/max가 footer에 노출될 수 있음도 검토한다.

ValidationFile/row group/column value count, footer offsets, checksum, schema, null count와 query result invariant를 publish 전에 확인한다.
BenchmarkCold/warm cache를 분리하고 bytes read, requests, decompressed bytes, decode CPU, rows pruned, peak memory, wall time을 함께 기록한다.

Version·engine 차이

Page index, Bloom filter, checksum, encoding 지원은 writer와 reader engine/version마다 다를 수 있다. Writer가 metadata를 기록해도 reader가 사용하지 않을 수 있고, 오래된 reader가 새 page encoding을 해석하지 못할 수도 있다. File format 이름만 compatibility로 취급하지 말고 사용 feature × writer version × reader engine/version matrix와 golden files로 검증한다.

가능한 가설Reader projection pushdown 미지원, statistics 누락/잘못된 정렬, 너무 큰 row group, footer partial publish, corrupt page header/data, column value count 불일치, unsupported encoding, tiny file 과다, stale metadata cache.
안전한 첫 조치해당 file/partition을 격리하고 원본과 query profile을 보존한다. Footer와 row group metadata만 먼저 검사하고, 실패 chunk를 최소 projection으로 재현한다. Snapshot pointer는 마지막 정상 상태로 유지한다.

7. 30분 실습: 3개 column을 실제 byte offset에 배치

목표: Fixed-width row/column file을 직접 만들고 age projection과 한 row 전체 조회에서 읽어야 할 연속 영역이 어떻게 달라지는지 계산한다. 실행 전 N=8일 때 file size, row 5의 offset, age column 시작 offset을 먼저 예측한다.

사전 조건: Python 3가 설치된 shell. 외부 package는 필요 없다. 정확한 임시 경로 /tmp/file-format-day04만 사용한다.

mkdir -p /tmp/file-format-day04 cd /tmp/file-format-day04 python3 - <<'PY' import struct from pathlib import Path rows = [(101+i, 20+(i%3)*10, 70.0+i) for i in range(8)] ROW = struct.Struct(">IHf") # id 4B, age 2B, score 4B row_bytes = b"".join(ROW.pack(*r) for r in rows) ids = b"".join(struct.pack(">I", r[0]) for r in rows) ages = b"".join(struct.pack(">H", r[1]) for r in rows) scores = b"".join(struct.pack(">f", r[2]) for r in rows) col_bytes = ids + ages + scores Path("rows.bin").write_bytes(row_bytes) Path("cols.bin").write_bytes(col_bytes) print("row_width", ROW.size, "rows", len(rows)) print("sizes", len(row_bytes), len(col_bytes)) print("age_offsets_row", [i*ROW.size+4 for i in range(len(rows))]) print("age_column_range", (len(ids), len(ids)+len(ages))) PY od -An -tx1 rows.bin od -An -tx1 cols.bin

예상 관찰: 두 file은 metadata 없는 toy layout이라 모두 80byte다. Row layout의 age는 offset 4,14,24,...로 흩어져 있고, column layout의 age 16byte는 offset 32..47에 연속한다. 전체 row 하나는 row layout에서 10byte 연속이지만 column layout에서는 id·age·score 세 영역을 읽어 조립해야 한다.

Projection과 point lookup을 검증

python3 - <<'PY' import struct from pathlib import Path N, ROW_SIZE = 8, 10 r, c = Path("rows.bin").read_bytes(), Path("cols.bin").read_bytes() ages_from_rows = [struct.unpack(">H", r[i*ROW_SIZE+4:i*ROW_SIZE+6])[0] for i in range(N)] age_start = 4*N ages_from_cols = list(struct.unpack(">" + "H"*N, c[age_start:age_start+2*N])) print("ages_equal", ages_from_rows == ages_from_cols, ages_from_cols) i = 5 row_point = struct.unpack(">IHf", r[i*ROW_SIZE:(i+1)*ROW_SIZE]) col_point = ( struct.unpack(">I", c[4*i:4*i+4])[0], struct.unpack(">H", c[4*N+2*i:4*N+2*i+2])[0], struct.unpack(">f", c[6*N+4*i:6*N+4*i+4])[0], ) print("point_equal", row_point == col_point, row_point) PY

해석: Column projection은 16byte 연속 range 하나면 되지만 row layout은 8개의 2byte range 또는 80byte full scan이 필요하다. 반대로 point row는 row layout 10byte range 하나, column layout 세 range가 필요하다. Object storage에서는 작은 range 세 개의 request latency가 payload byte보다 더 비쌀 수 있다.

실패 주입: 잘린 row와 row alignment

python3 -c "from pathlib import Path; b=Path('rows.bin').read_bytes(); Path('rows-truncated.bin').write_bytes(b[:-1])" python3 -c "from pathlib import Path; b=Path('rows-truncated.bin').read_bytes(); width=10; print('size',len(b),'remainder',len(b)%width); assert len(b)%width==0, 'partial row detected'"

예상: 두 번째 명령은 remainder 9와 assertion failure를 낸다. 마지막 9byte를 무시하면 7개 정상 row처럼 보일 수 있지만 source가 8개였다는 증거를 잃는다. Size, expected row count, checksum을 함께 검증하고 partial file 전체를 quarantine한다.

자주 나는 오류와 해결: >는 HTML에서 greater-than으로 렌더링된다. Shell에 보이는 실제 문자를 사용한다. Float 출력에는 IEEE 754 표현에 따른 작은 차이가 생길 수 있으므로 일반 계산에서는 tolerance를 쓰되, 이 실습은 같은 byte를 같은 format으로 decode하므로 tuple equality가 성립한다. od가 없으면 xxd -g 1을 사용한다.

8. 놓치기 쉬운 함정

  • Columnar = 모든 query가 빠름: Wide point read, tiny result, 높은 request latency, decode CPU 병목에서는 row store나 index가 낫다.
  • Row group = 물리적으로 하나의 blob: Parquet에서 row group은 논리적 horizontal partition이며 실제로는 각 column chunk가 contiguous한 구조다.
  • Page = I/O request 단위: Page는 encoding/compression 단위다. Sequential scan에서 page마다 별도 tiny read를 하는 것이 목표는 아니다.
  • Projection만 보고 predicate를 잊음: Filter column을 읽고 matching row를 다른 column과 정렬해야 한다. Index/selection vector와 row alignment가 필요하다.
  • Min/max를 정확한 index로 착각: Pruning 가능성만 판정하며 secondary index처럼 정확한 row 위치를 항상 주지 않는다.
  • Compression ratio만 최적화: 더 큰 group/page는 압축은 좋아져도 peak memory, retry 범위, selective read amplification을 키울 수 있다.
  • Warm cache benchmark만 보고: OS/object cache hit를 storage read 감소로 착각한다. Cold/warm run과 실제 bytes/request 지표를 분리한다.

9. 대기업 기술 면접 질문

Q1. 100TB event table의 row group size를 어떻게 정하겠습니까?

좋은 답변 구조: 평균 row width·file size·object storage·executor memory·동시성·대표 projection/predicate/selectivity를 질문 → 후보 128/512MB/1GB 등 수치 가정 → sequential I/O·compression·footer overhead와 writer memory·pruning granularity·retry 범위 trade-off → cold cache benchmark 지표(bytes, GET, decode CPU, peak memory) → skew/small-file compaction과 engine/version matrix → table별 adaptive 기준을 제시한다.

Q2. Columnar table에서 단건 조회가 느린 이유와 개선책은?

좋은 답변 구조: 필요한 field 수·latency SLA·key selectivity·정렬 여부 확인 → footer/index read, row group/page locating, 여러 column range GET, decode의 실제 흐름 → cache와 page index/정렬로 줄이는 방법 → serving KV/row-store materialized view 또는 database index 대안 → 이중 저장의 consistency·write amplification·운영 비용까지 설명한다.

Q3. WHERE age=30 SELECT score의 Parquet read path를 설명하세요.

좋은 답변 구조: Footer에서 schema·row group·chunk offsets 읽기 → age row-group statistics로 pruning → 가능하면 page ColumnIndex로 후보 age pages, decode/filter해 row positions 생성 → OffsetIndex/row alignment로 score의 대응 pages/ranges 읽기 → vectorized score decode와 selection 적용 → page index 미지원·unordered data·false positive·corrupt metadata fallback과 비용을 방어한다.

  3. Row group을 크게 만들 때 좋아지는 비용과 나빠지는 비용을 각각 두 개 이상 말하라.
짧은 정답·채점 기준
  1. 어제 1: Text/binary는 표현, self/external은 schema 위치다. JSON과 Avro OCF/Parquet 또는 raw Protobuf 예시가 있으면 만점.
  2. 어제 2: Wire에는 field number와 wire type만 있어 field 이름·선언 type·message 의미를 확정할 외부 정의가 필요하다.
  3. 어제 3: Registry 복구 후 replay할 원본을 잃어 data loss가 된다. Quarantine·미commit·idempotent replay를 말하면 만점.
  4. 오늘 1: Row는 한 entity 전체 point read, column은 projection/aggregation에 유리하며 각각 필요한 byte가 연속한다는 설명.
  5. 오늘 2: Row group은 horizontal row partition, column chunk는 그 group의 한 column contiguous I/O, page는 encoding/compression 단위다.
  6. 오늘 3: Sequential I/O·compression·metadata overhead는 개선되고 writer memory·pruning granularity·retry/corruption 범위는 악화될 수 있다.
