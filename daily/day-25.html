FILE FORMAT · WEEK 4 / DAY 25 · LESSON

ORC stripe·row index·bloom filter

Tail·stream directory·probabilistic pruning을 production read path로 연결 · 예상 학습 65분 + 실습 35분
한 줄 요약
ORC는 독립 처리 단위인 stripe 안에 index streams·column data streams·stripe footer를 두고, writer가 정한 row index stride마다 statistics와 seek positions를 기록한다. Optional bloom filter는 equality 후보를 더 줄이지만 false positive는 허용하며, 정상 구현에서 false negative가 없어야만 “없음→skip”이 안전하다.

2. 왜 중요한가

ORC reader가 customer_id = 42를 찾을 때 파일 전체를 바로 읽지 않는다. File/stripe statistics로 큰 범위를 제외하고, 남은 stripe의 row index statistics로 stride 범위를 좁힌 뒤, bloom filter가 “42는 절대 없음”이라고 답한 row group을 더 제외할 수 있다. 마지막 후보만 column streams에서 seek·decode한다.

하지만 bloom은 database secondary index가 아니다. “maybe”는 위치도 존재도 확정하지 않으며 실제 data predicate가 필요하다. False positive rate를 낮추면 bitset과 index I/O가 커진다. Distinct가 낮거나 min/max만으로 충분한 column에 bloom을 무조건 켜면 storage·writer CPU·tail latency만 늘 수 있다.

안전성 규칙: Statistics와 bloom은 one-sided filter다. Metadata가 없거나 hash/version·encoding이 불명확하면 읽는다. 정상 bloom의 negative만 skip에 쓰고 positive는 반드시 실제 value로 검증한다.

4. CS 내부 동작

4.1 Stripe는 whole-row partition이자 recovery/task 단위다

Row는 stripe 경계를 넘지 않는다. File footer의 StripeInformation은 offset, indexLength, dataLength, footerLength, numberOfRows를 제공한다. Reader는 선택 stripe의 footer와 필요한 streams만 range-read한다. Stripe가 크면 sequential I/O·compression이 좋아질 수 있지만 writer buffer, retry bytes, pruning granularity와 task parallelism 비용이 커진다.

4.2 한 column은 여러 streams로 분해된다

Integer column은 nullable이면 PRESENT bit stream과 non-null values DATA stream을 가질 수 있다. Binary/string은 LENGTH와 DATA, dictionary encoding이면 DICTIONARY_DATA와 dictionary index stream이 추가될 수 있다. 모든 값이 non-null이면 PRESENT를 생략할 수 있으므로 “stream이 없으면 corrupt”가 아니다. Schema·encoding·StripeFooter를 함께 해석한다.

4.3 Row index positions는 decoder state다

RowIndexEntry의 positions는 단순 file offset 하나가 아니다. Compression chunk 위치, decompressed bytes 소비량, RLE run에서 이미 소비한 values처럼 stream decoder를 같은 logical row boundary로 복원하는 state가 포함될 수 있다. Multiple streams의 position sequence를 잘못 매핑하면 column 간 row alignment가 어긋나 silent corruption이 생긴다.

4.4 Three-level statistics

ORC는 file, stripe, row-group(stride) 수준에서 statistics를 활용한다. File/stripe 통계는 tail에 있어 body를 읽기 전 pruning에 쓰고, row-level index는 stripe 앞 index section에 있어 selective scan일 때만 읽을 수 있다. Statistics가 missing·unsupported·untrusted면 skip하지 않고 다음 단계로 내려간다.

4.5 Bloom filter의 수학적 contract

m-bit bitset에 n개 값을 k개 hash 위치로 표시한다. Query 값의 k개 bit 중 하나라도 0이면 확실히 absent, 모두 1이면 maybe present다. 대략적인 false-positive probability는 p ≈ (1-e^(-kn/m))^k다. n을 과소 추정하거나 m을 줄이면 p가 올라가 read 절감이 약해진다. p가 커져도 correctness는 유지되지만 hash·serialization mismatch로 false negative가 생기면 안전 계약이 깨진다.

4.6 Statistics → bloom 순서

Range predicate는 min/max가 주역이다. Equality/IN에서는 먼저 min/max로 명백한 out-of-range를 제거하고, 남은 broad ranges에 bloom을 적용한다. Bloom은 ordering 정보를 보존하지 않으므로 x > 100 같은 range를 직접 해결하지 않는다. Positive candidate는 반드시 stream data에서 실제 equality를 검사한다.

Best practice·anti-pattern·edge case

  • Best: Explain/profile에서 stripes·row groups considered/skipped와 stat/bloom reason, index bytes, data bytes를 분리한다.
  • Best: Bloom on/off와 full scan의 result hash·count를 canary에서 비교한다.
  • Best: StripeFooter streams를 길이 누적으로 계산하되 section boundary와 overflow를 먼저 검증한다.
  • Best: File/stripe stats → row index stats → bloom 순으로 cheap·broad filter부터 적용한다.
  • Anti-pattern: Bloom positive를 exact match로 간주해 data predicate를 생략한다.
  • Anti-pattern: Stripe 내부 stream 순서를 column id 순이라고 하드코딩한다.
  • Anti-pattern: 10,000 rows를 모든 file의 고정 stride로 가정한다.
  • Edge: All-null column은 PRESENT만 있거나 data stream이 비어 있을 수 있다. Missing stream과 corruption을 구분한다.
  • Edge: High-cardinality/oversubscribed bloom은 false positives가 늘어 성능만 악화될 수 있다.
  • Version: Obsolete non-UTF8 bloom과 현재 UTF8 bloom 처리 정책, native/hive reader 차이를 배포 version 문서와 golden files로 확인한다.

7. 35분 실습: row-index + bloom pruning simulator

목표: Python 표준 라이브러리로 stride별 min/max와 bloom filter를 만든다. Statistics→bloom→actual predicate 순서, deterministic false positive와 bit corruption false negative를 관찰한다.

사전 조건: Python 3.9 이상. 외부 package·파일·Docker가 필요 없다. 교육용 bloom이며 ORC hash/serialization 구현을 대체하지 않는다.

실행 전 예측: Values 범위가 1~100인 group에서 42가 없으면 min/max만으로 skip 가능한가? Bloom “maybe”는 match인가? Inserted 42의 bit 하나를 지우면 어떤 correctness failure가 생기는가?

python3 - <<'PY' import hashlib class Bloom: def __init__(self, m=32, k=3): self.m, self.k, self.bits = m, k, 0 def indexes(self, value): raw = str(value).encode("utf-8") d = hashlib.sha256(raw).digest() h1 = int.from_bytes(d[:8], "little") h2 = int.from_bytes(d[8:16], "little") | 1 return [(h1 + i*h2) % self.m for i in range(self.k)] def add(self, value): for i in self.indexes(value): self.bits |= 1 << i def maybe(self, value): return all(self.bits & (1 << i) for i in self.indexes(value)) def build(values): b = Bloom() for v in values: b.add(v) return {"values":values, "min":min(values), "max":max(values), "bloom":b} groups = [build([1,5,9,100]), build([40,42,50,60]), build([200,300])] assert all(g["bloom"].maybe(v) for g in groups for v in g["values"]) def plan_eq(group, value, trust_bloom=True): if value < group["min"] or value > group["max"]: return False, "SKIP_STATS_DISJOINT" if trust_bloom and not group["bloom"].maybe(value): return False, "SKIP_BLOOM_NEGATIVE" return True, "READ_CANDIDATE" for query in [42, 7]: actual=[] print("query=", query) for n,g in enumerate(groups): read,reason=plan_eq(g,query) print(" RG",n,"READ" if read else "SKIP",reason) if read: actual += [v for v in g["values"] if v == query] print(" result=",actual) # Find a deterministic false positive in group 0: maybe does not mean present. g0=groups[0] fp=next(v for v in range(g0["min"],g0["max"]+1) if v not in g0["values"] and g0["bloom"].maybe(v)) print("false_positive=",fp,"actual_present=",fp in g0["values"]) # Failure injection: corrupt one required bit for inserted value 42. g1=groups[1] bit=g1["bloom"].indexes(42)[0] g1["bloom"].bits &= ~(1 << bit) print("corrupt_bloom_42_maybe=",g1["bloom"].maybe(42)) unsafe_read,reason=plan_eq(g1,42,trust_bloom=True) safe_read,_=plan_eq(g1,42,trust_bloom=False) print("unsafe=",unsafe_read,reason,"safe_fallback_read=",safe_read) assert fp not in g0["values"] assert not unsafe_read and safe_read PY

예상 관찰: Query 42는 RG0가 min/max와 겹치지만 bloom negative로 skip, RG1은 read 후 실제 42를 찾고 RG2는 stats로 skip한다. 작은 bitset 때문에 없는 값이 bloom positive인 false positive도 나오지만 actual predicate 결과에는 포함되지 않는다. 42의 bit를 지우면 false negative로 RG1이 unsafe skip되며, bloom을 불신해 read하면 복구된다.

실패 주입·오류·cleanup

  • 실패 주입: Inserted 42의 bit를 지워 no-false-negative invariant를 깨뜨린다. Error 없이 data가 누락되는 correctness incident다.
  • 오류: Bloom positive를 결과에 바로 넣지 않는다. 실제 data equality를 적용한다.
  • 오류: Python SHA-256 simulator hash를 ORC production hash로 사용하지 않는다. Writer/reader의 공식 version contract를 따른다.
  • 오류: Bitset이 작아 false positive가 많아져도 correctness는 유지된다. 이것을 corruption과 구분한다.
  • 확장: m·k·n을 바꾸며 observed false-positive rate, index bytes와 avoided groups를 표로 만든다.
  • Cleanup: Memory object만 사용하므로 파일·package·container가 남지 않는다.

8. 놓치기 쉬운 함정

  1. Stripe는 whole rows를 가지며 row는 stripe를 넘지 않는다.
  2. Stripe 안 stream 순서는 StripeFooter directory가 결정한다.
  3. Missing PRESENT stream은 all-non-null이면 정상일 수 있다.
  4. Row index position은 offset 하나가 아니라 decoder resume state일 수 있다.
  5. Row index stride는 file footer의 값이며 10,000을 하드코딩하지 않는다.
  6. Bloom은 equality/IN 후보 제거에 적합하고 range ordering은 제공하지 않는다.
  7. Bloom negative만 확정이며 positive는 actual predicate가 필요하다.
  8. Dictionary는 partial stripe read에도 전체를 읽을 수 있다.
  9. Hash/UTF-8/version mismatch는 false negative를 만들어 correctness를 깰 수 있다.
  10. Pruning on/off result canary 없이 성능 지표만 보지 않는다.

9. 대기업 기술 면접 질문

Q1. ORC reader가 equality predicate로 최소 byte만 읽는 흐름을 설명하세요.

좋은 답변 구조: Tail/Postscript/Footer로 stripes·schema·compression을 얻는다 → file/stripe stats로 prune한다 → selected stripe footer로 stream directory를 만든다 → predicate column ROW_INDEX와 bloom을 읽는다 → stats→bloom negative 순으로 row groups를 좁힌다 → positions로 projected streams를 seek/decode한다 → actual equality로 positive 후보를 검증한다.

Q2. Row index stride와 bloom false-positive rate를 어떻게 정합니까?

좋은 답변 구조: Query projection/equality selectivity, row width, distinct/stride, stripe size, object request latency를 수치화한다 → 작은 stride의 index·writer CPU와 pruning 이득을 비교한다 → target FPP에서 bit budget을 계산한다 → representative load의 index/data bytes·groups skipped·P95·cost를 측정한다 → correctness canary와 rollback 기준을 둔다.

Q3. Bloom filter 적용 뒤 특정 고객이 검색되지 않습니다. 대응하세요.

좋은 답변 구조: Bloom pruning을 즉시 disable해 full stripe read로 correctness를 복구한다 → snapshot·tail·stripe footer·row index·bloom bytes·hash/version과 missing IDs를 보존한다 → on/off 최소 반례로 false negative를 증명한다 → writer/reader encoding mismatch·bit corruption을 진단한다 → last-good rollback 또는 immutable rewrite·full scan 대사·atomic republish를 설명한다.

ORC v2 문서는 evolving draft이므로 여기서는 안정된 v1 specification과 공식 운영 문서를 기준으로 삼았다. 실제 기본값과 bloom encoding 지원은 배포 library/version에서 다시 확인한다.
