FILE FORMAT · WEEK 5 / DAY 30 · COMPRESSION

Snappy, ZSTD, Gzip, LZ4 특성

압축률이 아니라 end-to-end query cost로 codec 선택하기 · 예상 학습 60분 + 실습 35분
한 줄 요약
Codec 선택은 “가장 작은 파일” 찾기가 아니라 encoding된 page를 얼마나 적은 CPU·I/O·memory·호환성 비용으로 저장하고 다시 읽을지 결정하는 workload별 최적화다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의
CodecCompressor와 decompressor가 합의한 byte 변환 규칙이다. 같은 이름이라도 framing 규격이 다르면 호환되지 않을 수 있다.
Compression ratio원본 bytes ÷ 압축 bytes. 값이 클수록 작아졌지만 CPU 시간과 latency는 말해 주지 않는다.
Throughput초당 처리한 bytes. Write에는 압축 throughput, scan에는 압축 해제 throughput이 중요하다.
Latency요청 시작부터 결과가 나올 때까지 시간. 평균뿐 아니라 p95·p99 tail latency도 본다.
Framing압축 block의 경계·길이·검증 정보를 감싸는 규칙. 알고리즘이 같아도 frame이 다르면 reader가 해석하지 못한다.
PageParquet에서 encoding·compression의 작은 단위다. Page header는 압축 전후 크기와 page 종류를 알려 준다.
Range read파일 전체가 아니라 offset과 length로 필요한 byte 구간만 읽는 I/O다.
Working set동시에 memory·CPU cache에서 다루는 데이터의 양. 압축 page와 해제 buffer가 함께 존재할 수 있다.

2. 왜 중요한가

Object storage에서 1GB를 덜 읽으면 network 시간과 요청 비용이 줄지만, 이를 위해 CPU를 과도하게 쓰면 동시 query 수가 떨어진다. 반대로 빠른 codec으로 파일이 커지면 cache hit가 낮아지고 remote I/O가 병목이 된다. 따라서 codec은 storage, network, CPU, memory를 서로 교환하는 설계 knob다.

핵심 불변식: decompress(compress(encoded_page))는 입력 encoded bytes와 정확히 같아야 한다. Writer가 footer·column metadata에 기록한 codec enum, page header의 압축 전후 크기, 실제 payload framing이 모두 일치해야 reader 성공을 확정할 수 있다.

3. 아키텍처 그림과 요청 흐름

① Logical values → Encoding
dictionary·RLE·bit packing·delta로 page bytes 생성
↓ control path: codec·level·page size 선택
② Page compressor
Snappy / ZSTD / Gzip / LZ4_RAW
↓ data path: compressed payload + size metadata
③ Storage commit
pages → column chunk → row group → footer → publish
↓ footer read → pruning → selected range GET
④ Reader buffers
compressed input → decompress → encoded bytes
↓ decode → vector batch
⑤ 동일 logical values
filter·aggregate·materialize
  1. Writer가 선택 상태를 소유한다. Data 분포, CPU budget, reader fleet 지원, I/O 가격을 기준으로 codec과 level을 고른다.
  2. Encoding 후 compression한다. Dictionary ID나 delta처럼 이미 구조화된 bytes를 codec이 다시 압축한다. 두 단계의 효과는 독립적이지 않다.
  3. Page 단위로 기록한다. Parquet는 page data block을 압축하고 PageHeader의 compressed/uncompressed size와 column metadata의 codec을 남긴다.
  4. Commit 시점은 파일 전체다. 모든 pages와 footer가 durable하고 catalog/snapshot이 완성 파일을 가리킬 때 publish가 성공한다. Footer 전 write crash는 partial file이다.
  5. Reader는 역순으로 검증한다. Footer로 codec을 확인하고 필요한 ranges만 읽어 buffer 크기를 제한한 뒤 decompress·decode한다.

4. CS 내부 동작

Snappy: speed-first baseline

일반적으로 압축·해제 속도가 빠르고 CPU 사용이 예측 가능해 interactive scan과 범용 default에 자주 쓰인다. 압축률은 ZSTD·Gzip보다 낮을 수 있으므로 remote I/O가 비싼 workload에서는 전체 시간이 더 길어질 수 있다. “항상 가장 빠르다”가 아니라 실제 hardware와 data로 확인한다.

ZSTD: level로 CPU와 ratio를 조절

ZSTD는 여러 compression level을 제공해 ratio와 write CPU를 조절할 수 있다. 낮은 level은 read-heavy lake의 좋은 균형점이 될 수 있지만, level을 올려도 decompress 비용·파일 크기 이득이 workload 전체 비용을 개선하는지 측정해야 한다. Reader fleet가 ZSTD를 지원하는지도 먼저 확인한다.

Gzip: 높은 보급성과 CPU trade-off

Gzip은 오래된 reader까지 넓게 지원되는 편이고 높은 압축률을 줄 수 있지만, 압축·해제 CPU가 speed-first codec보다 클 수 있다. Parquet 규격의 GZIP은 RFC 1952 framing이며 zlib 또는 raw deflate와 같은 이름으로 취급하면 안 된다. 여러 GZIP member를 쓰는 page는 reader 호환성도 주의한다.

LZ4: 빠른 block 처리와 framing 함정

LZ4는 빠른 압축·해제를 목표로 하며 CPU-bound scan에 유리할 수 있다. 그러나 Parquet의 과거 LZ4 enum은 undocumented Hadoop framing 때문에 deprecated다. 새 writer는 상호운용 가능한 LZ4_RAW 지원을 확인해야 하며, “LZ4 알고리즘 지원”만으로 파일 호환성을 단정하면 안 된다.

CPU·I/O·cache cost 식

scan_time ≈ metadata + remote_I/O(compressed_bytes) + decompress_CPU + decode_CPU + materialize working_set ≈ compressed_input + uncompressed_page + decoded_vectors

Compression ratio가 좋아지면 I/O는 줄지만 decompression CPU와 temporary buffer pressure가 늘 수 있다. 작은 page는 random access와 cache locality를 돕지만 header·codec 호출 overhead가 늘고, 큰 page는 ratio가 좋아질 수 있으나 selective read와 tail latency가 나빠질 수 있다.

5. 실무 설계 판단

상황첫 후보판단 이유와 검증
Interactive·CPU 여유 적음Snappy / LZ4_RAWDecode throughput과 p95 latency 우선. 파일 증가로 I/O 병목이 생기는지 확인.
Remote I/O·storage 비쌈ZSTD 낮은~중간 level읽는 bytes 감소가 CPU 증가를 상쇄하는지 cost/query로 측정.
장기 archive·write 드묾ZSTD / GzipReader 호환성과 복구 시간까지 포함. 최고 level 강제는 benchmark 후 결정.
Mixed reader fleet공통 지원 codec가장 오래된 production reader로 canary read. 지원표만 믿지 말고 실제 파일 검증.
  • Best practice: 동일 logical table·row-group/page 설정·warm-up·반복 횟수로 size, write MB/s, read MB/s, CPU time, peak RSS, query latency를 함께 기록한다.
  • Anti-pattern: 파일 크기 하나만 보고 codec을 전사 기본값으로 고정한다.
  • Edge case: 이미 암호화되거나 random에 가까운 payload는 압축이 거의 안 된다. ORC처럼 압축 결과가 더 크면 original chunk를 저장하는 포맷 동작도 있다.
  • Version/engine 차이: Parquet의 deprecated LZ4와 LZ4_RAW는 구분한다. ZSTD·LZ4_RAW 도입 시 reader 구현·버전별 read/write 지원을 확인한다.
  • Small-file 대응: Codec을 바꿔도 object listing·open·footer request 오버헤드는 줄지 않는다. Compaction과 적절한 row-group 크기가 별도 필요하다.

⑥ 하지 말아야 할 조치원본을 in-place 수정, 실패 파일을 재시도만 반복, footer enum을 bytes 확인 없이 변경, 전체 dataset을 검증 없이 일괄 재압축하지 않는다.

7. 35분 실습: 동일 Parquet를 codec별로 측정

사전 조건: 저장소 root에서 Docker와 기존 lab image(make build)를 사용할 수 있어야 한다. PyArrow 20.0.0이 고정되어 있다.

먼저 예측: (1) 모든 파일의 row count와 checksum은 같다. (2) codec별 size·write/read 시간이 다르다. (3) 압축률 1등이 read latency 1등이라고 보장할 수 없다. (4) 파일 truncation은 footer 또는 page read에서 안전하게 실패해야 한다.

docker compose run --rm lab python - <<'PY' import os, shutil, tempfile, time import pyarrow as pa import pyarrow.compute as pc import pyarrow.parquet as pq root = tempfile.mkdtemp(prefix="codec-lab-") try: n = 200_000 table = pa.table({ "id": pa.array(range(n), type=pa.int64()), "country": pa.array([("KR", "US", "JP", "DE")[i % 4] for i in range(n)]), "payload": pa.array([f"group-{i % 100:03d}-" + "x" * 24 for i in range(n)]), }) expected = pc.sum(table["id"]).as_py() results = [] for codec in ("snappy", "zstd", "gzip", "lz4"): if not pa.Codec.is_available(codec): print(codec, "SKIP: unavailable") continue path = os.path.join(root, f"{codec}.parquet") t0 = time.perf_counter() pq.write_table(table, path, compression=codec, row_group_size=50_000) write_s = time.perf_counter() - t0 t0 = time.perf_counter() out = pq.read_table(path, columns=["id"]) read_s = time.perf_counter() - t0 assert out.num_rows == n and pc.sum(out["id"]).as_py() == expected meta = pq.ParquetFile(path).metadata.row_group(0).column(0) results.append((codec, os.path.getsize(path), write_s, read_s, meta.compression)) for row in sorted(results, key=lambda x: x[1]): print("codec=%s bytes=%d write=%.4fs read=%.4fs metadata=%s" % row) source = os.path.join(root, "snappy.parquet") broken = os.path.join(root, "truncated.parquet") with open(source, "rb") as src, open(broken, "wb") as dst: data = src.read() dst.write(data[:-32]) try: pq.read_table(broken) raise AssertionError("truncated file unexpectedly readable") except Exception as exc: print("SAFE_FAILURE:", type(exc).__name__) finally: shutil.rmtree(root, ignore_errors=True) PY

예상 관찰: 실행 환경에 따라 순위와 시간은 달라지지만 네 파일의 logical checksum은 같다. Metadata에는 실제 codec이 기록되고, truncation은 정상 결과를 내지 않는다. 한 번의 wall-clock 결과를 결론으로 삼지 말고 5회 이상 반복·warm-up하고 median과 p95를 기록한다.

실패 주입: Snappy 파일의 마지막 32 bytes를 잘라 footer를 손상시킨다. Reader가 실패하지 않으면 테스트 실패다.

자주 나는 오류와 해결: LZ4가 unavailable이면 SKIP 결과를 기록하고 engine 지원을 확인한다. Docker image가 없으면 먼저 make build한다. Host background load가 크면 CPU pinning 또는 반복 횟수를 늘린다.

Cleanup: finally가 임시 directory를 제거하고 --rm이 container를 제거한다. 실행 중 강제 종료했다면 /tmp/codec-lab-* 중 본 실습이 만든 경로만 확인 후 삭제한다.

8. 놓치기 쉬운 함정

  • Encoding과 compression을 섞어 말하지 않는다. Dictionary/RLE 뒤에 Snappy/ZSTD가 적용된다.
  • Compression ratio만 보고 고르지 않는다. Scan CPU, bytes read, memory, tail latency, reader 지원을 함께 본다.
  • Parquet LZ4와 LZ4_RAW를 같은 framing으로 간주하지 않는다.
  • Codec level과 library version을 benchmark report에 기록하지 않으면 결과를 재현할 수 없다.
  • OS page cache·object cache·warm-up 상태가 다른 실험을 비교하지 않는다.

9. 대기업 기술 면접 질문

Q1. 100TB read-heavy lake에서 Snappy와 ZSTD 중 선택하라.
좋은 답변 구조: query projection·scan bytes·CPU quota·network 가격 가정 → 같은 encoding/page/row group으로 A/B → size, decompression GB/s, p95 query, cost/query → oldest reader 호환성 → canary와 rollback.

Q2. ZSTD로 바꿨더니 파일은 25% 줄고 query는 15% 느려졌다. 유지할 것인가?
좋은 답변 구조: workload SLO와 비용 목표 확인 → CPU-bound/I/O-bound 분리 → concurrency와 cache hit까지 계산 → level 조정·column별 codec·Snappy 대안 → 대표 workload 수치로 결정.

Q3. 새 LZ4 파일을 일부 engine이 못 읽는다. 원인을 byte path로 설명하라.
좋은 답변 구조: footer codec enum → LZ4 vs LZ4_RAW framing → range read와 page header sizes → decompressor 지원 → 실패 window → quarantine·공통 codec 재작성·snapshot rollback.

10. 복습 문제와 정답

어제 내용 회상 3문제

  1. Dictionary가 low-cardinality에서 유리한 이유는?
  2. RLE와 bit packing이 각각 유리한 분포는?
  3. Delta encoding이 정렬이 깨지면 불리해지는 이유는?

오늘 내용 확인 3문제

  1. Compression ratio만으로 codec을 고르면 안 되는 이유를 두 가지 말하라.
  2. Parquet의 LZ4와 LZ4_RAW를 구분해야 하는 이유는?
  3. Reader가 compressed page를 logical values로 만드는 순서를 쓰라.
짧은 정답·채점 기준
어제 1: 고유값을 한 번 저장하고 작은 ID를 반복. 2: 긴 동일 run은 RLE, 작은 범위의 섞인 정수는 packing. 3: 인접 delta가 커져 bit width 증가.
오늘 1: CPU/latency·memory·호환성·I/O가 함께 변함 중 두 가지. 2: 과거 LZ4 enum의 비표준 framing이 deprecated이고 LZ4_RAW가 상호운용 규격이기 때문. 3: range read → decompress → decode → vector/materialize.
채점: 각 2점, 총 12점 중 9점 이상 통과. 정의 1점 + 내부 흐름·trade-off 1점.
