회상: selective query read path 그리기

Parquet·ORC metadata pruning에서 vectorized materialization까지 · 예상 학습 55분 + 실습 35분
한 줄 요약
Selective query는 “조건에 맞는 row만 읽기”가 아니라 footer·index로 불필요한 byte ranges를 제거하고, 필요한 ranges만 I/O한 뒤, decode·nested reconstruction·late materialization을 거쳐 정확한 rows를 반환하는 다단계 상태 전이다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의

ProjectionSELECT에 필요한 columns만 요청하는 것. Columnar file은 다른 column chunks를 읽지 않을 수 있다.

2. 왜 중요한가

Columnar format의 성능은 “압축률이 좋다” 한 문장으로 설명되지 않는다. Query가 1 TB table에서 2 columns와 1% 날짜 범위만 필요하다면, 좋은 reader는 partition·file·row group/stripe·page 순서로 후보를 줄여 실제 I/O를 수 GB 이하로 낮춘다. 하지만 pruning metadata가 없거나 잘못됐거나 predicate가 변환되어 pushdown되지 않으면 같은 file format도 full scan처럼 동작한다.

반대로 너무 많은 작은 ranges를 요청하면 object-store round trip, TLS, request charge, kernel bookkeeping이 늘어 큰 sequential read보다 느릴 수 있다. 따라서 목표는 “최소 bytes”가 아니라 정확성을 보존하면서 총비용이 가장 낮은 read plan이다.

핵심 불변식: Metadata는 skip을 허용하는 증거이지 결과 그 자체가 아니다. “skip”은 false negative를 만들면 안 되며, “read”는 후보를 실제 predicate로 다시 검증해야 한다.

3. 아키텍처 그림과 요청 흐름

① SQL / logical predicate
SELECT id,tags WHERE day=D AND id BETWEEN 4 AND 7
↓ normalize expression · resolve schema/field IDs
② Catalog·partition pruning
Snapshot과 partition metadata로 candidate files를 고정한다.
↓ footer/postscript tail range read
③ File metadata plan
Parquet row groups / ORC stripes의 schema·offset·statistics·indexes를 해석한다.
↓ min/max·null count·Bloom·page/row index로 safe skip
④ Range coalescing
필요한 column chunk/stream/page ranges를 병합해 I/O requests를 만든다.
↓ Range GET / pread → compressed buffers
⑤ Decompress·decode
Dictionary·levels·values를 vector batch로 복원하고 filter vector를 만든다.
↓ surviving positions에 payload/nested parents materialize
⑥ Result batch
Predicate를 실제 values로 재검증하고 row order·count·null semantics를 보존한다.
Control path: Query → snapshot/schema → metadata → skip/read decisions → ranges → batch policy.
Data path: Storage bytes → compressed buffers → decompressed pages/streams → level/value vectors → selection → result.

각 번호의 요청·응답·상태 변화

  1. Query normalization: Timestamp timezone, casts, null semantics를 정규화한다. 이때 원래 predicate와 pushdown 가능한 predicate를 분리한다.
  2. Snapshot 고정: File list와 schema version을 한 시점으로 고정한다. Listing 도중 새 file이 보이면 partial snapshot이 될 수 있다.
  3. Metadata 읽기: Parquet은 footer tail, ORC는 postscript/footer/stripe metadata를 통해 layout directory를 얻는다. Offset은 metadata가 소유한다.
  4. Skip 결정: Statistics가 predicate와 겹치지 않으면 skip한다. 겹치거나 metadata가 없으면 READ가 안전한 기본값이다.
  5. Range plan: 인접한 작은 ranges를 합치되 불필요한 bytes와 request 수의 trade-off를 계산한다.
  6. Decode: Compression 해제 후 encoding과 nested levels/streams를 해석한다. Dictionary page나 parent levels를 누락하면 projected leaf도 복원할 수 없다.
  7. 성공 확정: Candidate rows에 predicate를 다시 적용하고 counts·offsets·schema·checksum/length 불변식을 통과한 batch만 반환한다.

4. CS 내부 동작

4.1 Pruning은 구간 논리다

Predicate id BETWEEN 4 AND 7과 block statistics [min,max]가 겹치지 않으면 block을 skip한다. max<4 OR min>7일 때만 불가능함을 증명한다. Min/max가 겹쳐도 matching row가 있다는 뜻은 아니므로 실제 values를 읽어 재검증한다.

4.2 False positive는 비용, false negative는 correctness

Bloom filter가 “있을 수 있음”이라고 답해 불필요한 stripe를 읽는 false positive는 성능 비용이다. 실제 값이 있는데 “없음”이라 답하는 false negative는 결과 누락이므로 허용할 수 없다. Corrupt·unsupported metadata는 SKIP이 아니라 READ 또는 quarantine으로 내려야 한다.

4.3 Range coalescing은 I/O와 over-read의 균형

Ranges 100개를 각각 4 KB로 요청하면 400 KB만 읽지만 100회 latency를 낸다. 1 MB window로 병합하면 request는 줄지만 필요 없는 bytes를 읽는다. Storage latency, bandwidth, request charge, cache reuse를 합친 비용함수로 gap threshold를 정한다.

4.4 Decode는 CPU·cache 문제다

Compressed bytes가 작아도 dictionary lookup, bit unpacking, RLE, definition/repetition levels, UTF-8 validation과 nested offsets 생성이 CPU를 사용한다. Vectorized reader는 연속 buffers와 validity bitmaps를 사용해 branch misprediction과 per-row allocation을 줄인다.

4.5 Late materialization은 선택도가 높을 때 유리하다

Filter column을 먼저 읽어 selection vector를 만들면 wide payload를 surviving rows에만 materialize할 수 있다. 하지만 다른 columns가 별도 remote ranges에 있고 선택도가 낮다면 추가 pass와 random I/O가 오히려 비싸다. Early/late 선택은 row width·selectivity·range locality·cache pressure로 결정한다.

4.6 Nested projection에도 structure bytes가 필요하다

tags.list.element values만으로 null list, empty list, null element와 row boundaries를 복원할 수 없다. Parquet definition/repetition levels 또는 ORC length/present streams와 parent state가 필요하다. “한 leaf만 projection” 비용에는 structure decode와 offsets 생성이 포함된다.

상태 소유자·불변식·성공 시점

상태소유자와 불변식

5. 실무 설계 판단

결정판단 기준과 이유
Row group/stripe 크기크면 compression·sequential I/O가 좋고 metadata가 작다. 작으면 pruning granularity가 좋지만 footer/index와 task 수가 늘어난다.
Sort/clustering자주 쓰는 selective predicate의 값 범위를 block별로 좁혀 min/max pruning 효율을 높인다. Write amplification과 다른 query의 locality를 함께 본다.
Bloom filterEquality lookup이 잦고 cardinality·bits/value 예산이 맞을 때 사용한다. Range query에는 min/max가 더 직접적이다.
Page index큰 row groups 안에서 page skip 가치가 request/metadata/decode 비용보다 큰지 engine support와 함께 확인한다.
Range 병합Object-store p50/p99 latency, bandwidth, request price, gaps와 cache hit를 측정해 threshold를 정한다.
Late materializationWide rows·높은 filter selectivity에서 유리하다. 낮은 selectivity와 remote noncontiguous columns에서는 early batch가 나을 수 있다.

Best practice·anti-pattern·edge case·engine 차이

  • Best: scanned files/row groups/stripes/pages, requested/received bytes, range count, decompression/decoding CPU, output rows를 단계별 metric으로 남긴다.
  • Best: Full scan과 pruned scan의 result hash를 golden query로 비교해 optimization이 correctness를 바꾸지 않음을 검증한다.
  • Best: Metadata missing/corrupt/unsupported는 READ 또는 quarantine으로 명시한다.
  • Anti-pattern: “Statistics가 겹친다”를 “matching row가 있다”로 해석한다.
  • Anti-pattern: Bytes만 최소화하고 수천 개의 tiny Range GET을 만든다.
  • Anti-pattern: CAST(column), timezone conversion, UDF가 pushdown되는지 확인하지 않고 pruning을 기대한다.
  • Edge: NaN, signed zero, truncated string statistics, null-only blocks, missing Bloom, encrypted metadata와 schema evolution은 보수적 fallback이 필요하다.
  • Engine: Parquet page index, Bloom filter, nested predicate, ORC row index 사용 여부와 default batch/range coalescing은 engine·version별로 다르다. Query plan과 metrics로 확인한다.

6. 장애 대응

증상Selective query가 full scan, Range GET 폭증, CPU 100%·I/O idle, 결과 누락, nested rows 엇갈림, 특정 file/engine에서 corrupt·OOM·timeout.
먼저 수집할 증거/지표Query plan과 normalized predicate, snapshot/file versions, footer/postscript/schema, block/page statistics·Bloom, selected/skipped counts, range offsets/lengths/request latency, bytes requested/received, decompress/decode CPU, output row hash, engine/writer versions.
가능한 가설Predicate pushdown 불가, stale/corrupt statistics, schema mapping·timezone 오류, page index 미지원, unsorted data, tiny ranges, dictionary/levels 누락, partial footer, small-file 폭증, false-negative bug.
안전한 첫 조치Affected snapshot을 고정하고 pruning을 끈 full read와 결과 hash를 비교한다. Missing/unknown metadata는 READ로 강제하고 최소 file·row group·predicate를 격리한다. Corrupt file은 quarantine한다.
rollback/복구Last-known-good engine/config/snapshot으로 rollback한다. Source data에서 immutable rewrite 후 counts·hash·statistics·footer bounds를 검증하고 atomic snapshot으로 교체한다. Small files는 별도 compaction commit으로 수렴시킨다.
하지 말아야 할 조치증거 없이 statistics 재작성, corrupt block skip 후 성공 처리, unknown을 SKIP으로 간주, bad object overwrite, partial output publish, 결과 누락을 성능 개선으로 해석, 원본 없이 metadata patch를 하지 않는다.

7. 35분 실습: selective read planner를 손으로 그린 뒤 실행

목표: 표준 Python만으로 synthetic row-group metadata를 pruning하고, 인접 byte ranges를 병합하며, corrupt metadata에서 READ fallback이 false negative를 막는지 확인한다. 실제 Parquet parser가 아니라 read-plan 불변식 simulator다.

사전 조건: Python 3.9 이상. 외부 package·Docker·파일이 필요 없다.

실행 전 예측: id BETWEEN 4 AND 7은 어떤 groups를 READ하는가? Group 1의 id metadata가 없어지면 SKIP인가 READ인가? Gap 32 bytes 이하를 합치면 Range GET 수는 몇 개가 되는가?

python3 - <<'PY' groups = [ {"rg":0, "id_stats":(0,3), "ranges":[(100,180),(200,250)]}, {"rg":1, "id_stats":(4,7), "ranges":[(300,390),(410,470)]}, {"rg":2, "id_stats":(8,11), "ranges":[(520,600),(900,960)]}, ] low, high = 4, 7 def decision(stats): if stats is None: return "READ" # unknown은 safe fallback minimum, maximum = stats return "SKIP" if maximum < low or minimum > high else "READ" def coalesce(ranges, max_gap=32): out = [] for start, end in sorted(ranges): assert 0 <= start < end if out and start - out[-1][1] <= max_gap: out[-1] = (out[-1][0], max(out[-1][1], end)) else: out.append((start, end)) return out plan = [(g["rg"], decision(g["id_stats"])) for g in groups] selected = [g for g in groups if decision(g["id_stats"]) == "READ"] ranges = coalesce([r for g in selected for r in g["ranges"]]) print("plan=", plan) print("selected=", [g["rg"] for g in selected]) print("ranges=", ranges) assert plan == [(0,"SKIP"),(1,"READ"),(2,"SKIP")] assert ranges == [(300,470)] # Failure injection: matching group의 statistics가 손실됨. damaged = [dict(g) for g in groups] damaged[1]["id_stats"] = None damaged_plan = [(g["rg"], decision(g["id_stats"])) for g in damaged] print("damaged_plan=", damaged_plan) assert damaged_plan[1] == (1,"READ") print("SAFE_FALLBACK: unknown metadata did not cause false-negative skip") PY

예상 관찰: 정상 plan은 RG0·RG2를 SKIP하고 RG1만 READ한다. RG1의 두 ranges는 gap 20이므로 (300,470) 하나로 병합된다. Metadata가 사라져도 RG1은 READ라서 결과 누락을 만들지 않는다.

실패 주입·자주 나는 오류·cleanup

  • 실패 주입: 실제 matching group의 statistics를 None으로 바꾼다.
  • 오류: Metadata 없음은 “matching row 없음”이 아니다. Unknown은 READ다.
  • 오류: Range end를 inclusive로 혼동하지 않는다. 실습 ranges는 반열린 구간 [start,end)다.
  • 오류: Range 병합은 bytes만 늘리는 게 아니라 requests를 줄인다. 두 비용을 함께 계산한다.
  • 해결: max_gap을 p99 request latency·bandwidth·request charge로 튜닝하고 golden result hash로 검증한다.
  • Cleanup: Memory object만 사용하므로 생성 파일·package·container가 없다.

8. 놓치기 쉬운 함정

  1. Projection pruning과 predicate pruning은 별개이며 둘 다 plan에 보여야 한다.
  2. Statistics가 겹치는 것은 후보라는 뜻이지 match 확정이 아니다.
  3. Missing·corrupt·unsupported metadata는 SKIP이 아니라 READ 또는 quarantine이다.
  4. Partition/file/block/page pruning은 서로 다른 granularities와 costs를 가진다.
  5. Page index가 file에 있어도 engine이 실제로 사용하지 않을 수 있다.
  6. 최소 bytes가 최소 latency는 아니다. Tiny ranges는 request 비용을 폭증시킨다.
  7. Nested leaf projection에도 levels/present/length streams와 parent offsets가 필요하다.
  8. Dictionary와 structure streams를 range plan에서 빼면 decode가 실패하거나 의미가 깨진다.
  9. Pruning 후에도 실제 values에 predicate를 다시 적용해야 한다.
  10. Optimization은 full scan과 result hash가 같을 때만 성공이다.

9. 대기업 기술 면접 질문

Q1. 1 TB Parquet table에서 1% 날짜와 2 columns를 읽는 path를 설계하세요.

좋은 답변 구조: Snapshot과 schema를 고정한다 → partition/file pruning → footer tail read → row-group/page statistics로 safe skip → 필요한 column chunks와 dictionary/levels ranges → range coalescing → vectorized decode/late materialization → 실제 predicate 재검증 → files/bytes/ranges/CPU/output rows metrics와 full-scan hash 비교까지 설명한다.

Q2. Bytes는 90% 줄었는데 query가 더 느려졌습니다. 왜입니까?

좋은 답변 구조: Baseline 수치(bytes, requests, p50/p99 latency, CPU)를 요구한다 → tiny Range GET·TLS/request charge·cache miss·두 번 decode·selection vector·low selectivity 가설 → ranges 병합 threshold와 early/late materialization A/B → 비용함수와 결과 동일성으로 결정한다.

Q3. Metadata pruning이 결과를 누락시킨 의심이 있습니다. 대응하세요.

좋은 답변 구조: Affected snapshot·engine/version·file checksum을 고정한다 → pruning off full scan과 result hash 비교 → 최소 predicate/file/block 격리 → statistics/Bloom/schema/timezone/cast/NaN 가설 → unknown=READ와 quarantine → last-good rollback → immutable rewrite·atomic publish·false-negative regression test를 제시한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Parquet file 끝 8 bytes는 footer 위치를 어떻게 알려 주는가?
  2. Row-group statistics로 id 4~7 후보를 고를 때 어떤 비교를 하는가?
  3. Column chunk의 실제 byte range를 만들 때 어떤 offset과 size를 사용했는가?

오늘 내용 확인 3문제

  1. Selective read의 control path와 data path를 각각 순서대로 말하라.
  2. Metadata가 없거나 corrupt일 때 SKIP이 위험한 이유와 안전한 상태 전이를 설명하라.
  3. 최소 bytes plan과 최소 total-cost plan이 다른 예를 수치로 설명하라.

짧은 정답·채점 기준

어제 1마지막 4 bytes는 PAR1, 그 앞 little-endian 4 bytes는 footer length다. file_size-8-footer_len이 footer start다.
어제 2max<4 또는 min>7이면 skip, 아니면 candidate READ다.
어제 3Dictionary page offset이 있으면 그것, 없으면 data page offset을 start로 하고 total_compressed_size를 더해 end를 만든다.
오늘 1Control: query→snapshot/schema→metadata→skip/read→ranges/batch. Data: storage bytes→decompress→decode→selection/nested materialization→result.
오늘 2불가능함을 증명하지 못했으므로 SKIP은 false negative를 만들 수 있다. Unknown→READ, invalid→quarantine 또는 full-read fallback이 안전하다.
오늘 3100×4 KB는 400 KB지만 100 requests다. 1 MB 병합 read가 latency/request charge가 큰 remote storage에서 더 빠를 수 있다.

채점: 각 2점, 총 12점. 10점 이상 통과. Metadata decision과 byte movement, decode·correctness·failure fallback을 한 그림으로 연결하면 면접 Level 3다.

11. 공식 자료

  • Apache Parquet — File Format: File→row group→column chunk→page 계층과 metadata 기반 읽기 구조를 확인한다.
  • Apache Parquet — Page Index: ColumnIndex·OffsetIndex로 page skip과 row range를 연결하는 계약을 확인한다.
  • Apache parquet-format — parquet.thrift: Footer, statistics, page/column metadata의 wire contract를 확인한다.
  • Apache ORC Specification: Stripe, index/data/footer streams와 row index·Bloom filter layout을 확인한다.

Format specification과 query engine의 실제 지원 범위는 같다고 가정하지 않는다. 배포 engine/version의 plan과 scan metrics로 사용 여부를 검증한다.
