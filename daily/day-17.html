Protobuf field number·wire type

Schema field에서 tag·payload·unknown-field skip까지 · 예상 학습 55분 + 실습 35분
한 줄 요약
Protobuf binary record는 field name 대신 field number와 wire type을 합친 varint tag를 쓰며, parser는 wire type으로 payload 경계를 찾아 알려진 field는 schema 의미로 해석하고 모르는 field는 안전하게 건너뛴다. 따라서 번호는 영구 identity이고, 재사용은 parse 성공 뒤의 조용한 의미 오염을 만든다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의

2. 왜 중요한가

Field name user_id는 개발자가 읽는 schema와 generated API에 있지만 binary payload에는 반복되지 않는다. Wire에는 번호와 경계만 있으므로 이름을 바꾸되 같은 번호·호환 type을 유지하는 변경과, 번호를 바꾸는 변경은 완전히 다르다. 번호 변경은 wire 관점에서 기존 field 삭제와 새 field 추가다.

더 위험한 경우는 삭제한 번호를 다른 의미로 재사용하는 것이다. 예전 로그·queue·cache·mobile client가 email = 5를 보내는데 새 server가 is_admin = 5로 읽으면, wire type이 우연히 맞을 때 parser는 성공할 수 있다. Parse success는 semantic correctness가 아니다.

오늘의 핵심 불변식: 한 message type에서 field number는 배포가 끝나도 재사용하지 않는 영구 identity다. Decode 성공은 bounded byte consumption, schema match, unknown-field 정책과 business invariant까지 통과한 뒤에만 확정한다.

3. 아키텍처 그림과 요청 흐름

id = 1, name = 2, values

② Protobuf message bytes

↓ outer frame: length/header/checksum + immutable transport
③ Consumer parser
tag → field number + wire type → bounded payload cursor
↓ known: schema decode · unknown: skip/preserve · malformed: reject
④ Generated message object

⑤ Durable result or quarantine
reason code · original frame · schema/build provenance
Data path: logical fields → tag/value bytes → frame → parser cursor → typed object → sink.
Control path: schema revision, generated-code build, field-number ledger, compatibility gate, size/recursion limits와 rollout 상태를 전달한다.
  1. Compile: .proto에서 field number·declared type·presence 규칙을 읽어 encoder/decoder를 생성한다.
  2. Encode tag: Encoder는 field number를 왼쪽으로 3bit 옮기고 wire type을 낮은 3bit에 합친 뒤 varint로 쓴다.
  3. Encode payload: Wire type 0은 varint, 1은 8 bytes, 2는 length+bytes, 5는 4 bytes다. Group wire types 3·4는 legacy 경계다.
  4. Frame and publish: 메시지 bytes 밖에서 length·schema/service version·checksum·idempotency key를 결합하고 완전한 frame만 공개한다.
  5. Parse tag: Consumer는 tag varint를 bounded하게 읽고 field number 0, invalid wire type, overlong varint를 거부한다.
  6. Dispatch: 알려진 번호는 schema type으로 해석하고, 모르는 번호는 wire type에 맞게 정확히 소비하거나 보존한다.
  7. Commit: Frame을 끝까지 소비하고 required business invariant·unknown-field metric·sink durability를 확인한 뒤 checkpoint한다.

4. CS 내부 동작

4.1 Tag는 identity와 byte 경계를 압축한다

field 1의 int32는 wire type 0이므로 tag 값은 (1 << 3) | 0 = 8, byte는 08이다. 값 150은 varint 96 01이므로 전체 record는 08 96 01이다. 낮은 3 bits는 wire type, 나머지 상위 bits는 field number다.

Tag 자체도 varint라서 자주 쓰는 field에 작은 번호를 주면 반복 비용이 줄어든다. Wire type 0~5 기준 field 1~15의 tag는 1 byte, 16~2047은 2 bytes다. 하지만 이미 배포한 번호를 크기 최적화 목적으로 재번호화하면 호환성을 깨뜨린다.

4.2 Wire type은 semantic type이 아니다

IDWire type경계와 대표 schema types
0VARINTContinuation bit가 끝날 때까지. int32/64, uint32/64, sint32/64, bool, enum.
1I64정확히 8 bytes, little-endian. fixed64, sfixed64, double.
2LENVarint length 뒤 N bytes. string, bytes, submessage, packed repeated scalar.
3 / 4SGROUP / EGROUPDeprecated group 시작/끝. Skip할 때 nesting과 matching field를 추적해야 한다.
5I32정확히 4 bytes, little-endian. fixed32, sfixed32, float.

int32, bool, enum은 모두 wire type 0이다. 따라서 번호를 재사용하며 int32를 bool로 바꾸면 old 값 150이 “non-zero → true”로 조용히 바뀔 수 있다. Wire type 일치는 payload 경계만 보장할 뿐 의미 호환을 보장하지 않는다.

4.3 Unknown field skip이 forward evolution의 기초다

Old reader가 new field number를 만나도 tag에서 wire type을 얻어 payload를 소비할 수 있다. VARINT는 종료 byte까지, I64/I32는 고정 byte 수, LEN은 length를 검증한 뒤 그만큼 이동한다. 이 때문에 old reader는 새 field를 몰라도 뒤에 오는 known field를 계속 읽을 수 있다.

다만 “skip 가능”과 “round-trip 보존”은 다르다. Binary runtime은 보통 unknown fields를 message state에 보존하지만 언어·runtime API, 명시적 discard, ProtoJSON/Text 변환, object 재구성 과정에서 사라질 수 있다. Proxy가 미래 field를 통과시켜야 한다면 실제 runtime/version으로 golden bytes round-trip을 검증한다.

4.4 LEN은 allocation 명령이 아니라 검증할 주장이다

Length prefix가 1GB라고 적혀 있어도 즉시 1GB를 할당하면 안 된다. 먼저 outer frame remaining, application max field length, total message budget와 integer overflow를 확인한다. Submessage라면 부모 cursor에 bounded slice를 만들고 recursion depth·field count·CPU budget도 제한한다.

4.5 Field order와 byte equality는 계약이 아니다

Field는 어떤 순서로 도착해도 parse되어야 하며 serializer의 출력 순서는 보장되지 않는다. 같은 logical message가 항상 같은 bytes가 된다고 가정해 raw bytes를 cache key·signature·dedup key로 쓰면 runtime upgrade에서 깨질 수 있다. Deterministic serialization도 특정 binary에서의 재현성을 돕는 옵션이지 서로 다른 언어·버전의 canonical format을 자동 보장하지 않는다.

4.6 Protobuf message와 transport frame을 분리한다

(tag, value)* stream은 parser가 주어진 buffer 끝까지 읽는 구조다. TCP나 concatenated file에서 message A가 어디서 끝나는지는 별도 length prefix, record container, RPC envelope가 정해야 한다. Partial frame을 complete message로 넘기면 LEN EOF나 varint truncation이 발생하고, 재시도 경계도 잃는다.

Anti-pattern·edge case·version 차이

  • Field name이 같으면 같은 field: Binary identity는 번호다. 이름만 같고 번호가 다르면 새 field다.
  • Wire type이 같으니 type 변경 가능: 경계가 같아도 signedness, enum, bool, unit과 authorization 의미가 다르다.
  • 삭제 후 번호 재사용: 오래된 log, retry queue, offline client, rollback binary가 다시 나타난다.
  • Unknown field는 항상 보존: ProtoJSON/Text bridge, builder 재구성, discard API와 runtime 차이를 확인한다.
  • LEN을 신뢰하고 allocate: OOM, integer overflow, CPU/recursion DoS를 부른다.
  • Serialized bytes로 equality: Field order와 deterministic behavior는 canonical cross-runtime 계약이 아니다.
  • Protobuf가 message framing 제공: Stream·file에서는 바깥 length/container가 필요하다.
  • Field 0 허용: 유효한 field number가 아니므로 tag 0은 malformed로 거부한다.
  • Wire type 6·7 skip: 정의되지 않은 wire type은 길이를 알 수 없어 안전하게 건너뛸 수 없다.
  • Edition/proto2/proto3 동작 동일: Presence, packed defaults, enum과 generated API는 syntax·edition·runtime에 따라 다를 수 있으므로 배포 조합을 고정해 테스트한다.

7. 35분 실습: tag parser·unknown skip·번호 재사용

목표: Python 표준 라이브러리만으로 tag를 encode/decode하고, 알려지지 않은 VARINT·I32 field를 건너뛰며, 잘린 LEN과 field number 재사용의 차이를 관찰한다.

사전 조건: Python 3.9 이상. 외부 package와 protoc는 필요 없다. Production parser를 구현하려는 실습이 아니라 byte mental model을 검증하는 최소 실험이다.

실행 전 예측: Field 1/WIRE 0 tag, field 2/WIRE 2 tag, field 15/WIRE 0 tag를 16진수로 적는다. Old reader가 field 9를 몰라도 field 2를 읽을 수 있는 이유, bytes 08 96 01을 bool field 1로 재해석한 결과를 먼저 예상한다.

7.1 Bounded wire scanner

python3 - <<'PY' from struct import pack def enc_varint(n): out = bytearray() while n > 0x7f: out.append((n & 0x7f) | 0x80); n >>= 7 out.append(n); return bytes(out) def tag(field_no, wire): assert 1 <= field_no <= 536_870_911 and wire in (0, 1, 2, 3, 4, 5) return enc_varint((field_no << 3) | wire) def read_varint(buf, pos, max_bytes=10): value = 0 for i in range(max_bytes): if pos >= len(buf): raise ValueError("TRUNCATED_VARINT") b = buf[pos]; pos += 1; value |= (b & 0x7f) << (7 * i) if b < 0x80: return value, pos raise ValueError("OVERLONG_VARINT") def scan(buf, known={1:"id", 2:"name"}, max_len=64): pos, rows = 0, [] while pos < len(buf): key, pos = read_varint(buf, pos, 5) field_no, wire = key >> 3, key & 7 if field_no == 0: raise ValueError("FIELD_ZERO") start = pos if wire == 0: value, pos = read_varint(buf, pos) elif wire == 1: if len(buf) - pos < 8: raise ValueError("TRUNCATED_I64") value, pos = buf[pos:pos+8], pos+8 elif wire == 2: size, pos = read_varint(buf, pos, 5) if size > max_len: raise ValueError("LEN_LIMIT") if size > len(buf) - pos: raise ValueError("LEN_EXCEEDS_FRAME") value, pos = buf[pos:pos+size], pos+size elif wire == 5: if len(buf) - pos < 4: raise ValueError("TRUNCATED_I32") value, pos = buf[pos:pos+4], pos+4 else: raise ValueError("GROUP_OR_INVALID_WIRE_NOT_SUPPORTED_IN_LAB") rows.append((field_no, wire, known.get(field_no, "UNKNOWN"), start, pos, value)) return rows msg = b"".join([ tag(1, 0) + enc_varint(150), tag(9, 5) + pack("<I", 0x12345678), tag(15, 0) + enc_varint(7), tag(2, 2) + enc_varint(3) + b"kim", ]) print("bytes:", msg.hex(" ")) for row in scan(msg): print(row[:6]) print("tags:", tag(1,0).hex(), tag(2,2).hex(), tag(15,0).hex()) PY

예상 관찰: Tags는 08, 12, 78이다. Reader가 모르는 field 9/I32와 15/VARINT도 정확히 소비하므로 마지막 field 2의 kim을 정상적으로 찾는다. Field order는 schema 선언 순서와 달라도 된다.

7.2 실패 주입과 silent semantic corruption

python3 - <<'PY' def read_varint(buf, pos=0, max_bytes=10): value = 0 for i in range(max_bytes): if pos >= len(buf): raise ValueError("TRUNCATED_VARINT") b = buf[pos]; pos += 1; value |= (b & 0x7f) << (7*i) if b < 0x80: return value, pos raise ValueError("OVERLONG_VARINT") def read_one_len(buf, max_len=64): key, pos = read_varint(buf, 0, 5) if key >> 3 == 0 or key & 7 != 2: raise ValueError("BAD_TAG") size, pos = read_varint(buf, pos, 5) if size > max_len: raise ValueError("LEN_LIMIT") if size > len(buf) - pos: raise ValueError("LEN_EXCEEDS_FRAME") return buf[pos:pos+size] cases = { "truncated_len": bytes.fromhex("12 05 61 62"), "field_zero": bytes.fromhex("00 01"), "overlong_tag": bytes.fromhex("80 80 80 80 80 00"), } for name, raw in cases.items(): try: if name == "truncated_len": print(name, read_one_len(raw)) else: key, _ = read_varint(raw, 0, 5) if key >> 3 == 0: raise ValueError("FIELD_ZERO") print(name, key) except Exception as e: print(name, "REJECT", str(e)) # Old schema: int32 score = 1. New broken schema: bool is_admin = 1. raw = bytes.fromhex("08 96 01") key, pos = read_varint(raw); value, pos = read_varint(raw, pos) print("same bytes, old meaning score=", value) print("same bytes, reused meaning is_admin=", bool(value), "cursor=", pos) PY

예상 관찰: 잘린 LEN·field zero·overlong tag는 cursor를 commit하지 않고 명시적으로 거부된다. 반면 번호 1을 bool로 재사용한 경우 같은 bytes가 score=150과 is_admin=true로 모두 parse된다. 이것이 번호 재사용이 단순 parse error보다 위험한 이유다.

7.3 자주 나는 오류와 해결·cleanup

  • Hex 예상이 다름: Tag와 value는 각각 별도 varint다. 먼저 key integer를 계산한 뒤 byte로 나눈다.
  • String을 바로 읽음: LEN은 length varint를 검증한 뒤 payload slice를 만든다.
  • Unknown을 1 byte만 skip: Wire type별 종료 규칙을 따라야 다음 tag 경계를 보존한다.
  • Group 입력: 이 최소 lab은 3/4를 의도적으로 거부한다. Production runtime은 nesting·matching end-group과 depth limit을 구현한다.

Cleanup: 위 명령은 파일·package·container를 만들지 않으므로 정리할 것이 없다. Shell history에 민감한 실제 payload를 붙여 넣지 않는다.

8. 놓치기 쉬운 함정

  1. Field number는 database column 순서가 아니라 wire identity다.
  2. Tag의 낮은 3 bits만 wire type이며 declared schema type 전체가 아니다.
  3. Unknown field를 skip할 수 있어도 application이 새 의미를 이해하는 것은 아니다.
  4. Unknown field preservation은 JSON bridge나 object reconstruction을 지나며 깨질 수 있다.
  5. Length prefix를 검증하기 전에 allocation하거나 cursor를 advance하지 않는다.
  6. 같은 logical message의 serialized bytes가 항상 동일하다고 가정하지 않는다.
  7. Field 이름 rename과 field number 변경을 같은 작업으로 취급하지 않는다.
  8. 삭제한 번호는 retention이 끝나도 reserve한다. Offline copy와 rollback binary는 더 오래 산다.
  9. Parser success 뒤에도 enum/range/PII/authorization invariant를 검증한다.
  10. Protobuf message 자체와 stream/file의 outer frame을 분리한다.

9. 대기업 기술 면접 질문

Q1. Protobuf가 새 field를 모르는 old reader에서도 동작하는 원리를 byte 단위로 설명하세요.

좋은 답변 구조: (field_number << 3) | wire_type tag부터 계산한다 → wire type별 payload 경계를 그린다 → known dispatch와 unknown skip/preserve를 구분한다 → LEN limit·invalid wire·partial frame 실패 창을 말한다 → unknown metric, reader-first rollout, JSON bridge 검증과 rollback을 제시한다.

Q2. Field number 재사용이 왜 parse error보다 위험할 수 있습니까?

좋은 답변 구조: 이름이 binary에 없고 번호가 identity임을 말한다 → 같은 wire type의 여러 semantic types를 예로 든다 → old bytes를 new schema로 읽어 silent corruption/PII·권한 문제를 만든다고 설명한다 → log retention·offline client·rollback을 포함한 failure window를 수치로 가정한다 → reserved, 새 번호 dual-write/read, canary와 aggregate 검증으로 복구한다.

Q3. 인터넷에서 받은 Protobuf payload parser를 어떻게 방어적으로 설계합니까?

좋은 답변 구조: Outer authenticated frame과 Protobuf 내부를 분리한다 → max frame/message/field, varint byte 수, recursion/repeated/unknown budget과 deadline을 둔다 → allocation 전 remaining·overflow를 검증한다 → immutable evidence와 reason taxonomy를 남긴다 → quarantine·backpressure·idempotent replay와 fail-open/closed 비용을 방어한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Avro decoder cursor와 결과 object는 각각 writer/reader schema 중 무엇을 따르는가?
  2. Reader-only field의 default는 어디서 생기며, default 변경이 왜 과거 결과를 바꾸는가?
  3. Exact writer schema를 잃은 payload에 latest schema를 적용하면 안 되는 이유는?

오늘 내용 확인 3문제

  1. Field 15, wire type 0과 field 16, wire type 2의 tag integer·byte 수를 계산하라.
  2. Unknown LEN field를 안전하게 skip하는 검증 순서를 말하라.
  3. int32 score = 5를 삭제하고 bool is_admin = 5로 재사용했을 때 가능한 장애와 안전한 migration을 설명하라.

짧은 정답·채점 기준

어제 1Cursor는 writer field order/type으로 bytes를 소비하고, 결과는 reader의 matched fields·alias·promotion·default 의미로 구성한다.
어제 2Reader schema가 read-time에 materialize한다. 따라서 동일 old bytes도 reader default가 바뀌면 logical result가 바뀐다.
어제 3Avro datum은 field name/tag를 반복하지 않아 wrong schema가 cursor와 값을 바꾸며, 예외 없이 오해석될 수도 있다.
오늘 115/0은 120, varint 78 1 byte. 16/2는 130, varint 82 01 2 bytes다.
오늘 2Tag bounded decode → valid field/wire 확인 → length bounded decode → app max와 integer overflow → frame remaining → bounded slice/cursor commit 순서다.
오늘 3Old score의 non-zero가 true로 해석되어 권한 오염이 가능하다. 번호 5를 reserved하고 새 번호에 is_admin을 추가해 readers-first dual-write/read·aggregate 검증 후 전환한다.

채점: 각 2점, 총 12점. 10점 이상 통과. 오늘 답변에서 tag 계산, wire 경계, silent semantic corruption, bounded parser, rollout·rollback을 하나의 흐름으로 연결하면 면접 Level 3다.
