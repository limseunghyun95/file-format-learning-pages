FILE FORMAT · WEEK 1 / DAY 01

file, byte, encoding, serialization의 차이

파일·byte·schema 정신 모델 · 예상 학습 30분 + 실습 30분

한 줄 요약
파일은 이름 붙은 byte sequence이고, encoding은 의미와 byte 사이의 규칙이며, serialization은 구조화된 값을 전송·저장 가능한 byte로 바꾸는 계약이다. 이 경계를 섞으면 “파일은 열리지만 값은 틀린” 조용한 데이터 장애가 생긴다.

1. 선수 용어 사전

Bit / ByteBit는 0 또는 1, byte는 보통 8bit 묶음이다. Storage와 network API는 의미가 아니라 byte를 다룬다.
FileFilesystem/object storage에서 이름·경로·metadata로 식별되는 유한한 byte sequence. 확장자는 해석 힌트일 뿐 실제 내용을 강제하지 않는다.
Character / Code point문자와 Unicode가 부여한 추상 번호를 구분한다. 화면의 grapheme 하나가 code point 여러 개로 구성될 수도 있다.
Encoding추상 값이나 문자를 byte sequence로 표현하는 규칙. UTF-8은 Unicode scalar value를 1~4 octet으로 표현한다.
Serialization객체·row·message 같은 구조화된 값을 저장·전송 가능한 표현으로 바꾸는 과정. field order, type, null, default, framing이 계약에 포함된다.
Schemafield 이름·type·필수 여부·기본값과 호환 규칙을 정의하는 producer-consumer 계약.
Parser / DecoderParser는 문법 구조를 해석하고 decoder는 encoded byte를 값으로 복원한다. 실제 library에서는 두 책임이 결합될 수 있다.
Framing연속 byte에서 record의 시작·끝을 알아내는 규칙. newline, length prefix, container metadata 등이 예다.

2. 값이 파일이 되는 전체 경로

① Logical value
{id: 7, name: "승현", active: true}
↓ schema · serialization
② Format structure
JSON token / Avro field / Parquet column page
↓ character·integer encoding · compression
③ Byte sequence
7b 22 69 64 ... 또는 binary layout
↓ buffered write · fsync/close · object PUT
④ Stored file/object
path · size · checksum/etag · content type
↓ read · decompress · decode · parse · validate
⑤ Consumer value
schema와 의미가 맞을 때만 원래 값 복원
  1. Application은 memory의 logical value를 가진다. 아직 file도 byte도 아니다.
  2. Serializer가 schema와 format 규칙을 적용한다. JSON은 text token을, Avro/Protobuf는 field identifier와 binary encoding을, Parquet는 column chunk·page·metadata 구조를 만든다.
  3. 문자는 UTF-8 같은 character encoding을 거쳐 byte가 된다. Integer도 fixed-width, varint, little/big endian 같은 규칙이 필요하다.
  4. Writer가 byte를 buffer와 kernel page cache를 거쳐 storage에 기록한다. write() 성공, process close, durable storage 반영은 같은 시점이 아니다.
  5. Reader는 역순으로 복원한다. 압축 codec·format·schema·encoding 중 하나라도 다르면 즉시 오류, 깨진 문자, 잘못된 값, schema drift 중 하나가 나타난다.

3. “확장자 = 포맷”이 아닌 이유

.json은 filename suffix다. OS가 내용이 JSON인지 보장하지 않는다. HTML을 data.json으로 저장해도 byte는 그대로다. 반대로 확장자가 없어도 content가 유효한 JSON일 수 있다. Production에서는 확장자, MIME/content-type, magic bytes, container metadata, schema registry, 실제 parser 검증을 계층별로 사용한다.

조용한 실패: CSV parser가 delimiter나 quote 규칙을 잘못 가정하면 파일은 “성공적으로” 읽히면서 column이 밀릴 수 있다. 성공/실패 boolean만 보지 말고 row count, null ratio, type range, checksum과 quarantine 정책을 둔다.

4. CS 내부 동작

정보와 표현의 분리

숫자 65, 문자 “A”, byte 0x41은 특정 문맥에서 연결되지만 동일한 개념은 아니다. 0x41을 unsigned integer로 보면 65, ASCII/UTF-8 character로 보면 A, bitmask로 보면 여섯 번째 bit가 켜진 값이다. Byte 자체에는 type이 없고 schema와 decoding context가 의미를 부여한다.

UTF-8과 경계

UTF-8은 ASCII 범위를 같은 1byte 값으로 유지하고, 그 밖의 Unicode scalar value를 가변 길이 byte sequence로 표현한다. 따라서 byte index와 character index는 일반적으로 같지 않다. Multi-byte character 중간에서 file이나 network chunk가 잘리면 decoder는 incomplete sequence를 만난다. Chunk boundary가 character boundary를 보장한다고 가정하면 안 된다.

Serialization의 상태 소유자

  • Producer schema: 어떤 field와 logical type을 썼는지 소유한다.
  • Wire/file format: field와 byte의 배치·framing·encoding을 소유한다.
  • Consumer schema: byte를 어떤 type과 default로 복원할지 소유한다.
  • Container metadata: codec, row group, statistics, embedded schema 등 self-description을 제공할 수 있다.

핵심 불변식은 producer가 쓴 표현을 consumer가 호환 가능한 규칙으로 해석해야 한다는 것이다. “Parser가 열었다”만으로 business 의미가 보존됐다고 말할 수 없다.

Durability와 partial file

Process가 buffer에 쓴 data, kernel이 page cache에 받은 data, disk/object storage가 durable하게 보관한 data는 서로 다른 상태다. Local filesystem의 atomic rename pattern, object storage의 immutable object + manifest/pointer publish, checksum·size 검증은 partial publish를 reader에게 감추기 위한 protocol이다.

6. 장애 대응 표

상황: 어제 적재된 파일의 한글이 깨지고 일부 row의 column이 밀렸다.

증상replacement character(�), decode error, column 수 불일치, null 급증, row count 감소.
먼저 수집할 증거/지표원본 byte checksum·size, 앞/뒤 hex, encoding 선언과 BOM, delimiter/quote/newline, producer version, schema ID, parser 옵션, rejected row sample.
가능한 가설UTF-8이 아닌 byte, multi-byte 중간 절단, CRLF/LF 혼용, quote escape 오류, truncated upload, schema/order mismatch, 잘못된 decompressor.
안전한 첫 조치문제 object를 immutable quarantine에 복사하고 downstream publish를 멈춘다. 원본 byte를 보존한 채 strict decoder와 parser로 최초 실패 offset을 찾는다.
Rollback/복구Known-good producer/schema로 source에서 재생성한다. 불가피한 transcoding은 원본·도구 버전·loss count를 기록하고 row-level reconciliation 뒤 publish한다.
하지 말아야 할 조치무조건 errors=ignore로 byte를 버리거나 확장자만 바꾸지 않는다. 손상 원본 위에 수정본을 덮어쓰지 않는다. 실패 row를 조용히 drop하지 않는다.

7. 30분 재현 실습

목표: 같은 logical row가 JSON text와 UTF-8 byte에서 어떻게 보이고, 잘린 multi-byte sequence가 왜 decode되지 않는지 관찰한다.

먼저 예측: 문자열 “승현”은 2글자이므로 UTF-8에서도 2byte일까?

make build
make shell

python - <<'PY'
import json
row = {"id": 7, "name": "승현", "active": True}
text = json.dumps(row, ensure_ascii=False, separators=(",", ":"))
raw = text.encode("utf-8")
print("logical:", row)
print("text:", text)
print("chars:", len(text), "bytes:", len(raw))
print("hex:", raw.hex(" "))
open("/tmp/day01.json", "wb").write(raw)
print("round-trip:", json.loads(raw.decode("utf-8")))
print("tail bytes:", raw[-8:])
PY

od -An -tx1c /tmp/day01.json

python - <<'PY'
raw = open("/tmp/day01.json", "rb").read()
for cut in range(1, 5):
    damaged = raw[:-cut]
    try:
        damaged.decode("utf-8")
        print(cut, "byte cut: UTF-8 valid, JSON may still be incomplete")
    except UnicodeDecodeError as e:
        print(cut, "byte cut: decode failure at", e.start)
PY

예상 관찰: 한글 code point는 UTF-8에서 각각 3byte다. File을 어디서 자르느냐에 따라 UTF-8 decoding 단계에서 실패할 수도 있고, UTF-8은 유효하지만 JSON framing이 불완전해 parser 단계에서 실패할 수도 있다. 두 실패는 원인과 복구 방법이 다르다.

추가 실패 주입: raw.decode("latin-1")로 같은 byte를 잘못 해석해 보라. 오류 없이 깨진 문자열이 나오는 것이 즉시 실패보다 위험할 수 있다.

Cleanup: container 종료 시 /tmp/day01.json은 사라진다. 별도 삭제가 필요하면 정확한 파일만 지운다.

8. 놓치기 쉬운 함정

  1. Binary = 암호화: Binary는 byte layout 방식이지 confidentiality를 뜻하지 않는다.
  2. Text = schema 없음: CSV/JSON도 이름·type·null·delimiter에 대한 schema 계약이 필요하다.
  3. Self-describing = 완전한 의미: Embedded type이 있어도 통화 단위·timezone·business invariant는 별도 계약이다.
  4. Compression과 format 혼동: gzip은 byte stream compression이며 CSV/JSON/Parquet 같은 logical layout을 대체하지 않는다.
  5. Default encoding 의존: OS·runtime locale에 따라 결과가 달라진다. Boundary에서 encoding을 명시한다.
  6. Parser permissive mode 남용: 처리 성공률을 높이는 대신 데이터 손실을 숨길 수 있다. reject count와 sample을 관측한다.

9. 대기업 기술 면접 질문

Q1. JSON과 Parquet 중 무엇을 선택하겠습니까?

좋은 답변 구조: producer/consumer와 access pattern → row 수·column 수·selectivity·파일 크기 수치 → schema evolution → human debugging → scan I/O·CPU/compression → streaming/batch 경계 → benchmark와 migration 비용까지 설명한다. “Parquet가 무조건 빠르다”로 끝내지 않는다.

Q2. Encoding 오류를 어떻게 무손실 복구합니까?

좋은 답변 구조: 원본 byte 보존 → checksum·출처·producer version → BOM/magic/통계적 추측은 증거일 뿐임을 명시 → strict decode 후보 → loss count → source 재생성 우선 → quarantine·재처리·감사 기록을 제시한다.

Q3. Schema가 있는데도 데이터 계약 장애가 나는 이유는?

좋은 답변 구조: Physical type과 business semantics 구분 → null/default/rename/enum/timezone/decimal precision → producer-consumer 배포 순서 → compatibility gate → canary와 rollback → semantic validation을 설명한다.

10. 선수 지식 확인과 정답

  1. 10진수 65와 byte 0x41은 언제 같은 의미인가?
  2. File extension을 바꾸면 content도 변하는가?
  3. Compression은 serialization 전에만 해야 하는가?

정답: ① Decoder가 그 byte를 unsigned integer/ASCII 규칙으로 해석하는 문맥에서 연결된다. ② 이름만 바뀌며 byte는 변하지 않는다. ③ 일반적으로 serialized byte stream에 codec을 적용하지만 container format이 column/page 단위 compression을 정의할 수도 있어 계층을 명시해야 한다.
