한 줄 요약
컬럼형 저장의 핵심은 “행을 세로로 보관한다”가 아니라, 분석 쿼리가 필요한 열의 연속 byte만 읽고 같은 type의 값을 batch로 decode·계산하게 만드는 물리적 locality다. 이득은 projection이 좁고 scan·aggregate가 클수록 커지며, point lookup·한 행 write·wide projection에서는 반대로 비용이 될 수 있다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의
OLAPOnline Analytical Processing. 많은 행을 읽어 필터·집계·조인하는 분석 workload다. “지난달 지역별 매출 합계”가 대표적이다.
OLTPOnline Transaction Processing. 소수 행을 key로 찾고 짧게 읽고 쓰는 거래 workload다. 주문 한 건 조회·수정이 대표적이다.
Row layout한 행의 모든 field byte를 가까이 둔다. 한 행 전체를 가져올 때 locality가 좋지만 한 열만 scan해도 다른 field가 함께 읽힐 수 있다.
Columnar layout같은 열의 여러 행 값을 가까이 둔다. 실제 Parquet·ORC는 파일 전체를 열별 한 덩어리로 만들지 않고 row group·stripe 안에서 열별 stream을 구성한다.
Locality곧 사용할 byte가 저장장치·메모리·CPU cache에서 가까이 있는 성질이다. Spatial locality는 인접 주소, temporal locality는 최근 값을 다시 쓰는 성질이다.
Cache lineCPU cache와 memory 사이를 옮기는 고정 크기 block이다. 64B는 흔한 예시지만 모든 CPU의 보편 규칙은 아니다.
ProjectionSELECT amount, region처럼 query가 실제 결과·계산에 요구하는 열 집합이다. Projection pushdown은 reader가 불필요한 열을 읽지 않게 한다.
SelectivityPredicate를 통과하는 행의 비율이다. 1억 행 중 100만 행이면 1%다. 읽기 전에 skip 가능한 범위와 decode 후 걸러지는 비율을 구분한다.
I/O amplification논리적으로 필요한 byte보다 실제 storage·network에서 더 많이 읽는 비율이다. 필요한 1GB를 위해 20GB를 읽으면 20배다.
Vectorization값을 한 건씩 object로 처리하지 않고 동일 type의 연속 batch로 decode·계산하는 실행 방식이다. Function call·branch·object allocation을 줄일 수 있다.
SIMDSingle Instruction, Multiple Data. 한 명령으로 여러 숫자 lane을 처리하는 CPU 기능이다. 연속되고 같은 type인 vector가 활용하기 쉽다.
Late materializationPredicate 열을 먼저 읽어 통과 row 위치를 selection vector로 만든 뒤, 필요한 나머지 열을 늦게 조합하는 기법이다.

2. 왜 중요한가

1억 행, 평균 행 폭 200B인 table은 raw 기준 약 20GB다. Query가 8B amount와 8B timestamp만 필요하다면 projection byte는 행당 16B, 총 1.6GB다. 압축·metadata·request 비용 전의 단순 모델만으로도 row scan은 필요한 byte의 약 12.5배를 옮길 수 있다. 컬럼형은 16B에 가까운 연속 영역만 요청할 가능성을 만든다.

하지만 “Parquet라서 12.5배 빠르다”는 결론은 틀리다. Predicate로 row group을 skip했는지, object storage range request가 몇 번인지, compression codec의 CPU 비용, cache hit, decode vector 폭, projected 열 수, output cardinality가 합쳐져 wall time이 된다. 면접과 실무에서는 format 이름이 아니라 bytes read → requests → decode CPU → materialization → output을 설명해야 한다.

오늘의 비용식: 대략적인 scan 비용은 T ≈ request latency × request count + bytes read / effective bandwidth + decode CPU + operator CPU + materialization이다. 이 식은 예측 모델이며 실제 engine profile로 각 항을 검증해야 한다.

4. CS 내부 동작

4.1 Cache line과 spatial locality

예시로 64B cache line과 64B fixed row를 가정하자. amount가 8B여도 row layout에서는 다음 amount가 64B 뒤에 있어 cache line마다 필요한 byte가 8B뿐일 수 있다. 유효 사용률은 8/64=12.5%다. Amount column이 연속이면 한 cache line에 8개의 amount가 들어가므로 scan loop가 가져온 byte 대부분을 계산에 쓴다. 실제 CPU prefetcher·cache hierarchy·alignment는 machine마다 다르므로 profile로 확인한다.

4.2 Compression은 locality의 2차 효과다

같은 type과 비슷한 값이 모이면 dictionary, run-length encoding, delta, bit packing과 일반 compression이 반복 패턴을 더 쉽게 찾는다. Row layout에서 status·timestamp·문자열이 교차하면 entropy model의 locality가 약해질 수 있다. 다만 high-cardinality encrypted value나 이미 압축된 blob은 columnar만으로 크게 줄지 않으며 codec CPU가 I/O 절감보다 비쌀 수도 있다.

4.3 Vector batch·branch·SIMD

Typed column vector는 매 row마다 type tag를 확인하고 object를 만드는 일을 줄인다. Null은 validity bitmap, 조건 통과 위치는 selection vector로 분리할 수 있다. 동일 연산을 batch loop에 적용하면 branch prediction이 쉬워지고 compiler·runtime이 SIMD를 쓰기 좋아진다. 그러나 variable-length string, nested value, 높은 null branching, UDF는 이 경로를 깨뜨릴 수 있다.

4.4 Storage request와 failure window

Local disk의 sequential read와 object storage의 여러 range GET은 같은 “1GB read”가 아니다. 너무 작은 page·column chunk·file은 request count와 TLS·queue·metadata overhead를 늘린다. 반대로 row group이 너무 크면 writer memory, retry 범위, tail latency가 커지고 pruning granularity가 거칠어진다. Parquet 공식 configuration의 큰 row group 권고는 HDFS 맥락의 출발점이지 모든 engine·object store에 고정 적용할 정답이 아니다.

Best practice·anti-pattern·engine 차이

  • Best: Query log에서 projection·predicate·scan bytes 분포를 먼저 구하고 file layout을 결정한다.
  • Best: bytes read / projected logical bytes, skipped row groups, range request count를 함께 관측한다.
  • Best: Row group·stripe를 독립 recovery/parallelism 단위로 보고 writer memory와 retry cost를 제한한다.
  • Best: Frequently filtered column의 clustering·statistics 품질을 검증하고 null·NaN·truncated statistics edge case를 fixture로 둔다.
  • Anti-pattern: “Parquet면 빠름”만 믿고 SELECT *, 수 KB small files, UDF로 pushdown을 무력화한다.
  • Anti-pattern: Compression ratio만 최대화하려고 거대한 block을 만들고 latency·memory·pruning을 희생한다.
  • Anti-pattern: Writer가 footer까지 완성하기 전에 catalog에 file path를 공개한다.
  • Edge: High-cardinality string·encrypted payload·already-compressed blob은 dictionary·codec 효과가 제한적이다.
  • Engine: Page index·bloom·vectorized nested decode·predicate pushdown 지원은 engine와 version마다 다르다. Explain plan과 scan profile로 확인한다.
  • Object store: 동일 byte라도 range GET 수가 많으면 latency·request charge가 커진다. Coalescing·prefetch 효과를 측정한다.

가능한 가설Wide projection, pushdown/UDF failure, poor clustering·statistics, row group 과대/과소, small files, range fragmentation, cold cache, expensive codec, scalar fallback, high-cardinality dictionary thrash, corrupt footer/page, partial publish.
안전한 첫 조치Write/publish 확대를 중단하고 affected snapshot을 고정한다. 대표 query 한 개를 baseline과 동일 cache 조건에서 재현해 bytes·requests·CPU 항을 분리한다. Corrupt/partial files는 manifest에서 격리하되 원본 bytes를 보존한다.
Rollback / 복구Last-known-good snapshot/file set으로 atomic pointer를 되돌린다. Bad files를 quarantine하고 committed source로 target size·sort·codec에 맞춰 idempotent rewrite한다. Count·min/max·checksum·business aggregate를 대사한 뒤 새 snapshot을 publish한다.
하지 말아야 할 조치Evidence 없이 cache만 비우기, object를 제자리 overwrite, footer byte 수동 수정, corrupt row skip 후 성공 처리, 모든 query에 무조건 larger block 적용, unrelated files까지 bulk compaction, partial output을 committed snapshot에 섞지 않는다.

7. 35분 실습: 같은 table의 row/column byte locality 측정

목표: Python 표준 라이브러리로 64B fixed row와 분리된 amount/status column을 만들고, 좁은 projection의 물리 byte·compression·scan time을 비교한다. 이는 교육용 memory model이며 Parquet benchmark가 아니다.

사전 조건: Python 3.9 이상, 여유 memory 약 40MB. 외부 package와 파일 생성은 없다.

실행 전 예측: 20만 행에서 amount 8B와 status 1B만 읽을 때 row layout 12.8MB와 column layout 1.8MB의 비율, 결과 합계의 동일성, full projection과 point lookup에서 이득이 왜 줄어드는지 먼저 적는다.

python3 - <<'PY' import struct, time, zlib from array import array N = 200_000 ROW = struct.Struct("<QQqB31s8x") # 64 bytes rows = bytearray(ROW.size * N) amounts = array("q") statuses = bytearray(N) payload = b"A" * 31 for i in range(N): amount = (i % 10_000) - 5_000 status = 1 if i % 4 == 0 else 0 ROW.pack_into(rows, i * ROW.size, i, 1_700_000_000 + i, amount, status, payload) amounts.append(amount) statuses[i] = status def row_query(): total = 0 for off in range(0, len(rows), ROW.size): _, _, amount, status, _ = ROW.unpack_from(rows, off) if status == 1: total += amount return total def col_query(): total = 0 for amount, status in zip(amounts, statuses): if status == 1: total += amount return total def timed(fn): best = float("inf") result = None for _ in range(3): start = time.perf_counter() result = fn() best = min(best, time.perf_counter() - start) return result, best row_bytes = len(rows) projected_bytes = len(amounts) * amounts.itemsize + len(statuses) rr, rt = timed(row_query) cr, ct = timed(col_query) amount_bytes = amounts.tobytes() column_streams = amount_bytes + bytes(statuses) print("row_size=", ROW.size, "rows=", N) print("row_scan_bytes=", row_bytes) print("column_projected_bytes=", projected_bytes) print("io_amplification_model=", round(row_bytes/projected_bytes, 2)) print("same_result=", rr == cr, "result=", rr) print("best_seconds_row_col=", round(rt, 4), round(ct, 4)) print("compressed_row_col=", len(zlib.compress(rows, 6)), len(zlib.compress(column_streams, 6))) # 실패 주입: SELECT * 또는 한 행 point lookup 비용 모델 full_projection = ROW.size * N point_row_ranges = 1 point_column_ranges = 5 request_ms = 8 print("full_projection_ratio=", full_projection/row_bytes) print("point_lookup_request_ms_row_col=", point_row_ranges*request_ms, point_column_ranges*request_ms) assert rr == cr assert row_bytes == 12_800_000 assert projected_bytes == 1_800_000 PY

예상 관찰: 논리 결과는 같고 byte model은 12.8MB 대 1.8MB, 약 7.11배다. 시간과 compression 크기는 machine·Python 구현에 따라 달라지므로 어느 쪽이 몇 배 빠르다고 일반화하지 않는다. 정확한 관찰은 layout과 bytes이며, 성능은 profile 결과다.

실패 주입·자주 나는 오류·cleanup

  • 실패 주입 1: Query를 SELECT *로 바꾸면 projected bytes가 row width에 가까워져 I/O 이득이 사라진다.
  • 실패 주입 2: 한 row의 5개 열을 object store에서 각각 8ms range 요청한다고 가정하면 요청 대기만 40ms다. Row/index lookup 1회 8ms가 유리할 수 있다.
  • 오류: array('q') byte order·itemsize는 platform을 확인해야 portable wire format이 된다. 실무 file format은 명시적 endian/schema를 사용한다.
  • 오류: Python loop time을 SIMD/vectorized engine의 대리 지표로 쓰지 않는다. Bytes·result invariant만 일반화한다.
  • 오류: Compression 비교는 payload distribution에 의존한다. Random·null·high-cardinality fixture를 별도 추가한다.
  • Cleanup: Memory object만 만들고 파일·package·container를 생성하지 않으므로 process 종료와 함께 정리된다.

8. 놓치기 쉬운 함정

  1. Columnar file도 row group·stripe 안에서 열을 나누며, 전역 한 열 파일이 아니다.
  2. Projection selectivity와 predicate selectivity는 다르다.
  3. Statistics는 row group을 skip할 뿐 통과 행의 exact index가 아닐 수 있다.
  4. Bytes 감소와 wall time 감소를 같은 것으로 취급하지 않는다.
  5. Small files는 metadata·listing·request amplification을 만든다.
  6. 거대한 row group은 pruning·retry·writer memory를 악화할 수 있다.
  7. Point lookup·한 행 update에는 row layout이 더 자연스러울 수 있다.
  8. Nested/string/UDF는 scalar fallback과 materialization 비용을 만들 수 있다.
  9. Footer가 존재해도 partial object·wrong offset·checksum failure는 별도 검증이 필요하다.
  10. Cache-warm benchmark 하나로 production P95를 결정하지 않는다.

9. 대기업 기술 면접 질문

Q1. 왜 columnar format이 OLAP에 유리한지 CPU와 storage까지 설명하세요.

좋은 답변 구조: OLAP의 scan·narrow projection을 정의한다 → row width W와 projected P로 bytes를 계산한다 → range read·compression·cache line·typed vector·SIMD 경로를 잇는다 → metadata pruning과 late materialization을 설명한다 → point lookup·wide projection·request overhead라는 반례를 제시한다.

Q2. 100M행×200B table에서 16B만 투영합니다. 20GB와 1.6GB 계산만으로 성능을 확정할 수 있나요?

좋은 답변 구조: 계산을 lower-bound model로 제시한다 → compression, row-group skipping, request count·bandwidth, decode/operator CPU, output cardinality를 추가한다 → cache condition과 concurrency를 통제한 benchmark를 설계한다 → plan/profile의 bytes·requests·CPU·spill 증거로 결론을 갱신한다.

Q3. Parquet 전환 후 P95가 3배 느려졌습니다. 어떻게 진단하고 안전하게 복구합니까?

좋은 답변 구조: Snapshot과 대표 query를 고정한다 → projection/pushdown/skipping/file size/range GET/decode CPU/spill 증거를 수집한다 → small file·wide projection·scalar fallback·poor clustering 가설을 비용 항별로 검증한다 → publish 중단·last-known-good snapshot rollback → quarantine/rewrite/reconcile 후 단계적 재발행을 설명한다.

어제 2유효 tag와 payload라 decode가 성공하지만 old value가 새 semantic으로 commit되어 registry/parser metric이 0일 수 있다.
어제 3새 writer bytes를 old reader가 안전하게 읽는 forward edge, checkpoint·sink state·quarantine·replay까지 되돌릴 수 있어야 한다.
오늘 1Row는 cache line당 8B만 유효할 수 있고 column은 8개 amount를 연속 사용한다. 64B는 예시이며 실제 hardware를 확인한다.
오늘 2Control은 plan→footer/tail→pruning→ranges·budget, data는 compressed pages→typed vectors→selection→late materialization→aggregate다.
오늘 3P가 W에 가까우면 bytes 이득이 줄고, point lookup은 여러 column range의 request latency와 decode/materialization이 한 row/index read보다 클 수 있다.

채점: 각 2점, 총 12점. 10점 이상 통과. Byte 수치, request·CPU 항, success invariant와 반례까지 연결하면 면접 Level 3다.

11. 공식 자료

  • Apache Parquet — File Format: Row group 안에서 column chunk를 배치하고 metadata 뒤 관심 column chunk를 읽는 구조를 확인한다.
  • Apache Parquet — Configurations: Row group·page 크기의 sequential I/O, buffering, header/parse trade-off를 확인한다.
  • Apache Parquet — Data Pages: Page header, repetition/definition level과 encoded value의 물리 순서를 확인한다.
  • Apache ORC — ORC v1 Specification: Stripe·column stream·projection·index/statistics 기반 row-set skipping을 확인한다.

공식 size 권고도 storage·engine 맥락에 따른 시작점이다. 실제 runtime의 vectorization·page index·bloom 지원은 해당 version 문서와 explain/profile로 검증한다.
