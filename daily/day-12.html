한 줄 요약
Type inference는 문자열을 “알아서 이해”하는 기능이 아니라 sample·locale·timezone·range·rounding 정책으로 raw lexeme을 typed value에 투영하는 과정이다. 계약 없이 자동 추론하면 00123, 1,234, 03/04/2026, DST 경계가 서로 다른 값으로 조용히 바뀐다.

2. 왜 중요한가

우편번호 00123을 integer 123으로 바꾸면 leading zero는 복구할 수 없다. 1,234는 한 locale에서는 천이백삼십사, 다른 locale에서는 1.234일 수 있다. 03/04/2026도 3월 4일과 4월 3일이 모두 가능하다. Parser가 오류 없이 값을 만들었다고 해서 의미가 맞는 것은 아니다.

시간은 더 어렵다. 2026-11-01 01:30 America/New_York은 DST 종료 때 서로 다른 두 instants일 수 있고, 2026-03-08 02:30은 그 zone에서 존재하지 않을 수 있다. Host local timezone을 몰래 적용하면 같은 파일이 machine·tzdb version에 따라 다른 UTC를 만든다.

핵심 원칙: Inference 결과는 data fact가 아니라 versioned decision이다. Raw lexeme과 source provenance를 보존하고, explicit schema·locale·date format·timezone·epoch unit이 있는 validated layer를 별도로 만든다.

3. 아키텍처 그림과 요청 흐름

Data path: raw token → candidate → typed value → column/sink.
Control path: schema version, null tokens, decimal/group symbols, accepted date patterns, timezone/fold/gap, epoch unit, precision/scale, overflow·rounding, tzdb version을 배포한다.
  1. Capture: Bytes, quote/presence, source identifier, ingestion time를 immutable raw layer에 남긴다.
  2. Profile: 전체 또는 명시된 sample에서 candidate types와 실패율·min/max·length·distinct patterns를 계산한다. 이 단계는 제안만 한다.
  3. Resolve contract: Column owner가 domain을 기준으로 string/int/decimal/date/timestamp와 locale·zone·unit을 승인한다.
  4. Parse strictly: Lexical pattern을 확인한 뒤 range·precision·calendar validity와 DST fold/gap을 검사한다. 임의 fallback chain은 금지한다.
  5. Validate: Cross-field invariant(예: end ≥ start), null policy, accepted/rejected counts를 검증한다.
  6. Commit: Typed output과 quarantine가 durable해진 뒤 checkpoint한다. Raw-to-typed mapping version이 lineage에 남아야 성공이다.

4. CS 내부 동작

4.1 Inference는 hypothesis selection이다

Parser는 token마다 boolean, integer, decimal, date, timestamp, string 후보를 검사한다. 첫 1,000 rows가 모두 digits면 integer를 선택할 수 있지만 1,001번째 N/A, 12.50, 20자리 ID가 나오면 reject·widen-to-string·null coercion 중 하나를 택해야 한다. 이 정책이 engine/version마다 다르면 같은 bytes가 다른 schema가 된다.

Sample inference는 시간 O(k×c)(sample rows k, candidates c)로 싸지만 rare value를 놓친다. Full scan은 evidence가 좋지만 I/O·latency가 커지고, 여전히 domain 의미(우편번호인지 수량인지)는 알 수 없다. 따라서 inference는 schema proposal과 profiler report로 제한한다.

4.2 Type lattice와 irreversible widening/narrowing

Engine은 보통 candidate conflict를 더 넓은 type으로 승격한다. Integer와 decimal이 섞이면 decimal/float, 숫자와 text가 섞이면 string이 될 수 있다. 하지만 float로 승격하면 decimal 정밀도를 잃을 수 있고, string으로 늦게 승격해도 앞선 values를 이미 integer로 materialize했다면 00123 원형은 돌아오지 않는다.

Typed column은 vectorized execution과 compression에 유리하지만 올바른 type일 때만 그렇다. Mixed-type object column은 branch와 boxing 비용을 늘리고 predicate pushdown/statistics 신뢰성을 떨어뜨린다. Raw와 validated 계층을 분리하면 정확성과 실행 효율을 동시에 얻는다.

4.3 Locale는 문법 계약이지 “사용자 PC 설정”이 아니다

1,234를 comma grouping으로 볼지 decimal separator로 볼지는 source contract가 정해야 한다. Process locale·spreadsheet UI·operator laptop 설정을 암묵적으로 쓰면 재실행 결과가 달라진다. Grouping 크기, non-breaking space, currency symbol, sign 위치도 locale data에 따라 달라질 수 있다.

교환 형식에서는 locale-neutral decimal dot, ISO/RFC profile date처럼 한 문법을 우선하고, 사람 표시 단계에서 locale formatting을 적용한다. Localized input이 unavoidable하면 locale tag를 record/file metadata로 전달하고 strict parser를 column별로 고정한다.

4.4 날짜 문자열은 calendar fields일 뿐 instant가 아니다

2026-04-03은 날짜이고 timezone이 필요하지 않다. 2026-04-03 09:00은 civil datetime이며 zone 없이는 instant가 아니다. 2026-04-03T09:00:00+09:00은 numeric offset 덕분에 instant를 정하지만, “다음 해 서울 09:00” 같은 recurring schedule의 future rules를 표현하려면 zone ID가 필요하다.

Storage contract는 의미에 따라 분리한다. Event occurred_at은 UTC instant + 원 offset/zone provenance, birthday는 date, 매일 09:00 schedule은 local time + IANA zone ID + gap/fold policy가 적합하다. 모든 시간을 UTC timestamp 하나로 우겨 넣으면 civil intent가 사라진다.

4.5 DST fold와 gap resolution

Zone rules가 offset을 바꾸면 local clock이 뒤로 가는 fold에서 같은 civil time이 두 instants에 대응한다. 앞으로 가는 gap에서는 어떤 instant에도 대응하지 않는다. Library가 tzinfo를 붙였다고 valid가 된 것은 아니다. Candidate instants를 UTC로 보냈다가 같은 zone으로 round-trip해 원 civil fields와 일치하는지 검사한다.

Fold는 earlier/later offset 또는 reject 중 business policy를 요구한다. Gap은 reject, 다음 valid instant로 shift, 이전 offset 유지 중 하나를 명시해야 한다. 예약·금융 cutoff·로그 분석마다 정책이 다르며 silent normalization은 금지한다.

4.6 Offset, zone ID, tzdb version

Offset -04:00은 그 instant의 UTC 차이만 알려주고 America/New_York의 DST rules 전체를 알려주지 않는다. Time zone rules는 법·행정 결정으로 변경될 수 있으므로 IANA tz database version도 재현성의 일부다.

과거 event instant가 이미 offset/UTC로 확정됐다면 tzdb update 후에도 instant는 유지해야 한다. Future civil schedule은 새 rules로 재평가할지 원래 계산을 고정할지 product policy가 필요하다. Reprocessing job은 parser·tzdb version을 lineage에 기록한다.

4.7 Epoch 숫자는 unit 없는 물리량이다

1700000000을 seconds로 보면 2023년대 instant지만 milliseconds로 보면 1970년 1월이다. 1700000000000은 milliseconds로 흔해 보여도 magnitude heuristic은 과거/미래 data에서 깨진다. Schema에 unit과 origin·range를 명시하고 integer overflow와 precision을 검증한다.

Anti-pattern·edge case·engine 차이

  • 샘플 100행=전체 schema: Rare pattern과 late drift를 놓친다.
  • Leading zero 제거: 우편번호·계정·전화번호·코드는 숫자 모양의 identifier일 수 있다.
  • 여러 date pattern fallback: 03/04처럼 둘 다 성공하면 deterministic해 보여도 의미가 틀린다.
  • Host locale/timezone 사용: Machine·container 설정에 따라 재실행 결과가 달라진다.
  • UTC로 바꾸면 끝: Recurring civil schedule과 원 zone intent를 잃을 수 있다.
  • Offset=zone: +09:00은 time zone rules ID가 아니다.
  • Epoch magnitude 추측: Seconds/millis/micros는 schema unit으로 정한다.
  • Engine 동일성 가정: Inference sample size, null tokens, overflow, decimal promotion, date patterns, DST normalization은 engine/version별로 다를 수 있다.

7. 35분 실습: 정보 손실과 DST 경계 재현

목표: 자동 숫자·날짜 추론이 raw 의미를 잃는 과정을 보고, explicit Decimal/date format/timezone 정책과 DST fold/gap 검증을 구현한다.

사전 조건: Python 3.9+와 system IANA timezone data가 필요하다. 정확한 임시 경로 /tmp/file-format-day12만 사용한다.

실행 전 예측: 00123, 1,234, 03/04/2026의 가능한 의미를 각각 적고, 뉴욕의 2026-03-08 02:30과 2026-11-01 01:30이 몇 instants에 대응할지 예측한다.

7.1 Naive inference의 정보 손실

mkdir -p /tmp/file-format-day12 cd /tmp/file-format-day12 python3 - <<'PY' from datetime import datetime raw = {"postal_code": "00123", "amount": "1,234", "date": "03/04/2026"} naive = { "postal_code": int(raw["postal_code"]), "amount_en": int(raw["amount"].replace(",", "")), "amount_decimal_comma": raw["amount"].replace(",", "."), "date_mdy": datetime.strptime(raw["date"], "%m/%d/%Y").date(), "date_dmy": datetime.strptime(raw["date"], "%d/%m/%Y").date(), } print("raw=", raw) print("naive=", naive) PY

예상 관찰: Postal code는 123이 되어 원형을 잃는다. Amount는 1234 또는 1.234가 모두 가능하고, date는 2026-03-04와 2026-04-03 모두 parse에 성공한다. Parser 성공 여부만으로 의미를 선택할 수 없다.

7.2 명시적 parsing contract

python3 - <<'PY' import re from datetime import datetime, timezone from decimal import Decimal contract = { "postal_code": {"type": "string", "pattern": r"\d{5}"}, "amount": {"type": "decimal", "decimal": ",", "grouping": False, "scale": 3}, "date": {"type": "date", "format": "%d/%m/%Y"}, "epoch": {"type": "instant", "unit": "milliseconds"}, } raw = {"postal_code": "00123", "amount": "1,234", "date": "03/04/2026", "epoch": "1700000000000"} assert re.fullmatch(contract["postal_code"]["pattern"], raw["postal_code"]) postal_code = raw["postal_code"] amount = Decimal(raw["amount"].replace(",", ".")) assert -1000000 < amount < 1000000 date = datetime.strptime(raw["date"], contract["date"]["format"]).date() epoch_ms = int(raw["epoch"]) instant = datetime.fromtimestamp(epoch_ms / 1000, tz=timezone.utc) print(postal_code, amount, date, instant.isoformat()) PY

예상 관찰: 00123은 string으로 보존되고 amount는 exact Decimal 1.234, date는 2026-04-03, epoch는 명시적 milliseconds로 UTC instant가 된다. 실제 contract에서는 precision/scale과 rounding도 검사한다.

7.3 실패 주입: DST gap과 fold

python3 - <<'PY' from datetime import datetime, timezone from zoneinfo import ZoneInfo, ZoneInfoNotFoundError try: zone = ZoneInfo("America/New_York") except ZoneInfoNotFoundError: raise SystemExit("IANA tzdata가 필요합니다") def candidates(local_text): naive = datetime.strptime(local_text, "%Y-%m-%d %H:%M:%S") valid = [] for fold in (0, 1): aware = naive.replace(tzinfo=zone, fold=fold) utc = aware.astimezone(timezone.utc) back = utc.astimezone(zone).replace(tzinfo=None) if back == naive and all(utc != old for _, old in valid): valid.append((fold, utc)) return valid for text in ("2026-03-08 02:30:00", "2026-11-01 01:30:00"): result = candidates(text) state = "GAP" if len(result) == 0 else "UNIQUE" if len(result) == 1 else "FOLD" print(text, state, [(fold, utc.isoformat()) for fold, utc in result]) PY

예상 관찰: 3월 시각은 유효한 candidate가 없는 GAP, 11월 시각은 서로 다른 두 UTC candidates가 있는 FOLD다. Contract가 reject/shift와 earlier/later 중 무엇을 택할지 정하지 않으면 typed instant를 만들지 않는다.

7.4 실패 주입: sample schema drift

python3 - <<'PY' tokens = ["10", "20", "30", "12.50", "N/A"] sample = tokens[:3] inferred = "integer" if all(t.isdigit() for t in sample) else "string" print("sample=", sample, "inferred=", inferred) for index, token in enumerate(tokens): try: print(index, int(token)) except ValueError as e: print(index, "QUARANTINE", repr(token), type(e).__name__) PY

예상 관찰: Sample은 integer를 제안하지만 late values가 실패한다. Production에서는 auto-null/auto-widen 대신 raw token과 reason을 quarantine하고 contract review 후 새 schema version으로 replay한다.

7.5 자주 나는 오류와 해결·cleanup

  • ZoneInfoNotFoundError: System tzdata가 없을 수 있다. 승인된 IANA tzdata package/image를 version-pin한다.
  • Decimal을 float로 변환: 다시 binary rounding이 생긴다. DB/file까지 decimal precision/scale을 유지한다.
  • replace(tzinfo=zone)만 사용: Gap/fold validation이 아니다. UTC round-trip candidates를 검사한다.
  • Epoch OverflowError: Unit·range·runtime 지원 범위를 먼저 검증하고 reject한다.

8. 놓치기 쉬운 함정

  1. Empty, null sentinel, malformed token을 모두 null로 합치면 producer quality와 business absence를 구분할 수 없다.
  2. Naive datetime에 UTC label만 붙이는 것은 timezone conversion이 아니라 잘못된 재해석이다.
  3. RFC 3339 offset timestamp는 instant에는 충분하지만 future civil schedule의 zone rules는 보존하지 않는다.
  4. Fractional seconds 자릿수가 다르면 string sort와 precision 비교가 예상과 다를 수 있다.
  5. Timezone abbreviation CST는 여러 지역을 뜻할 수 있어 zone ID로 쓰기 부적합하다.
  6. Tzdb update 후 future schedule 결과가 달라질 수 있다. 재계산 정책과 영향 audit가 필요하다.
  7. Schema inference 결과를 file metadata에 쓰고 raw를 지우면 잘못된 추론을 되돌릴 수 없다.

9. 대기업 기술 면접 질문

Q1. 20개 국가에서 오는 schema 없는 CSV의 numeric/date inference를 설계하세요.

좋은 답변 구조: Source별 locale·domain·SLO와 error budget을 묻는다 → raw immutable layer와 profiler proposal을 분리한다 → candidate/type lattice·sample bias를 설명한다 → explicit per-source contract·quarantine·reconciliation을 둔다 → schema evolution, parser version, rollback/replay까지 방어한다.

Q2. 글로벌 예약 시스템의 timestamp data contract를 설계하세요.

좋은 답변 구조: Event instant와 future civil schedule을 분리한다 → instant는 RFC 3339/UTC와 precision, schedule은 local datetime+IANA zone+fold/gap policy로 모델링한다 → tzdb version·offset provenance를 저장한다 → DST candidates와 변경된 법규 처리, audit·recompute trade-off를 설명한다.

Q3. Parser upgrade 뒤 매출이 1,000배 증가했다면 어떻게 대응합니까?

좋은 답변 구조: Publish/checkpoint를 멈춘다 → raw amount tokens, locale/decimal/grouping, old/new parser/config, version별 aggregates를 수집한다 → 1,234 해석 drift 가설을 검증한다 → last-known-good rollback과 새 output version replay를 한다 → typed overwrite/임의 보정 금지와 예방 metrics를 제시한다.

10. 복습 문제와 정답

어제 내용 회상 3문제

  1. NDJSON의 raw LF가 안전한 record boundary가 되는 문법적 이유는?
  2. Sink commit과 checkpoint 중 무엇이 먼저이며, 반대 순서의 결과는?
  3. NDJSON byte-range worker가 split 시작과 끝에서 record ownership을 정하는 방법은?

오늘 내용 확인 3문제

  1. Full scan inference도 00123을 우편번호인지 수량인지 확정할 수 없는 이유는?
  2. UTC offset과 IANA time zone ID는 어떤 정보를 각각 소유하는가?
  3. DST gap/fold를 library의 단순 tzinfo 부착보다 안전하게 판별하는 방법은?

짧은 정답·채점 기준

어제 1JSON string의 newline은 escaped돼야 하므로 unescaped 0x0A를 delimiter로 scan할 수 있다.
어제 2Sink/reject commit이 먼저다. Checkpoint 선행 뒤 crash하면 해당 record가 영구 유실된다.
어제 3시작이 0이 아니면 다음 LF 뒤부터, 종료 offset을 지난 첫 LF까지 한 worker가 담당하는 규칙을 둔다.
오늘 1Lexical pattern은 같아도 domain semantics가 다르다. Producer/field contract 없이는 leading zero 보존 여부를 결정할 수 없다.
오늘 2Offset은 특정 instant의 UTC 차이, zone ID는 지역의 시간 변화 rules 집합을 가리킨다.
오늘 3Fold 0/1 candidates를 UTC로 변환 후 zone으로 round-trip한다. 0개면 gap, 서로 다른 2개면 fold다.

채점: 각 2점, 총 12점. 10점 이상 통과. 오늘 1번에서 information loss/raw retention, 오늘 2번에서 future rules/tzdb version, 오늘 3번에서 business resolution policy까지 말하면 면접형 답변이다.
