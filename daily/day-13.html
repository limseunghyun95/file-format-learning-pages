랩: malformed record quarantine parser

Bytes에서 accepted·reject·checkpoint까지 · 예상 학습 45분 + 실습 40분
한 줄 요약
좋은 ingestion parser는 bad row를 “건너뛰는” 코드가 아니라, 완전한 record마다 accepted 또는 reasoned reject를 durable하게 만들고 그 뒤에만 checkpoint를 전진시키는 상태 머신이다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의
Malformed recordEncoding·framing·문법·schema·domain 계약 중 하나를 만족하지 못한 record다. “파싱 예외”보다 범위가 넓다.
Quarantine실패 record의 raw bytes 또는 digest, 위치, reason, parser/schema version을 정상 data와 분리해 보존하는 reject sink다.
Failure taxonomyUTF8_INVALID, RECORD_TOO_LARGE, JSON_SYNTAX, DUPLICATE_KEY, SCHEMA_FIELD, DOMAIN_RANGE처럼 실패를 안정된 code로 분류한 체계다.
Reconciliation입력·accepted·rejected·pending 수가 불변식을 만족하는지 맞춰 보는 검산이다.
Dead-letter queue주 처리 경로가 다룰 수 없는 message를 보내는 별도 queue다. 파일 기반 quarantine와 목적은 비슷하지만 보존·재처리 계약은 별도다.

2. 왜 중요한가

skip_bad_rows=true는 job을 초록색으로 만들 수 있지만 매출 record 2%를 조용히 버릴 수 있다. 반대로 bad row 하나에서 전체 1TB file을 실패시키면 가용성과 재처리 비용이 커진다. 실무의 답은 “무조건 fail/skip”이 아니라 error budget, field 중요도와 source contract에 맞춘 record 격리·batch gate다.

Quarantine는 쓰레기통이 아니다. 원인 분석, producer 책임 추적, parser fix 검증과 idempotent replay를 위한 evidence store다. Accepted와 reject를 각각 썼는데 checkpoint가 앞서거나 두 sink 중 하나만 commit되면 결과가 수렴하지 않는다.

오늘의 합격 불변식: 모든 complete framed record는 정확히 하나의 terminal state—ACCEPTED 또는 REJECTED—를 갖고, complete = accepted + rejected이며, checkpoint는 그 결과가 durable해진 뒤에만 전진한다.

3. 아키텍처 그림과 요청 흐름

↓ terminal result durable first
⑤ Reconcile + checkpoint
complete = accepted + rejected → next offset
Data path: bytes → frame → decoded value → accepted/reject.
Control path: dialect, max bytes/depth, duplicate policy, schema version, reason taxonomy, reject threshold, PII retention, checkpoint/rollback version을 배포한다.
  1. Frame: NDJSON은 LF, CSV는 quote-aware state machine으로 logical record를 찾는다. Buffer/read chunk 경계는 record 경계가 아니다.
  2. Decode: Raw bytes를 strict UTF-8로 decode한다. Replacement character로 조용히 고치지 않는다.
  3. Parse: Syntax와 duplicate key를 검사한다. JSON dict가 된 뒤에는 duplicate 증거가 사라질 수 있다.
  4. Validate: Required/unknown fields, exact type, precision/range, timestamp offset 같은 domain 규칙을 적용한다.
  5. Commit terminal result: Accepted upsert 또는 reject insert 중 정확히 하나를 idempotency key와 함께 확정한다.
  6. Checkpoint: Terminal commit 뒤 next offset을 기록한다. Batch 종료 때 reconciliation과 reject-rate gate를 확인한다.

상태 소유자와 전이

FramerFile identity, start/end offset, buffered partial bytes와 complete count를 소유한다.
ValidatorParser/schema/config version과 deterministic terminal reason을 소유한다.
SinksACCEPTED 또는 REJECTED terminal state와 idempotency key uniqueness를 소유한다.
허용 전이RECEIVED → FRAMED → VALIDATED → ACCEPTED/REJECTED → CHECKPOINTED. ACCEPTED와 REJECTED는 상호 배타적이다.
성공 시점Accepted/reject reconciliation, threshold와 sink durability 검증 후 checkpoint와 publish pointer가 확정된 때다.

4. CS 내부 동작

4.1 오류 계층을 순서대로 검사한다

Byte/size → framing → encoding → syntax → structural schema → semantic domain 순으로 검사하면 reason이 안정된다. Invalid UTF-8 bytes를 먼저 lossy decode하면 뒤에서 JSON_SYNTAX로 잘못 분류돼 원인을 잃는다. Oversize record도 전체를 memory에 올린 뒤 검사하면 resource protection에 실패한다.

4.2 Error code는 API다

Exception message는 library/version에 따라 바뀐다. 외부 reason_code는 소수의 안정된 enum으로 유지하고 내부 exception class/message는 diagnostic detail로 별도 보존한다. Retryable한 IO_TIMEOUT과 deterministic한 DUPLICATE_KEY를 같은 재시도 정책에 넣지 않는다.

4.3 Raw evidence와 보안

Raw bytes는 재현에 가장 강하지만 PII·secret을 담을 수 있다. Encryption, least privilege, retention, audit log를 적용하고 UI에는 masked preview만 노출한다. 규제로 raw 보존이 불가능하면 keyed digest, byte length, safe field hashes와 source replay pointer를 남긴다.

4.4 Atomicity와 crash windows

Accepted/reject sink와 checkpoint가 서로 다른 system이면 완전한 distributed transaction이 어려울 수 있다. Sink upsert를 idempotent하게 만들고 checkpoint를 뒤에 두면 sink 성공 후 crash는 duplicate attempt로 복구된다. 반대 순서는 영구 유실이다. Outbox/transactional table 또는 commit manifest로 상태 전환을 원자화할 수도 있다.

4.5 Reject threshold와 blast radius

Record-level 격리가 batch 성공을 자동 의미하지 않는다. Reject 0.01%는 허용해도 30%면 producer contract 장애일 수 있다. 전체·field·reason·producer version별 absolute count와 ratio, 연속 reject burst를 gate로 둔다. 중요한 결제 field 오류는 한 건이어도 batch stop 정책이 가능하다.

4.6 CSV resynchronization은 어렵다

NDJSON은 raw LF가 record delimiter지만 CSV quoted field 안에는 newline이 있을 수 있다. 깨진 quote 뒤 다음 newline을 record 시작으로 단정하면 이후 정상 rows까지 잘못 자른다. Max record bytes, quote-aware state, known column count와 safe resync policy가 필요하고, 확신할 수 없으면 file/split 격리가 더 안전하다.

4.7 Replay는 새 output version으로

Parser fix 뒤 quarantine를 원래 table에 in-place patch하면 과거 snapshot과 audit가 흐려진다. Raw + old reason을 input으로 새 parser/schema version에서 replay하고 새 run_id/output version을 만든 뒤 counts와 business aggregates를 비교해 atomic pointer를 전환한다.

5. 실무 설계 판단

판단Best practice와 이유
Reason taxonomy계층별 안정된 code와 retryable flag를 정의하고 raw exception은 detail로 둔다.
EvidenceFile generation, byte range, raw/digest, parser/schema version, ingestion run_id를 reject에 넣는다.
Resource limitsRecord bytes, nesting, fields, string/number length, reject payload 크기까지 ingress 전에 제한한다.
Commit orderAccepted/reject terminal result → reconciliation → checkpoint 순서를 지키고 sink를 idempotent하게 한다.
Quality gateReason·producer·schema별 count/ratio와 critical-field zero tolerance를 배포 계약에 둔다.
Replay새 parser/config version과 run_id로 재처리해 before/after reconciliation 후 pointer를 전환한다.
RetentionPII classification, encryption, access audit, TTL과 legal hold를 정상 raw와 동일 수준으로 적용한다.

Anti-pattern·edge case·engine 차이

  • 모든 오류를 BAD_ROW: 원인·owner·retry 정책을 잃는다.
  • Unicode replacement: Invalid bytes를 정상 string처럼 만들어 silent corruption을 낳는다.
  • Exception text를 reason code로 사용: Upgrade 뒤 dashboard와 replay selection이 깨진다.
  • Reject sink best-effort: 실패 record 자체가 사라져 reconciliation이 틀어진다.
  • 무제한 raw preview: Quarantine가 PII 유출 경로가 된다.
  • Checkpoint first: Sink failure 시 data loss가 확정된다.
  • Engine 동일성 가정: CSV strictness, duplicate handling, NaN, max field size와 line recovery는 library/version별로 다르다.

7. 40분 통합 실습: deterministic quarantine pipeline

목표: 정상 2건과 invalid UTF-8, duplicate key, unknown field, bad timestamp, oversize record를 섞은 NDJSON bytes를 만들어 terminal reason·offset·checkpoint와 reconciliation을 검증한다.

사전 조건: Python 3 표준 library만 필요하다. 정확한 임시 경로 /tmp/file-format-day13만 사용한다.

실행 전 예측: 아래 7개 complete lines 중 accepted/rejected 수와 각 reason을 먼저 적는다. 마지막 LF가 없는 tail을 추가하면 complete count와 checkpoint가 어떻게 변할지도 예측한다.

7.3 자주 나는 오류와 해결·cleanup

  • Oversize line에서 memory 증가: 전체 raw를 buffer하지 말고 cap 이후에는 digest/byte count만 갱신하며 LF까지 bounded discard한다. 실습의 read_frame이 이 방식이다.
  • UTF8_INVALID 대신 RECORD_TOO_LARGE: Validation ordering상 size가 먼저다. Test fixture 길이를 limit 아래로 유지한다.
  • Duplicate가 안 잡힘: 일반 dict 생성 후 검사했다. object_pairs_hook 단계에서 검사한다.
  • Raw PII 노출: 예시는 digest만 저장한다. Production preview는 mask·encrypt·TTL을 적용한다.

8. 놓치기 쉬운 함정

  1. Reject도 terminal output이므로 reject sink 장애를 무시하면 안 된다.
  2. Incomplete tail은 malformed complete record와 다르다. Writer 완료 상태를 확인한다.
  3. One record가 여러 reasons를 가질 때 primary reason ordering과 secondary diagnostics를 구분한다.
  4. Raw digest만으로 replay할 수 없다. Source generation과 retention/replay pointer가 필요하다.
  5. Reject rate가 낮아도 중요한 특정 producer/field에 집중될 수 있다.
  6. Parser fix가 과거 reject 모두를 accepted로 만들지는 않는다. Domain contract 위반은 계속 reject다.
  7. Quarantine replay 자체에도 idempotency, authorization, audit와 rate limit이 필요하다.

9. 대기업 기술 면접 질문

Q1. 하루 10억 records ingestion에서 malformed 0.1%를 처리하는 플랫폼을 설계하세요.

좋은 답변 구조: SLO·critical fields·허용 손실을 수치화한다 → bounded framer와 validation 계층을 그린다 → accepted/reject terminal state와 reconciliation을 둔다 → idempotent sinks·checkpoint crash windows를 방어한다 → PII retention, reason dashboard, threshold·rollback·replay 비용까지 설명한다.

Q2. Skip bad rows와 fail-fast 중 무엇을 선택합니까?

좋은 답변 구조: 이분법을 거부하고 error class·business impact·batch ratio를 묻는다 → framing/encoding 불확실은 split/file stop, 독립 domain error는 quarantine 가능처럼 blast radius를 구분한다 → critical zero-tolerance와 rate gate를 둔다 → evidence·replay 가능성을 조건으로 결정한다.

Q3. Sink commit 뒤 checkpoint 전 crash에서 exactly-once를 어떻게 근사합니까?

좋은 답변 구조: 상태 전이를 그린다 → checkpoint-first의 data loss를 배제한다 → record_id 또는 generation+offset unique key로 sink upsert한다 → replay가 같은 terminal result로 수렴함을 설명한다 → outbox/transactional metadata 대안과 비용을 비교한다.
