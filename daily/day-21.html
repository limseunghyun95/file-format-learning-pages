FILE FORMAT · WEEK 3 / DAY 21 · REVIEW

회상: rename·reuse가 위험한 이유

Field identity·schema resolution·rollback을 한 장으로 연결 · 예상 학습 55분 + 실습 35분
한 줄 요약
이름은 사람이 보는 label이고, serialization이 field를 식별하는 규칙은 format마다 다르다. Protobuf는 field number, Avro record resolution은 name·reader alias가 핵심이다. Rename·reuse를 UI refactor처럼 다루면 old bytes가 새 의미로 조용히 오염되므로 identity를 영구 계약으로 관리해야 한다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의
Field identitySchema version이 달라도 “같은 논리 field”임을 연결하는 식별 계약이다. Format마다 number, name, ID, alias 등 기준이 다르다.
Rename같은 의미를 유지하며 사람이 보는 이름을 바꾸는 변경이다. Wire·JSON·generated API·query name에서 효과가 서로 다르다.
Reuse과거 field가 쓰던 number/name/enum value를 다른 의미에 다시 배정하는 것이다. Historical bytes가 남아 있으면 identity 충돌이다.
Reserved삭제한 Protobuf field number/name을 미래 schema에서 다시 쓰지 못하게 막는 compile-time tombstone이다.
AliasAvro reader가 새 name을 old writer name과 연결하도록 선언한 대체 이름이다. 임의 rename을 자동 추론하는 기능은 아니다.
Tombstone삭제 사실과 재사용 금지를 영구 기록한 표식이다. Data가 사라진 뒤에도 offline client·backup 때문에 유지할 수 있다.
Expand-contract새 field를 추가하고 dual read/write·backfill한 뒤 old field를 단계적으로 제거하는 가역 migration 방식이다.
Semantic migration이름만 바꾸는 것이 아니라 unit·range·meaning까지 바뀔 때 변환 규칙과 provenance를 적용하는 data migration이다.
Replay horizonHistorical bytes가 다시 읽힐 수 있는 최장 기간이다. Queue TTL, object retention, backup, offline client를 포함한다.
Shadow readOld/new reader를 같은 bytes에 실행해 결과를 비교하되 새 결과는 production state에 적용하지 않는 검증이다.
Schema fingerprint정규화된 schema를 식별하는 hash/ID다. Payload를 어떤 writer schema로 해석했는지 추적한다.
Silent corruptionParser는 성공했지만 잘못된 logical value가 sink에 commit되어 오류가 늦게 발견되는 장애다.

2. 왜 중요한가

Protobuf binary에는 field name이 없다. int32 age = 1의 bytes 08 01은 V2가 bool is_admin = 1로 number를 재사용해도 잘 형성된 VARINT다. Old age=1이 new is_admin=true로 읽히면 parser error·registry error가 모두 0인 채 권한이 상승한다.

반대로 Protobuf에서 name만 바꾸고 number·type을 유지하면 binary는 읽힐 수 있지만 ProtoJSON, TextFormat, generated API, log/query field name은 깨질 수 있다. Avro에서는 binary에 field name이 없더라도 reader resolution이 schema name으로 field를 맞추므로 alias 없는 rename은 old writer field와 연결되지 않는다. “Rename은 안전/위험”이 아니라 어떤 representation과 identity rule인가를 먼저 답해야 한다.

Week 3 최종 불변식: Field의 number/name/type/presence/default/semantic unit과 lifecycle 상태(active→deprecated→reserved)를 한 ledger에서 관리한다. Registry pass가 아니라 supported bytes의 reader×writer×runtime×business matrix가 배포 증거다.

4. CS 내부 동작과 Week 3 연결

4.1 Logical value에서 bytes까지

Schema는 logical field를 physical encoding으로 매핑한다. Protobuf field number와 wire type은 tag를 만들고, integer는 varint/zig-zag 규칙으로 payload가 된다. Avro는 writer schema의 depth-first 순서로 field name 없이 payload를 기록한다. Decode 시 필요한 identity metadata가 없거나 잘못되면 같은 bytes가 다른 object가 된다.

4.2 Compatibility 방향

Backward는 R_new(W_old), forward는 R_old(W_new)다. Rename/reuse review는 baseline·target과 두 cross edge를 모두 실행해야 한다. Rollback은 code를 되돌리는 행동이 아니라 이미 생성된 W_new bytes를 R_old가 안전하게 읽는다는 forward 증명이 포함된 상태 전이다.

4.3 Presence·default·unknown

Identity가 맞아도 absent와 explicit default를 접으면 PATCH 의미가 사라진다. Protobuf old reader가 new number를 unknown으로 보존할 수 있지만 JSON/manual copy에서 유실될 수 있다. Avro alias가 연결돼도 reader default 변화가 old bytes의 결과를 바꿀 수 있다. 그러므로 field ledger는 identity뿐 아니라 presence discipline과 default version까지 포함한다.

4.4 Failure window와 비용

Reuse failure window는 producer 배포 순간부터가 아니라 과거 bytes가 생성된 최초 시점까지 거슬러 올라간다. 모든 historical generation을 영구 matrix에 넣으면 비용이 커지므로 retention class, traffic percentile, risk tier로 fixture를 계층화하되 PII·권한·금액 field는 full transitive evidence를 유지하는 편이 안전하다.

5. 실무 schema review checklist

단계필수 질문과 승인 증거
IdentityFormat별 identity는 무엇인가? Number/name/alias/type/unit가 기존 ledger와 충돌하지 않는가?
HistoryQueue·object·backup·offline client·rollback의 최장 horizon과 실제 writer fingerprints는?
RepresentationBinary 외에 JSON/Text/log/query/cache key에서 이름을 사용하는가?
SemanticsUnit, range, enum, presence, default, PII, authorization invariant가 유지되는가?
MigrationAdd/dual read-write/backfill/old-write stop/reserve·alias 순서와 각 성공 조건은?
MatrixR1(W1), R2(W1), R1(W2), R2(W2) × boundary × runtime의 golden 결과 SHA는?
OperationsPair별 metric, quarantine capacity, checkpoint, idempotency key, rollback pointer와 reconciliation은?
Retirement삭제 number/name/enum value를 tombstone하고 ledger·compiler·lint가 재사용을 막는가?

Best practice·anti-pattern·edge case

  • Best: Protobuf number는 한 번 할당하면 영구 identity로 보고 삭제 뒤 number/name을 reserve한다.
  • Best: Avro rename은 reader alias, old/new fixture와 exact writer schema로 검증한다.
  • Best: 의미 변경은 rename이 아니라 새 field+명시적 transform+provenance로 migration한다.
  • Anti-pattern: 번호를 보기 좋게 재정렬한다. 이는 field 전체를 삭제·추가하는 것과 같다.
  • Anti-pattern: Binary matrix만 통과하고 ProtoJSON·Text·REST client를 무시한다.
  • Anti-pattern: Retention이 끝났다는 추측으로 reserved를 해제한다. Backup·DLQ·offline client가 남을 수 있다.
  • Edge: 같은 number와 같은 wire type의 reuse는 parser가 성공해 더 위험하다.
  • Edge: Avro alias가 wire resolution을 살려도 generated API·SQL column name·downstream catalog는 별도 migration이 필요하다.
  • Runtime: Unknown enum, TextFormat reserved name, generated has/clear API는 언어·runtime 차이를 matrix에 넣는다.
  • 완료: Tombstone commit, canary/replay 대사와 rollback reader 검증 뒤에만 old field를 retire한다.

6. 장애 대응

증상Parse error 없이 권한·PII·금액 값 오염, 특정 historical generation에서만 rename field missing, JSON client 4xx, unknown/default 급증, rollback 뒤 crash, replay aggregate 불일치.
먼저 수집할 증거/지표Immutable bytes/checksum, writer/reader schema fingerprint, field ledger와 reserved history, runtime build, binary/JSON path, field number·wire type·name·alias, presence/unknown/default, first/last affected offset, checkpoint·sink commit, domain audit.
가능한 가설Number/enum value reuse, alias 누락/방향 오류, JSON name rename, wrong writer schema, stale generated code, implicit presence loss, reader default 변화, unknown bridge loss, adjacent-only gap, semantic unit reuse.
안전한 첫 조치Affected writer 확대와 checkpoint를 멈추고 version pair·generation을 격리한다. Bytes·schema·runtime·domain audit를 보존하고 old/new identity map으로 4칸 matrix와 shadow read를 재현한다.
Rollback / 복구Last-known-good W/R routing과 tolerant reader를 먼저 복구한다. Corrupt semantic generation은 quarantine하고 ledger/tombstone을 수정한다. Safe checkpoint에서 idempotent replay하고 identity별 count·domain aggregate·audit를 reconcile한다.
하지 말아야 할 조치Raw bytes의 tag/name을 일괄 치환, latest schema fallback, reserved 해제, unknown/default 임의 보정, failed row skip 후 checkpoint, evidence 없는 cache clear, old/new 값을 같은 column에 무표식 혼합, idempotency 없는 replay를 하지 않는다.

7. 35분 실습: history auditor와 사고 재현

목표: Python 표준 라이브러리로 Protobuf field ledger 충돌과 Avro alias rename을 감사하고, 같은 bytes가 다른 meaning으로 parse되는 silent incident를 재현한다.

사전 조건: Python 3.9 이상. 외부 package·protoc는 필요 없다. 교육용 model이며 실제 runtime matrix를 대체하지 않는다.

실행 전 예측: V1 age=1 삭제 후 V3 is_admin=1, Protobuf name-only rename, Avro alias 유/무의 결과를 적고 어느 검사가 parser error 없이 사고를 잡는지 예상한다.

python3 - <<'PY' def audit_proto(history): seen, retired = {}, set() issues = [] for version in history: retired |= set(version.get("reserved", [])) for no, spec in version["fields"].items(): name, wire, meaning = spec if no in retired: issues.append((version["v"], no, "USES_RESERVED", name)) if no in seen and seen[no][2] != meaning: issues.append((version["v"], no, "SEMANTIC_REUSE", seen[no][2]+"->"+meaning)) seen.setdefault(no, spec) return issues bad = [ {"v":"V1", "fields":{1:("age",0,"person_age"),2:("name",2,"display_name")}}, {"v":"V2", "fields":{2:("name",2,"display_name")}, "reserved":[]}, {"v":"V3", "fields":{1:("is_admin",0,"authorization"),2:("full_name",2,"display_name")}}, ] good = [ {"v":"V1", "fields":{1:("age",0,"person_age"),2:("name",2,"display_name")}}, {"v":"V2", "fields":{2:("name",2,"display_name")}, "reserved":[1]}, {"v":"V3", "fields":{2:("full_name",2,"display_name"),3:("is_admin",0,"authorization")}, "reserved":[1]}, ] print("bad_history=", audit_proto(bad)) print("good_history=", audit_proto(good)) # bytes 08 01: field 1, VARINT, value 1 raw = bytes.fromhex("08 01") tag, value = raw no, wire = tag >> 3, tag & 7 for schema in ({1:"age"},{1:"is_admin"}): print("same_bytes", raw.hex(" "), "schema=", schema, "decoded=", {schema[no]:value}, "wire=", wire) print("parser_success_but_meaning_changed=", True) PY

예상 관찰: Bad history는 field 1의 semantic reuse를 찾는다. Good history는 number 1을 reserve하고 권한 field에 새 number 3을 써 통과한다. 08 01은 age와 is_admin 두 schema에서 모두 parse되므로 semantic ledger·golden assertion이 없으면 사고를 못 잡는다.

7.2 Avro rename과 representation matrix

python3 - <<'PY' def resolve(writer_record, reader): out={} for new_name,spec in reader.items(): names=[new_name]+spec.get("aliases",[]) old=next((n for n in names if n in writer_record),None) if old is not None: out[new_name]=writer_record[old] elif "default" in spec: out[new_name]=spec["default"] else: raise ValueError("MISSING:"+new_name) return out old={"amount":1000,"currency":"KRW"} for label,reader in [ ("alias",{"total":{"aliases":["amount"]},"currency":{}}), ("no_alias",{"total":{},"currency":{}}), ("bad_default",{"total":{"default":0},"currency":{}}), ]: try: result=resolve(old,reader) semantic_ok=result.get("total")==old["amount"] print(label,result,"semantic_ok=",semantic_ok) except Exception as e: print(label,"RESOLUTION_FAIL",e) paths={"protobuf_binary":"number", "proto_json":"name", "avro_resolution":"reader_name_or_alias", "domain":"meaning_and_unit"} for path,identity in paths.items(): print(path,"identity=",identity) PY

예상 관찰: Alias rename은 old amount를 new total로 연결한다. Alias가 없으면 error, default 0을 넣으면 parse/resolution은 성공하지만 1000이 0으로 바뀌어 semantic failure다. 같은 rename도 binary·JSON·Avro·domain 경로별 identity가 다르다.

7.3 실패 주입·오류·cleanup

  • 실패 주입: 첫 코드의 old age를 21 대신 1로 유지하면 bool range 검사까지 통과한다. 의미 ledger만 사고를 잡는다.
  • Reserved만 검사: 과거 meaning ledger도 비교해야 삭제 전에 이미 재사용된 충돌을 잡는다.
  • Name-only audit: Protobuf number와 JSON name을 별도 identity 축으로 검사한다.
  • Alias+default 동시 사용: Alias 누락이 default로 가려지지 않게 “default materialized count”를 metric으로 둔다.
  • Raw payload logging: PII 대신 checksum, field number/wire type/size와 보호 저장소 pointer를 기록한다.

Cleanup: 두 명령은 파일·package·container를 만들지 않는다. Production schema ledger를 실습에 복사할 때 내부 이름·PII classification을 제거하고 결과만 review artifact로 보존한다.

8. 놓치기 쉬운 함정

  1. 사람이 보는 name과 wire identity를 분리한다.
  2. Protobuf number 재정렬도 reuse와 같은 incompatible change다.
  3. 같은 wire type reuse는 parse 성공 때문에 더 위험하다.
  4. Protobuf binary rename과 JSON/API rename을 별도 검증한다.
  5. Avro alias는 reader 쪽에서 old writer name을 연결한다.
  6. Default로 rename failure를 숨기지 않는다.
  7. Meaning·unit 변경은 새 field와 migration으로 처리한다.
  8. Reserved/tombstone은 retention 종료 추정만으로 제거하지 않는다.
  9. Registry pass와 semantic matrix를 혼동하지 않는다.
  10. Rollback 전에 old reader가 이미 생성된 new bytes를 읽는지 확인한다.

9. 대기업 기술 면접 질문

Q1. Protobuf field rename과 number reuse를 구분해 설명하세요.

좋은 답변 구조: Binary tag가 number+wire type임을 말한다 → name-only rename은 binary 가능하지만 JSON/generated API 영향이 있음을 분리한다 → number reuse의 same-wire silent corruption 예를 든다 → reserve/tombstone, expand-contract와 cross matrix를 제안한다 → PII·권한 사고 복구까지 방어한다.

Q2. Avro field를 amount에서 total로 바꾸는 무중단 절차는?

좋은 답변 구조: Writer schema와 reader name/alias resolution을 정의한다 → retention writer generations를 inventory한다 → reader alias와 dual read/write, shadow replay, backfill을 설계한다 → default로 누락을 숨기지 않고 materialization metric을 둔다 → old writer 중단·reconcile·rollback 뒤 retire한다.

Q3. Schema registry가 허용한 변경으로 권한 사고가 났습니다. 대응과 재발 방지를 말하세요.

좋은 답변 구조: 새 writer/consumer checkpoint를 정지한다 → immutable bytes·fingerprint·identity ledger·audit를 수집한다 → version pair별 재현과 affected generation을 계산한다 → tolerant reader·quarantine·idempotent replay로 복구한다 → semantic ledger lint, golden matrix, canary domain alert와 tombstone policy를 추가한다.
