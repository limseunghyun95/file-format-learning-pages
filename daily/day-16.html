FILE FORMAT · WEEK 3 / DAY 16

Avro writer/reader schema resolution

Writer bytes에서 reader object까지 · 예상 학습 55분 + 실습 35분
한 줄 요약
Avro binary datum은 field name이나 tag를 매 record에 반복하지 않으므로, 정확한 writer schema로 bytes를 걷고 reader schema와 이름·alias·type 규칙을 대조해 field를 읽거나 건너뛰고 default를 채워야 한다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의
DatumAvro schema에 따라 직렬화되는 하나의 논리적 값 또는 record다. File container와 datum 자체를 구분한다.
Writer schemaProducer가 bytes를 만들 때 실제로 사용한 schema다. Decoder가 field 순서·type·경계를 따라 bytes를 소비하는 지도다.
Reader schemaConsumer가 결과 object에서 원하는 field·type·default를 표현하는 schema다. Writer schema를 대체하지 않고 함께 사용된다.

Promotion값을 잃지 않는다고 규격이 허용한 방향으로 writer primitive를 reader primitive에 올려 읽는 규칙이다. 임의 cast가 아니다.

2. 왜 중요한가

Protobuf는 각 field에 number와 wire type key를 붙인다. Avro binary record는 writer schema가 정한 field 순서대로 값을 이어 쓰며 field name을 반복하지 않는다. 그래서 작고 빠를 수 있지만, bytes와 writer schema가 분리되면 reader는 첫 varint가 id인지 amount인지 알 수 없다.

Schema registry에 “현재 최신 schema”가 있다고 충분하지 않다. 반드시 해당 bytes를 쓴 정확한 writer schema identity가 필요하다. 잘못된 schema를 주면 즉시 오류가 나기도 하지만 더 위험하게는 일부 bytes가 다른 type으로 조용히 해석될 수 있다. Schema ID, object generation, payload checksum과 writer build를 하나의 provenance로 묶어야 한다.

오늘의 핵심 불변식: payload bytes + exact writer schema identity는 분리되지 않으며, resolution 성공은 writer bytes를 정확히 끝까지 소비하고 reader object의 required/default/domain 규칙을 만족한 뒤에만 확정한다.

3. 아키텍처 그림과 요청 흐름

① Producer
logical datum + writer schema W1
↓ encode fields in writer order / publish schema identity
② Envelope or container
payload bytes + schema ID/fingerprint or OCF header
↓ immutable transport/storage with checksum
③ Consumer control path
fetch exact writer schema W1 + choose reader schema R2
↓ compile resolution plan W1 × R2
④ Streaming decoder
match/read · promote · skip writer-only · fill reader default
↓ validate logical meaning and terminal outcome
⑤ Reader object / quarantine
typed object → idempotent sink → checkpoint
Data path: datum → writer-ordered bytes → envelope/file → decoder cursor → reader object.
Control path: writer schema ID, reader schema version, compatibility decision, aliases/defaults, limits와 rollout policy를 전달한다.
  1. Write: Producer는 W1 field 순서와 type encoding으로 datum을 쓴다. Schema 등록 성공과 payload publish의 원자성 경계를 정한다.
  2. Bind identity: OCF header, single-object fingerprint, message header 등으로 bytes가 어떤 writer schema에 속하는지 고정한다.
  3. Resolve: Consumer는 W1과 R2를 가져와 record name·field name/alias·primitive type·union branch를 재귀적으로 비교한다.
  4. Decode writer order: Reader가 원하는 순서가 아니라 W1의 순서로 bytes를 걷는다. R2에 없는 W1 field도 type을 알아야 정확히 skip할 수 있다.
  5. Materialize reader object: Match field는 decode/promote하고, R2에만 있는 field는 reader default가 있을 때 채운다. 없으면 resolution error다.
  6. Commit: Full consumption, logical-type/domain validation, reconciliation과 sink durability 뒤 checkpoint를 확정한다.

4. CS 내부 동작

4.1 Resolution은 writer를 따라가며 reader projection을 만든다

Record를 읽을 때 decoder는 writer field 순서로 움직인다. 같은 이름 또는 reader alias로 match되는 reader field가 있으면 두 type을 resolve해 값을 만든다. Reader에 없는 writer field는 writer type을 이용해 bytes를 skip한다. 모든 writer fields를 처리한 뒤 아직 채워지지 않은 reader field는 default를 쓰거나 실패한다.

Writer W1 vs Reader R2Resolution action
같은 field + 같은 typeWriter encoding으로 읽어 reader field에 넣는다.
같은 field + 허용 promotionWriter primitive를 읽고 reader primitive로 승격한다.
Writer에만 fieldWriter type에 따라 bytes를 소비하되 reader object에는 넣지 않는다.
Reader에만 field + defaultOld bytes를 읽은 뒤 reader schema의 default를 materialize한다.
Reader에만 field + no defaultResolution error. Guess, null, zero로 조용히 채우지 않는다.
Reader alias matches writer name지원되는 resolution 경로에서는 rename된 reader field로 연결한다.

4.2 Default는 write-time 값이 아니다

새 reader가 old writer bytes에 없던 currency를 요청하면 reader default KRW를 사용한다. Old bytes 자체가 바뀌거나 field가 추가되는 것은 아니다. New writer가 field를 명시적으로 다른 값으로 쓰면 그 값을 읽는다. 따라서 default 변경은 과거 bytes의 read 결과를 바꾸는 semantic change가 될 수 있다.

4.3 Field reorder와 rename은 같은 문제가 아니다

Writer bytes는 writer schema 순서대로 쓰인다. Reader fields 순서가 달라도 name matching으로 결과를 구성할 수 있다. 그러나 rename은 이름 identity를 바꾸므로 alias 또는 별도 migration이 필요하다. “Record field 순서를 바꿔도 읽힌다”는 사실을 “이름을 바꿔도 자동으로 읽힌다”로 확장하면 안 된다.

4.4 Promotion과 logical type은 별도 층이다

Primitive numeric promotion은 규격이 허용한 방향만 사용한다. Narrowing은 overflow/precision 손실 때문에 거부해야 한다. Decimal, timestamp 같은 logical type은 underlying bytes만 맞는다고 business semantics가 같은 것이 아니다. Precision/scale, unit, timezone 정책과 runtime 지원을 golden data로 확인한다.

4.5 Union은 branch index와 schema match가 함께 필요하다

Writer는 union에서 실제 값에 해당하는 branch index와 branch bytes를 쓴다. Reader는 writer가 선택한 schema를 reader union의 호환 가능한 branch와 resolve한다. Reader union 순서, ambiguous named types와 default를 변경할 때 registry 판정만 믿지 말고 모든 branch fixture를 읽는다.

4.6 Container와 schemaless datum의 failure model이 다르다

OCF는 header metadata에 writer schema가 있어 file 자체로 lookup이 가능하다. Schemaless RPC/message bytes는 외부 schema ID가 사라지면 복원이 어렵다. Single-object encoding은 marker와 fingerprint로 lookup을 돕는다. 어느 방식이든 registry/cache outage, unknown ID, hash mismatch와 partial envelope에 대한 정책이 필요하다.

4.7 Resolution plan caching은 identity가 정확해야 한다

W×R 비교는 매 record마다 반복하기보다 schema identity pair로 plan을 cache할 수 있다. Cache key를 mutable subject “latest”로 잡으면 schema가 바뀐 뒤 오래된 plan이 재사용된다. Immutable writer fingerprint와 reader version을 key로 쓰고 eviction·negative cache·registry outage를 관측한다.

5. 실무 설계 판단

판단Best practice와 이유
Schema identityPayload와 immutable writer schema ID/fingerprint를 atomic envelope에 묶고 checksum·producer build를 기록한다.
Registry dependencyLocal bounded cache, startup prefetch, unknown-ID quarantine와 outage SLO를 둔다. 최신 schema fallback은 금지한다.
Add fieldNew reader가 old bytes를 읽어야 한다면 reader default와 business-safe meaning을 설계하고 old/new matrix를 실행한다.
Remove fieldOld readers가 new writer bytes를 읽는 방향을 검증하고 reuse/rename하지 않도록 lifecycle 기록을 유지한다.
RenameAlias 지원 범위와 중간 JSON/ETL/registry 동작을 검증한다. Critical field는 dual-write/dual-read migration을 고려한다.
LimitsMax message, string/bytes, array/map items, block size와 recursion depth를 decoder와 envelope 양쪽에 둔다.
RolloutReaders first → canary writers → shadow decode 순서로 배포하고 resolution errors, default usage, promotion, schema-ID miss와 domain aggregates를 비교한다.
ProofOld/new writer × old/new reader 2×2 bytes, union branches, null/default, aliases와 boundary values를 CI artifact로 보존한다.

Anti-pattern·edge case·version 차이

  • Reader schema만으로 decode: Avro datum의 field order/type boundary를 잃는다.
  • Unknown schema ID에 latest 사용: 조용한 오해석과 재현 불가능한 사고를 만든다.
  • Default=null이면 optional: Union/presence와 business required는 별도 계약이다.
  • Registry compatibility=semantic safety: Unit·currency·timezone·enum meaning과 default 변경은 별도다.
  • Alias만 추가하면 rename 완료: 모든 library, registry, JSON bridge와 analytics consumer가 alias를 동일하게 지원하지 않을 수 있다.
  • Promotion을 cast로 일반화: Narrowing과 decimal scale 변경은 손실을 만들 수 있다.
  • OCF header만 신뢰: Header/payload corruption, wrong codec, truncated block와 schema spoofing을 checksum·limits로 검증한다.
  • Cache key=subject latest: Old payload에 새 resolution plan을 적용할 수 있다.
  • Runtime 동작 동일 가정: Alias, logical type, union/default, malformed block와 limit 처리에는 language library/version 차이가 있을 수 있다.

7. 35분 실습: writer × reader resolution matrix

목표: 같은 W1 bytes를 compatible R2, alias R3, incompatible reader로 읽고, wrong writer schema가 왜 위험한지 fastavro로 재현한다.

사전 조건: 저장소 루트, Docker Desktop. 이 프로젝트의 고정된 Python/fastavro 환경을 사용한다.

실행 전 예측: R2의 새 currency 값, R3의 rename 결과, default 없는 reader-only field와 long→int narrowing 결과를 먼저 적는다. Reader field 순서를 바꾸면 bytes 소비 순서도 바뀌는지 생각한다.

7.1 Compatible·alias·writer-only field 관찰

cd "$(git rev-parse --show-toplevel)" docker compose run --rm lab python - <<'PY' from io import BytesIO from fastavro import schemaless_reader, schemaless_writer W1 = {"type":"record", "name":"Order", "namespace":"lab", "fields":[ {"name":"id", "type":"long"}, {"name":"amount", "type":"int"}, {"name":"legacy_note", "type":"string"} ]} datum = {"id":7, "amount":1200, "legacy_note":"old"} buf = BytesIO(); schemaless_writer(buf, W1, datum); raw = buf.getvalue() print("W1 bytes=", raw.hex(" ")) R2 = {"type":"record", "name":"Order", "namespace":"lab", "fields":[ {"name":"amount", "type":"long"}, {"name":"id", "type":"long"}, {"name":"currency", "type":"string", "default":"KRW"} ]} out2 = schemaless_reader(BytesIO(raw), W1, R2) print("R2=", out2) assert out2 == {"id":7, "amount":1200, "currency":"KRW"} R3 = {"type":"record", "name":"Order", "namespace":"lab", "fields":[ {"name":"id", "type":"long"}, {"name":"total", "type":"long", "aliases":["amount"]} ]} out3 = schemaless_reader(BytesIO(raw), W1, R3) print("R3 alias=", out3) assert out3 == {"id":7, "total":1200} print("observed: reader order changed, writer-only legacy_note skipped, default materialized") PY

예상 관찰: W1 bytes에는 field names가 없다. R2는 writer order로 bytes를 소비하면서 reader 결과를 id, amount, currency로 만들고 legacy_note를 skip한다. Amount int는 long으로 promotion되고 currency는 old bytes가 아니라 reader default에서 생긴다. R3는 alias가 지원되는 경로에서 amount를 total로 연결한다.

7.2 실패 주입: no default·narrowing·wrong writer schema

cd "$(git rev-parse --show-toplevel)" docker compose run --rm lab python - <<'PY' from io import BytesIO from fastavro import schemaless_reader, schemaless_writer W = {"type":"record", "name":"Metric", "fields":[ {"name":"id", "type":"long"}, {"name":"value", "type":"long"} ]} buf = BytesIO(); schemaless_writer(buf, W, {"id":1, "value":2147483648}) raw = buf.getvalue(); print("bytes=", raw.hex(" ")) cases = { "reader_field_without_default": {"type":"record", "name":"Metric", "fields":[ {"name":"id", "type":"long"}, {"name":"value", "type":"long"}, {"name":"unit", "type":"string"}]}, "narrow_long_to_int": {"type":"record", "name":"Metric", "fields":[ {"name":"id", "type":"long"}, {"name":"value", "type":"int"}]} } for name, reader in cases.items(): try: print(name, schemaless_reader(BytesIO(raw), W, reader)) except Exception as e: print(name, "REJECT", type(e).__name__, str(e)[:160]) WRONG_W = {"type":"record", "name":"Metric", "fields":[ {"name":"value", "type":"long"}, {"name":"id", "type":"long"} ]} try: print("wrong_writer_schema=", schemaless_reader(BytesIO(raw), WRONG_W, W)) except Exception as e: print("wrong_writer_schema REJECT", type(e).__name__, str(e)[:160]) PY

예상 관찰: Reader-only unit에 default가 없으면 resolution이 실패한다. Long→int narrowing도 거부된다. Wrong writer schema는 오류가 날 수도 있고 값이 바뀌어 보일 수도 있으므로 “예외가 없었다”를 정합성 증거로 사용하지 않는다. Exact schema identity와 business aggregate 검증이 필요하다.

8. 놓치기 쉬운 함정

  1. Writer schema는 “옛 schema”가 아니라 해당 bytes를 실제로 쓴 schema다.
  2. Reader schema field order와 writer bytes order를 혼동하지 않는다.
  3. Writer-only field skip에도 writer type이 필요하다. Field name만 알아서는 byte length를 모른다.
  4. Reader default 변경은 같은 old bytes의 현재 read 결과를 바꿀 수 있다.
  5. Alias는 wire bytes를 다시 쓰지 않지만 모든 중간 시스템의 field mapping을 자동 고치지 않는다.
  6. Primitive resolution 통과와 logical-type/domain compatibility를 구분한다.
  7. Union의 모든 branch와 null/non-null fixture를 테스트한다.
  8. Registry cache hit가 정확한 schema를 의미하려면 immutable ID/fingerprint key가 필요하다.
  9. Schema ID header와 payload publish를 분리해 쓰면 crash window에서 서로 다른 세대가 결합될 수 있다.

9. 대기업 기술 면접 질문

Q1. Avro에서 writer schema와 reader schema가 둘 다 필요한 이유를 설명하세요.

좋은 답변 구조: Avro datum이 field tag/name을 반복하지 않는다는 byte layout부터 말한다 → writer order로 cursor를 움직이고 reader name/alias로 projection하는 흐름을 그린다 → match/promote/skip/default/error 규칙을 설명한다 → schema ID loss·wrong schema·registry outage failure window를 다룬다 → OCF, single-object, Protobuf 대안과 size/운영 trade-off를 비교한다.

Q2. 새 field 추가가 안전한지 어떻게 판정합니까?

좋은 답변 구조: Backward/forward 요구와 배포 순서를 먼저 묻는다 → reader-only field가 old bytes에서 default를 필요로 함을 설명한다 → default의 business meaning과 null/presence를 검토한다 → old/new writer×reader 2×2, union/boundary fixtures와 metrics를 설계한다 → readers-first canary, rollback, idempotent replay를 제시한다.

Q3. Registry 장애 중에도 ingestion을 계속해야 합니까?

좋은 답변 구조: SLO·data loss 허용·known/unknown ID를 구분한다 → immutable schema cache와 cache key를 설계한다 → known ID는 bounded cache로 처리하고 unknown ID는 backpressure/quarantine한다 → latest fallback을 거부한다 → cache age/miss/registry latency, replay capacity와 fail-open/fail-closed 비용을 수치로 방어한다.
