FILE FORMAT · WEEK 3 / DAY 18

backward/forward/full compatibility

Writer×reader 방향에서 rolling deploy·rollback·retention까지 · 예상 학습 60분 + 실습 35분
한 줄 요약
호환성은 schema 두 장의 모양이 비슷한지가 아니라 어떤 writer가 만든 bytes를 어떤 reader가 읽어 어떤 의미를 얻는가의 방향성 계약이다. Backward는 새 reader가 old bytes를 읽는 것, forward는 old reader가 new bytes를 읽는 것, full은 양방향이며, 실제 안전성은 rolling deploy·rollback·저장 데이터 보존 기간 전체에서 검증해야 한다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의
WriterLogical value를 특정 schema/version으로 bytes에 기록한 producer다. 여기서는 W1, W2처럼 표시한다.
ReaderBytes를 자기 schema/version의 object와 의미로 복원하는 consumer다. R1, R2로 표시한다.

Full compatibleBackward와 forward가 모두 성립한다. 무중단 혼합 배포·consumer rollback에 유리하지만 business semantics까지 자동 보장하지 않는다.

Rollback문제 version에서 이전 binary/schema로 되돌리는 전환이다. New bytes가 이미 저장됐다면 old reader가 그것을 읽어야 하므로 forward 방향이 필요하다.

Semantic compatibility읽힌 값이 unit, range, presence, enum, PII, 권한과 domain invariant까지 같은 의도로 동작한다는 뜻이다.
Golden bytes특정 writer version이 만든 실제 serialized fixture와 기대 결과를 보존한 test artifact다.

2. 왜 중요한가

“새 schema가 old schema와 호환된다”는 문장은 방향이 없어서 운영 판단에 쓸 수 없다. 새 consumer를 먼저 배포할 때는 R2(W1)이 필요하고, 새 producer를 켠 뒤 old consumer가 남아 있거나 consumer를 rollback할 때는 R1(W2)가 필요하다. 두 방향의 요구 시점과 실패 비용이 다르다.

Registry가 adjacent schema diff를 통과시켰어도 6개월 된 object storage data, 재처리 queue, offline mobile client와 rollback binary에는 실패할 수 있다. 더구나 parser가 성공해도 새 code가 old message의 absent field를 잘못 해석하거나 old code가 새 enum 의미를 모르면 semantic incident가 난다.

오늘의 핵심 불변식: 호환성 판정에는 최소한 writer version, reader version, fixture bytes, expected logical result, runtime build와 적용 기간이 들어간다. “parse 성공”만으로 compatible이라 부르지 않는다.

4. CS 내부 동작

4.1 Backward와 forward는 시간축의 서로 다른 edge다

Readers-first 배포는 R2가 W1 bytes를 읽는 backward edge를 먼저 연다. 그 뒤 W2를 켜는 순간 R1이 남아 있으면 forward edge가 필요하다. Consumer를 함께 배포한다고 해도 queue lag, cache, retry와 rollback이 version skew를 만든다. “동시 배포”는 edge를 없애지 못한다.

4.2 Avro와 Protobuf의 byte mechanism은 다르다

관점AvroProtobuf binary
Field identityWriter/reader record field name·alias.Message 안의 field number.
Read inputsExact writer schema + optional reader schema.Tag-value bytes + reader generated schema.
Writer-only fieldWriter schema type으로 consume하고 reader result에서 무시.Wire type으로 skip하거나 runtime unknown state에 보존.
Reader-only fieldReader default가 있으면 materialize, 없으면 resolution error.Wire에 tag가 없고 generated API presence/default 규칙을 적용.
주요 위험Wrong writer schema, missing default, alias/type resolution.Number reuse, conditionally compatible type, unknown loss, presence/oneof.

4.3 Protobuf field 추가는 wire-safe여도 application-safe가 아닐 수 있다

Binary에서 새 field를 추가하면 R1은 unknown field로 처리하고 R2는 W1 bytes에서 absent 상태를 본다. 두 방향 parse는 흔히 성공한다. 그러나 R2 business logic이 email이 반드시 있어야 한다고 가정하거나, R1 proxy가 ProtoJSON을 거치며 unknown email을 잃으면 round-trip과 의미는 깨진다.

공식 문서는 binary wire-safe와 conditionally wire-compatible를 구분한다. 같은 wire type이라 parse 가능한 type 변경도 truncation, UTF-8, singular/repeated last-one-wins, enum runtime 표현 때문에 값이 손실될 수 있다. Schema checker가 “compatible”이라고 해도 golden values가 필요하다.

4.4 Transitive 정책은 history set의 크기를 정한다

Non-transitive check가 V3↔V2와 V2↔V1을 각각 통과해도 V3↔V1이 성립한다고 일반적으로 보장되지 않는다. 중간 version에서 default·alias·reserved·type을 단계적으로 바꾸면 누적 변화가 edge를 끊을 수 있다. 검사 대상은 직전 version이 아니라 실제 retention과 deployed readers가 만든 version set이다.

4.5 Compatibility는 relation이지 schema의 단일 속성이 아니다

Compatible(W,R,bytes,runtime,semantics)처럼 여러 입력에 대한 관계로 본다. 같은 schema pair도 Java와 Python의 enum API, JSON bridge, library limit, corrupt-input policy가 다르면 결과가 다르다. 그래서 schema diff, golden byte test, deployment telemetry의 세 층이 모두 필요하다.

4.6 성공 확정점은 rollback 가능성까지 포함한다

Canary parse error가 0이라고 완료가 아니다. New writer bytes가 retention에 들어간 뒤 old reader rollback이 가능한지, unknown/default/presence와 domain aggregate가 정상인지, failed generation을 어느 checkpoint부터 idempotent replay할지 확인해야 한다. Rollback binary가 new data를 읽지 못하면 code rollback만으로 복구되지 않는다.

Anti-pattern·edge case·version 차이

  • 호환=true 한 줄: 방향, history, runtime, semantics가 빠졌다.
  • Registry pass=production safe: Unit·presence·default·enum·PII·authorization을 검사하지 못한다.
  • R1/W2만 테스트: Backward edge와 baseline/target조차 빠진다.
  • Adjacent pass면 transitive: 누적 default·rename·type 단계가 V1↔V3 edge를 끊을 수 있다.
  • 동시 배포로 해결: Queue lag, cache, offline client와 rollback이 skew를 유지한다.
  • Parse error 0=성공: Silent truncation, unknown loss, default 증가와 domain aggregate 오염을 놓친다.
  • Protobuf field 추가는 무조건 full: Binary wire에서는 안전해도 required business logic·JSON bridge·oneof가 깨질 수 있다.
  • Avro default가 optional: Default는 reader가 old bytes를 읽을 때 materialize하며 writer encode 의무와 별개다.
  • Rollback=old binary 재배포: 이미 생성된 W2 bytes를 R1이 읽을 수 있는지 먼저 확인해야 한다.
  • 모든 언어 runtime 동일: Enum, unknown field, presence, size limit과 generated API가 다를 수 있다.

증상배포 뒤 특정 version pair만 parse 실패, rollback 후 consumer crash, unknown/default/null 급증, enum·sum·currency·권한 값 변화, replay에서만 실패, JSON proxy 뒤 새 field 소실, old mobile client 오류.

안전한 첫 조치Writer 확대와 affected consumer checkpoint를 멈춘다. Version pair별 traffic을 격리하고 payload·schema·runtime을 보존해 4칸 matrix를 production build로 offline 재현한다. Parse 성공 값도 domain invariant와 비교한다.
Rollback / 복구Last-known-good W/R pair로 routing하고 incompatible W2 generation을 quarantine한다. 필요하면 tolerant R2 reader를 먼저 복구 배포한다. Safe checkpoint부터 idempotent replay하고 pair count·unknown/default·business aggregate를 reconcile한 뒤 pointer를 전환한다.
하지 말아야 할 조치Latest schema fallback, raw bytes 수정, failed row skip 후 checkpoint, unknown/default를 임의 값으로 치환, registry policy를 즉석 완화, version label 없이 전체 traffic 합산, 증거 없는 cache clear, idempotency 없는 replay, new bytes 존재 확인 없이 old binary만 rollback하지 않는다.

7. 35분 실습: W1/W2 × R1/R2 compatibility matrix

목표: Python 표준 라이브러리만으로 Protobuf-like tag stream을 만들고, field 추가가 두 방향에서 parse되는 이유와 wire compatibility가 business compatibility를 보장하지 않는 이유를 관찰한다.

사전 조건: Python 3.9 이상. 외부 package나 protoc는 필요 없다. 이 코드는 교육용 bounded scanner이며 production runtime 대체가 아니다.

실행 전 예측: V2에 email=3을 추가했을 때 R2(W1)의 email presence, R1(W2)의 unknown field를 적는다. “email은 모든 신규 logic에서 필수”라는 domain rule을 켜면 어느 칸이 실패할지 예상한다.

7.1 네 칸을 bytes로 실행

python3 - <<'PY' def varint(n): out = bytearray() while n > 0x7f: out.append((n & 0x7f) | 0x80); n >>= 7 out.append(n); return bytes(out) def field(no, wire, value): key = varint((no << 3) | wire) if wire == 0: return key + varint(value) if wire == 2: raw = value.encode(); return key + varint(len(raw)) + raw raise ValueError("lab supports wire 0/2") def readv(buf, p): n = 0 for i in range(10): if p >= len(buf): raise ValueError("TRUNCATED_VARINT") b = buf[p]; p += 1; n |= (b & 0x7f) << (7*i) if b < 128: return n, p raise ValueError("OVERLONG_VARINT") def parse(buf, schema, max_len=128): p, obj, present, unknown = 0, {}, set(), [] while p < len(buf): key, p = readv(buf, p); no, wire = key >> 3, key & 7 if no == 0 or wire not in (0, 2): raise ValueError("BAD_TAG") if wire == 0: value, p = readv(buf, p) else: size, p = readv(buf, p) if size > max_len or size > len(buf)-p: raise ValueError("BAD_LEN") value, p = buf[p:p+size].decode(), p+size spec = schema.get(no) if spec is None: unknown.append((no, wire, value)); continue name, expected, default = spec if wire != expected: raise ValueError(f"WIRE_MISMATCH field={no}") obj[name] = value; present.add(name) for name, wire, default in schema.values(): obj.setdefault(name, default) return obj, present, unknown V1 = {1:("id",0,0), 2:("name",2,"")} V2 = {1:("id",0,0), 2:("name",2,""), 3:("email",2,"")} W1 = field(1,0,7) + field(2,2,"kim") W2 = W1 + field(3,2,"kim@example.com") for rname, schema in [("R1",V1),("R2",V2)]: for wname, raw in [("W1",W1),("W2",W2)]: obj, present, unknown = parse(raw, schema) business_ok = not (rname == "R2" and "email" not in present) print(f"{rname}({wname})", obj, "present=", sorted(present), "unknown=", unknown, "business_ok=", business_ok) print("W1=", W1.hex(" ")); print("W2=", W2.hex(" ")) PY

예상 관찰: 네 칸 모두 wire parse는 성공한다. R2(W1)은 email이 default empty지만 presence에는 없고 business rule은 실패한다. R1(W2)는 field 3을 unknown으로 분리한다. 즉 field 추가는 binary 양방향에 안전할 수 있지만 application full compatibility는 별도 판정이다.

7.2 실패 주입: 번호/type 재사용과 adjacent-only 함정

python3 - <<'PY' def v(n): o=bytearray() while n>127:o.append((n&127)|128);n>>=7 o.append(n);return bytes(o) def rv(b,p=0): n=0 for i in range(10): if p>=len(b):raise ValueError("EOF") x=b[p];p+=1;n|=(x&127)<<(7*i) if x<128:return n,p raise ValueError("OVERLONG") def one(raw, expected_wire): key,p=rv(raw); no,wire=key>>3,key&7 if no!=2 or wire!=expected_wire: raise ValueError(f"WIRE_MISMATCH {wire}!={expected_wire}") if wire==0:return rv(raw,p)[0] size,p=rv(raw,p) if size>len(raw)-p:raise ValueError("BAD_LEN") return raw[p:p+size].decode() old_name = v((2<<3)|2) + v(3) + b"kim" # V1: string name = 2 new_admin = v((2<<3)|0) + v(1) # V3: bool is_admin = 2 (금지) for label, raw, expected in [ ("R3(W1)", old_name, 0), ("R1(W3)", new_admin, 2)]: try: print(label, one(raw, expected)) except Exception as e: print(label, "REJECT", e) # Adjacent relation은 자동으로 transitive하지 않음을 작은 graph로 확인한다. edges={"V2": {"V1"}, "V3": {"V2"}} print("adjacent checks pass=", "V1" in edges["V2"] and "V2" in edges["V3"]) print("V3 directly checked against V1=", "V1" in edges["V3"]) PY

예상 관찰: 번호 2의 wire type을 바꾼 두 교차 방향은 모두 mismatch로 거부된다. Adjacent edge 두 개가 있어도 V3↔V1 direct proof는 없다. 실제 CI에서는 history set의 모든 golden bytes를 각 supported reader로 실행해야 한다.

7.3 자주 나는 오류와 해결·cleanup

  • Default empty를 present로 판단: Object value와 wire presence를 따로 기록한다.
  • Unknown을 실패로 처리: Format/runtime policy에 맞게 skip·preserve하고 metric으로 관찰한다.
  • 한 runtime만 실행: 실제 producer/consumer 언어·compiler/library 조합을 matrix dimension에 추가한다.
  • Business assertion 생략: Parse 결과뿐 아니라 unit/range/enum/PII/권한·aggregate를 fixture 기대값에 넣는다.

Cleanup: 위 명령은 파일·package·container를 만들지 않는다. 실제 production bytes에는 PII가 있을 수 있으므로 terminal·CI log에 붙여 넣지 않는다.

8. 놓치기 쉬운 함정

  1. Backward/forward 이름보다 reader와 writer 방향식을 먼저 쓴다.
  2. Baseline R1(W1)과 target R2(W2)도 검증해야 fixture 자체 오류를 찾을 수 있다.
  3. Full compatibility는 transitive compatibility와 다르다.
  4. Schema pair가 같아도 runtime·bridge·limit이 다르면 결과가 달라진다.
  5. Protobuf unknown field가 JSON 또는 field-by-field copy에서 사라질 수 있다.
  6. Avro reader default는 old bytes에 쓰여 있지 않으며 read-time 결과다.
  7. Wire-safe change도 generated API compile과 exhaustive enum switch를 깨뜨릴 수 있다.
  8. Stored data retention과 retry TTL 중 더 긴 기간이 history scope를 결정할 수 있다.
  9. Rollback binary가 new bytes를 읽지 못하면 단순 code rollback은 복구가 아니다.
  10. 호환성 완료 시점은 canary뿐 아니라 replay·reconciliation 성공까지 포함한다.

9. 대기업 기술 면접 질문

Q1. Backward·forward·full compatibility를 rolling deploy 흐름으로 설명하세요.

좋은 답변 구조: W1/W2와 R1/R2를 정의한다 → 4칸 matrix와 두 방향식을 그린다 → readers-first에서 R2(W1), writer canary에서 R1(W2)가 필요한 이유를 말한다 → queue/retention/offline/rollback failure window를 포함한다 → pair별 metrics·golden bytes·idempotent rollback/replay로 성공 조건을 제시한다.

Q2. Registry에서 FULL_TRANSITIVE를 켜면 왜 충분하지 않을 수 있습니까?

좋은 답변 구조: Registry의 schema-level relation과 scope를 확인한다 → runtime·format(Avro/Protobuf/JSON) byte mechanism을 구분한다 → default/presence/enum/unit/PII/unknown loss를 든다 → 실제 retention version set과 compiler/library matrix를 수치로 가정한다 → CI golden matrix, canary telemetry와 domain reconciliation을 추가한다.

Q3. 1년 보관 이벤트 schema를 무중단으로 변경하는 절차를 설계하세요.

좋은 답변 구조: Producer/consumer·replay SLA와 비용을 묻는다 → 모든 retained writer generation과 rollback readers를 inventory한다 → 새 field/dual-write/read migration을 설계한다 → readers-first, shadow old data, writer canary, fleet 확대 순서를 말한다 → quarantine capacity, checkpoint, rollback pointer, backfill/reconcile와 최종 tombstone을 방어한다.

10. 복습과 정답

어제 내용 회상 3문제

  1. Protobuf tag에서 field number와 wire type을 꺼내는 식은?
  2. Unknown LEN field를 안전하게 skip하는 순서는?
  3. Field number를 같은 wire type의 다른 의미로 재사용하면 왜 더 위험할 수 있는가?

오늘 내용 확인 3문제

  1. Readers-first와 writers-first 각 단계에서 필요한 compatibility 방향식을 쓰라.
  2. Protobuf 새 field 추가가 wire에서는 양방향 parse되는데 business에서는 backward 실패할 수 있는 예를 들어라.
  3. Adjacent FULL과 FULL_TRANSITIVE의 증거 범위 차이, 그리고 retention이 policy 선택에 미치는 영향을 설명하라.

짧은 정답·채점 기준

어제 1Encode는 (field_number << 3) | wire_type. Decode는 field=tag>>3, wire=tag&7이다.
어제 2Bounded tag → valid field/wire → bounded length → app limit/overflow → frame remaining → bounded slice와 cursor commit 순서다.
어제 3Parser가 성공해 old value를 bool/enum/권한 같은 새 의미로 조용히 오해석할 수 있기 때문이다.
오늘 1Readers-first는 R2(W1) backward, W2 canary 중 old reader가 남으면 R1(W2) forward가 필요하다.
오늘 2R2가 W1의 absent email을 default empty로 읽지만 새 logic이 email을 필수로 요구하면 parse 성공 뒤 domain 실패다.
오늘 3Adjacent는 Vn↔Vn-1, transitive는 supported history 전체와 직접 증명한다. 1년 data를 replay하면 1년의 writer generations를 scope에 포함해야 한다.

채점: 각 2점, 총 12점. 10점 이상 통과. 방향식, byte mechanism, version skew, transitive scope, semantic metric과 rollback/replay를 연결하면 면접 Level 3다.
