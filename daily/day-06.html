1. 선수 용어 사전

용어쉬운 설명과 정확한 정의
Logical value프로그램이 의미로 다루는 값이다. 예를 들어 {id: 513, name: "가"}는 아직 특정 파일의 bytes가 아니다.
Physical layout값·길이·경계·metadata가 파일의 어느 byte offset에 어떤 순서로 놓이는지 정한 배치 규칙이다.
Serialization구조화된 값을 저장·전송 가능한 byte sequence로 바꾸고 되돌리는 규칙과 과정이다.
Parser / decoderByte를 문법과 schema에 따라 읽어 token·field·typed value로 복원하는 구성요소다. Bytes가 유효해도 잘못된 contract를 쓰면 의미는 틀릴 수 있다.
Hex dump각 byte를 16진수 두 자리로 보여 주는 관찰 방법이다. 41은 decimal 65인 한 byte일 뿐이며, 문자 A인지는 encoding contract가 결정한다.
Offset파일 시작에서 몇 번째 byte인지 나타내는 위치다. Reader는 length·offset metadata로 필요한 범위를 찾는다.
Magic bytes파일 종류나 구조를 식별하려고 약속한 고정 byte 패턴이다. 확장자보다 강한 힌트지만, 전체 무결성을 보장하는 checksum은 아니다.
Framing연속된 byte stream에서 record의 시작과 끝을 찾는 규칙이다. Newline, delimiter, length prefix 등이 사용된다.
Endianness여러 byte짜리 정수를 상위 byte부터 둘지(big-endian), 하위 byte부터 둘지(little-endian) 정한 순서다.
Footer파일 끝부분에 둔 schema·offset·statistics 같은 metadata다. Reader가 먼저 끝을 읽어 data 위치를 계획할 수 있다.

2. 왜 중요한가

운영 장애에서 “파일이 존재한다”와 “올바른 reader가 완전한 bytes를 읽어 같은 의미를 복원한다”는 전혀 다른 주장이다. 확장자가 .parquet여도 JSON bytes일 수 있고, UTF-8 CSV도 record 중간에서 잘렸거나 dialect가 다르면 row boundary가 바뀐다. 반대로 binary는 암호화된 것이 아니라 사람이 바로 읽기 어려운 byte layout일 뿐이다.

Hex 관찰의 목적은 모든 포맷을 눈으로 decode하는 데 있지 않다. 어떤 사실이 byte에 직접 있고, 어떤 의미가 외부 schema·reader 설정에 의존하는지 구분하는 데 있다. 이 경계를 알아야 schema drift, 잘린 파일, 잘못된 encoding, writer/reader 버전 차이를 증거로 진단할 수 있다.

면접 기준: “Parquet가 더 빠르다”에서 멈추지 말고, 동일 logical rows가 text token·record framing·column chunk·footer로 어떻게 달라지고, workload·CPU·I/O·복구 단위가 어떤 trade-off를 만드는지 설명해야 한다.

3. 아키텍처 그림과 요청 흐름

① Logical rows
typed values
↓ schema + writer options (control path)
② Encoder
CSV / JSON / NDJSON / Parquet
↓ buffers → write syscall → bytes (data path)
③ File / object
header · payload · metadata · footer
↓ discover → open/range read → validate
④ Reader / parser
frame · parse metadata · decompress · decode
↓ typed vectors / rows + reject evidence
⑤ Consumer
business invariant · query · checkpoint
  1. 입력 상태: Application은 integer·string·null 같은 logical values와 field 의미를 소유한다. 아직 CSV comma나 Parquet page는 없다.
  2. 쓰기 제어: Writer는 schema, field order, UTF-8, delimiter, codec, row-group size를 결정한다. 이것이 control path다. 실제 values가 bytes로 이동하는 경로가 data path다.
  3. 쓰기 성공 경계: Process buffer에 썼다는 사실은 durable publish가 아니다. Flush·close·checksum·atomic rename 또는 object commit이 끝나고 catalog/manifest가 완성된 객체만 가리켜야 성공이다.
  4. 읽기 계획: Text reader는 앞에서부터 delimiter와 newline을 찾는 경우가 많다. Columnar reader는 footer/schema/offset을 먼저 읽고 필요한 column chunk와 row group만 range-read할 수 있다.
  5. decode와 검증: Parser 성공 뒤에도 amount 범위, nullability, row count, schema fingerprint 같은 business invariant를 통과해야 한다. 그 후에만 downstream checkpoint를 commit한다.

상태 소유자·불변식·성공 시점

Producer / writerLogical schema, serializer options, record count, idempotency key와 publish protocol을 소유한다.
Storage / publisher완성 전 staging 격리, durable object, checksum/size, atomic visibility와 immutable version을 소유한다.
Reader / consumerExpected format/schema, strict decode, quarantine, invariant 검증과 checkpoint를 소유한다.
핵심 불변식동일 input version은 동일 logical rows로 decode되고, 공개된 파일은 완전하며, 실패 row는 원본 bytes와 이유를 잃지 않는다.
소비 성공Decode + schema + row/count/range invariant + downstream write가 성공한 뒤 checkpoint가 원자적으로 확정될 때다.

4. CS 내부 동작: 의미가 bytes가 되는 순간

4.1 Text format: token과 framing도 bytes다

CSV의 integer 513은 보통 UTF-8 bytes 35 31 33으로 기록된다. 숫자 513 자체를 binary integer로 저장한 것이 아니라 문자 '5' '1' '3'을 저장한 것이다. Comma 2c, quote 22, LF 0a도 payload와 record boundary를 구성한다. Reader는 byte→문자 decode 뒤 dialect 문법을 적용하고, 다시 string→integer type conversion을 수행한다.

JSON은 field name과 punctuation을 매 row 반복하므로 self-describing에 가까운 가시성을 얻는 대신 byte 수와 parsing branch가 늘어난다. JSON array는 전체 container의 닫는 bracket이 필요하지만 NDJSON은 newline으로 record를 frame해 incremental processing과 record 단위 quarantine이 쉽다. 단, string 내부 newline escape와 실제 record newline을 구분해야 한다.

4.2 Binary layout: width·length·order가 contract다

513을 unsigned 32-bit little-endian으로 저장하면 01 02 00 00, big-endian이면 00 00 02 01이다. 네 bytes만 보고 signedness·endianness·field meaning을 알 수 없다. Variable-length string은 보통 length prefix 또는 offset table이 필요하다. Prefix 하나가 손상되면 다음 field 경계까지 잃을 수 있으므로 parser는 최대 길이와 remaining bytes를 확인해야 한다.

Schema-aware binary format은 field identity/type 규칙으로 parser의 추측을 줄인다. 하지만 schema가 payload 밖 registry에 있거나 writer schema를 잃으면, bytes가 온전해도 의미 복원이 불가능할 수 있다. Hex dump는 이 외부 의존성을 눈에 보이게 해 주는 증거다.

4.3 Columnar file: 같은 field를 모아 locality를 바꾼다

Parquet writer는 row를 받더라도 column별 values로 재배치해 row group 안의 column chunks와 pages를 만든다. Encoding이 repetition을 줄이고 codec이 encoded bytes를 압축한다. File footer에는 schema와 row group·column chunk 위치 같은 metadata가 들어간다. Reader는 끝의 magic/footer length를 이용해 metadata를 찾고 projection·statistics에 따라 data range를 선택한다.

그래서 Parquet 앞부분 128 bytes만 보고 모든 row를 읽을 수 없고, printable string이 거의 없다고 암호화된 것도 아니다. 반대로 footer magic이 보인다고 모든 page가 정상인 것도 아니다. Structural validation, checksum 지원 여부, 실제 decode와 row invariant를 단계적으로 확인해야 한다.

4.4 Memory·syscall·cache 비용

Serializer는 application objects를 buffer에 복사하고 encoding/compression을 수행한 뒤 OS write syscall로 kernel page cache에 넘긴다. Flush는 language buffer를 비울 수 있지만 storage durability까지 항상 보장하지는 않는다. 읽기에서는 file bytes가 page cache와 user-space buffer를 거쳐 parser/vector로 decode된다. Text parsing은 delimiter·escape·number conversion branch가 많고, columnar scan은 선택한 column의 연속 memory와 vectorized batch에 유리하지만 footer read·decompression·nested reconstruction 비용이 있다.

작은 sample의 파일 크기는 production 압축률의 결론이 아니다. Header/footer의 고정 비용, warm page cache, row 수, cardinality, sortedness, codec, column 선택률을 통제해야 CPU/I/O trade-off를 비교할 수 있다.

5. 실무 설계 판단

판단Best practice와 이유
Format detection확장자를 routing hint로만 쓰고 magic/header, parser probe, schema ID, content type을 함께 검증한다. 이름 변경만으로 format이 변하지 않는다.
Golden bytes대표 record의 실제 bytes·writer version·schema fingerprint·expected decoded values를 CI fixture로 보존한다. Library upgrade의 silent change를 잡는다.
Strict firstUnknown encoding, extra column, malformed row를 기본 실패로 하고 명시적 quarantine 정책만 허용한다. 조용한 replace/drop은 데이터 유실을 숨긴다.
Publish protocolStaging에 쓰고 close → size/checksum/schema/decode 검증 → immutable final publish → manifest commit 순서로 진행한다.
ObservabilityFile별 byte size, rows, schema/version, checksum, encode/decode latency, reject reason, compression ratio와 source identity를 기록한다.
Benchmark동일 logical rows와 query를 사용하고 warm/cold cache, codec, projection, selectivity, concurrency를 고정한다. 크기 하나로 결론내지 않는다.
Recovery원본 bytes를 immutable 보존하고 새 경로에 재처리한다. 운영 파일을 직접 고치지 않고 lineage와 idempotency key로 중복을 방지한다.

Anti-pattern·edge case·engine 차이

  • Hex에 printable text가 보이면 text format: Binary file metadata나 string column도 문자 bytes를 포함할 수 있다.
  • 파일 크기 = 유효 payload: Header/footer, dictionary, indexes, padding과 codec metadata가 포함된다.
  • 작은 sample로 압축 승자 선정: 고정 metadata가 지배하므로 production cardinality·분포·row 수에서 다시 측정한다.
  • Parser가 열면 정상: 일부 engine은 malformed row를 null/drop하거나 type을 자동 promotion한다. Strict option과 reject count를 명시한다.
  • JSON number는 항상 정확한 integer: Reader가 IEEE 754 double로 처리하면 큰 integer precision을 잃을 수 있다. Library와 target type을 테스트한다.
  • Parquet schema 동일 = 의미 동일: Timestamp timezone, decimal scale, unit, field semantics는 physical type만으로 보장되지 않는다.
  • 모든 Parquet reader가 동일: Logical type, page encoding, field ID, statistics 처리와 corrupt-file tolerance는 engine/library 버전에 따라 다를 수 있다.

6. 장애 대응

증상확장자는 Parquet인데 reader가 magic/footer 오류, CSV row 수 급감, Unicode decode 실패, 일부 file만 schema mismatch, 재시도 뒤 중복 row, 정상 parse됐지만 amount 합계가 달라짐.
먼저 수집할 증거/지표원본 immutable copy, URI/version/ETag, byte size와 checksum, 앞·뒤 64 bytes hex, detected MIME/magic, writer build·schema·options, reader/library version, row/reject count, publish timeline, 정상 file과의 diff.
가능한 가설잘못된 확장자/routing, partial upload·truncated footer, UTF-8/BOM/newline/dialect 차이, schema drift, codec/encoding 미지원, stale cache, length corruption, wrong object version, retry duplicate.
안전한 첫 조치해당 object version과 producer만 격리하고 downstream checkpoint를 멈춘다. 원본을 보존한 채 offline에서 strict reader와 hex/footer 검사를 수행하고 최근 정상 file과 비교한다.
Rollback / 복구Manifest를 마지막 검증된 immutable version으로 되돌린다. Correct writer로 새 object를 생성·검증해 새 version으로 publish하고 source ID 기반 idempotent replay 후 count/sum/checksum을 대조한다.
하지 말아야 할 조치확장자만 바꾸기, 운영 object 직접 byte 수정, decode error 무시/replace, bad row 조용히 drop, 모든 file 재업로드, checksum 없이 덮어쓰기, 실패 batch checkpoint commit, 원본 삭제를 하지 않는다.

7. 30분 통합 실습: 생성 → hex → decode → 실패 주입

목표: 동일한 3개 주문 row를 CSV·JSON·NDJSON·Parquet로 생성하고, byte layout과 schema/metadata 차이를 관찰한다. 파일 크기 순위를 먼저 예측한 뒤 실행한다.

사전 조건: 이 저장소 루트, Docker Desktop 실행, 약 2GB 여유 공간. 처음이면 image build 시간이 추가될 수 있다. 실습은 저장소의 고정 dependency(pyarrow 20.0.0, duckdb 1.3.2)를 사용한다.

7.1 환경과 동일 rows 생성

cd "/Users/limseunghyun/Documents/공부/File format" make doctor make build make sample wc -c practice/data/generated/orders.*

7.2 Hex에서 경계와 magic 찾기

for f in practice/data/generated/orders.csv \ practice/data/generated/orders.json \ practice/data/generated/orders.ndjson \ practice/data/generated/orders.parquet; do echo "=== $f ===" xxd -g 1 -l 128 "$f" done echo "=== parquet tail ===" tail -c 16 practice/data/generated/orders.parquet | xxd -g 1

실행 전 예측: CSV에서 comma(2c)와 LF(0a), JSON에서 brace/bracket·quote, NDJSON에서 row마다 LF를 찾는다. Parquet는 앞·뒤의 PAR1 magic이 보이지만 row text가 연속해서 보이지 않을 것이다.

관찰 기록: 각 포맷에 대해 ① record 경계 ② field name 반복 여부 ③ type 정보 위치 ④ random access용 metadata ⑤ 사람이 schema 없이 복원 가능한 범위를 표로 적는다.

7.3 Reader가 보는 schema와 footer

docker compose run --rm lab python - <<'PY' import pyarrow.parquet as pq p = "practice/data/generated/orders.parquet" pf = pq.ParquetFile(p) print("schema:", pf.schema_arrow) print("row_groups:", pf.metadata.num_row_groups) print("rows:", pf.metadata.num_rows) for i in range(pf.metadata.num_row_groups): rg = pf.metadata.row_group(i) print("row_group", i, "bytes", rg.total_byte_size) for j in range(rg.num_columns): c = rg.column(j) print(" ", c.path_in_schema, c.compression, c.encodings) PY

예상 관찰: Logical fields와 physical metadata가 분리되어 보인다. Reader는 모든 row bytes를 text처럼 scan하지 않고 footer metadata로 row group과 column 위치를 계획한다.

7.4 실패 주입 A: 확장자와 content 불일치

예상: Hex는 JSON bracket을 보이고 Parquet reader는 magic/footer가 없어서 거부한다. 파일명을 고치는 것이 아니라 routing·producer·manifest contract를 고쳐야 한다.

7.5 실패 주입 B: footer가 잘린 partial file

cp practice/data/generated/orders.parquet \ practice/data/generated/orders-truncated.parquet python3 - <<'PY' from pathlib import Path p = Path("practice/data/generated/orders-truncated.parquet") b = p.read_bytes() p.write_bytes(b[:-8]) print("truncated", len(b), "->", p.stat().st_size) PY tail -c 16 practice/data/generated/orders-truncated.parquet | xxd -g 1 docker compose run --rm lab python - <<'PY' import pyarrow.parquet as pq p = "practice/data/generated/orders-truncated.parquet" try: pq.read_table(p) except Exception as e: print(type(e).__name__, str(e)) PY

예상: File은 존재하고 앞부분 data도 남아 있지만 footer length/magic을 잃어 정상 Parquet로 열리지 않는다. Reader에서 “일단 읽히는 row만” 살리기보다 원본 version을 격리하고 producer publish를 복구한다.

8. 놓치기 쉬운 함정

  • Hex dump를 의미로 착각: 같은 bytes도 encoding/schema에 따라 다른 값이 된다. 반드시 writer contract와 함께 본다.
  • 한글 한 글자 = 한 byte: UTF-8에서 한글은 여러 bytes다. Character count와 byte length를 분리한다.
  • Newline을 항상 0a로 가정: CRLF(0d 0a), quoted multiline, final newline 유무가 있다.
  • Magic bytes = 무결성: Header/footer signature가 있어도 중간 page corruption과 semantic 오류는 남을 수 있다.
  • Parquet가 3 rows에서 더 큼 = 비효율: 작은 sample에서는 footer·schema 고정 비용이 지배한다.
  • Decode 성공 후 즉시 checkpoint: Row count·range·sum·schema invariant와 sink commit까지 확인해야 안전하다.
  • 복구하며 원본 덮어쓰기: 증거와 재현성을 잃는다. Immutable copy와 새 output version을 사용한다.

9. 대기업 기술 면접 질문

Q1. 동일한 주문 데이터를 CSV와 Parquet로 저장하면 bytes와 read path가 어떻게 달라집니까?

좋은 답변 구조: ① workload와 row/column 수를 가정 ② CSV의 UTF-8 token·delimiter·newline·type parse ③ Parquet row group→column chunk→page·footer metadata ④ projection/pruning·decompression·vector decode 경로 ⑤ 작은 파일·point lookup·write latency 반례 ⑥ bytes read, CPU, planning time으로 검증한다.

Q2. .parquet 파일이 열리지 않을 때 첫 10분의 진단 순서를 말해 보세요.

좋은 답변 구조: ① 재시도/소비 checkpoint 중지 ② URI·version·size·checksum·publish timeline 수집 ③ 앞/뒤 magic과 footer, 정상 file diff ④ wrong content·partial publish·unsupported feature·schema/codec 가설 분리 ⑤ immutable 원본 격리 ⑥ last-known-good manifest rollback과 새 version 재발행 ⑦ 확장자 변경·원본 수정·silent skip 금지까지 말한다.

Q3. Hex dump 실험을 production 포맷 선택 근거로 어떻게 확장하겠습니까?

좋은 답변 구조: ① Hex는 layout 이해와 golden-byte 회귀 검사의 도구라고 한정 ② 실제 분포·cardinality·null·nested data generator ③ codec·file/row-group size·projection·selectivity matrix ④ cold/warm cache와 concurrency 통제 ⑤ p50/p95 latency, CPU, bytes/request, rejects 측정 ⑥ corruption·schema evolution·rollback drill ⑦ 비용·호환성·운영성 ADR로 결론낸다.

10. 복습과 정답

어제 내용 회상 3문제: schema contract

  1. Backward compatibility를 reader/writer 주어를 넣어 한 문장으로 정의하라.
  2. Field rename이 wire-safe처럼 보여도 위험한 이유 두 가지를 말하라.
  3. Expand-contract 배포 순서를 네 단계로 말하라.
짧은 정답: ① New reader가 old writer data를 읽는다. ② 이름 기반 system에서는 drop+add가 될 수 있고, alias/field ID·JSON gateway·engine 지원이 다르다. ③ Reader 확장 → writer dual/new write → 관찰·backfill → old read/write 제거. 각 단계는 rollback 가능해야 한다.

오늘 내용 확인 3문제

  1. Hex에서 35 31 33과 01 02 00 00이 모두 513을 나타낼 수 있는 이유는?
  2. Parquet footer가 잘린 파일이 “존재하지만 publish 성공이 아닌” 이유는?
  3. 확장자와 content가 다를 때 안전한 첫 조치와 하지 말아야 할 조치를 각각 말하라.
정답/채점 기준: ① 앞은 UTF-8 문자 digits, 뒤는 little-endian fixed integer라는 서로 다른 encoding contract이며 schema 없이는 의미가 확정되지 않는다. ② Reader가 schema·offset metadata와 끝 magic을 찾지 못해 완전한 decode/invariant 검증을 할 수 없다. ③ Object version을 격리하고 bytes·checksum·writer metadata를 보존해 strict offline 재현한다. 확장자만 바꾸거나 원본을 직접 고치거나 오류 row를 drop하면 안 된다. 문제당 3점: 정의 1, 내부 흐름 1, 실패/대응 1. 총 7점 이상이면 통과다.

11. 공식 자료

  • Python 공식 struct 문서 — byte order, size, alignment을 실험할 때 참고한다.
