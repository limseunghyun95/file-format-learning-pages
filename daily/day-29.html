dictionary, RLE, bit packing, delta

논리값을 더 작은 정수·run·차이값으로 바꾸는 byte layout · 예상 학습 60분 + 실습 30분
한 줄 요약
Encoding은 값을 잃지 않으면서 반복, 작은 값 범위, 순서성을 byte layout에 드러내는 변환이며, dictionary·RLE·bit packing·delta는 서로 대체재가 아니라 데이터 분포에 따라 조합되는 도구다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의
Logical value사용자가 보는 값이다. 예: 문자열 "KR", 정수 1003. 파일에는 이 의미가 아니라 이를 표현한 bytes가 저장된다.
Encoding논리값을 복원 가능한 다른 표현으로 바꾸는 규칙. 값의 반복·범위·순서를 이용해 bytes와 decode 비용을 줄인다.
Compressionencoding된 byte stream을 다시 압축하는 단계다. Encoding은 값의 구조를 알고, codec은 대개 byte 패턴을 본다는 차이가 있다.
Cardinality전체 행 수에 비해 서로 다른 값의 수가 얼마나 많은지다. 1억 행의 국가 코드 200개는 low-cardinality다.
Dictionary중복 값을 사전에서 한 번만 저장하고 각 행은 작은 ID를 저장한다. [KR,US,KR] → 사전 [KR,US] + ID [0,1,0].
RLERun-Length Encoding. 같은 값이 연속된 구간(run)을 (값, 반복 횟수)로 기록한다.
Bit packing정수를 고정 32/64비트 대신 실제 범위에 필요한 최소 bit 폭으로 이어 붙인다. 0~7은 3비트면 충분하다.
Delta현재 값 대신 이전 값과의 차이를 저장한다. 증가하는 ID·timestamp처럼 인접 차이가 작을 때 효과적이다.
Page / Column chunkPage는 encoding·compression의 작은 실행 단위이고, 같은 column의 pages가 row group 안에서 column chunk를 이룬다.

2. 왜 중요한가

같은 logical values라도 분포와 순서에 따라 저장 bytes와 scan CPU가 크게 달라진다. Encoding이 잘 맞으면 storage·network·cache miss를 줄이고, 더 많은 값을 한 CPU cache line에 담아 vectorized scan을 돕는다. 반대로 high-cardinality 문자열에 dictionary를 강제하면 dictionary page와 ID stream을 모두 읽으면서도 이득이 사라진다.

핵심 불변식: decode(encode(values))는 원래 values와 정확히 같아야 한다. Writer가 특정 encoding을 기록했다면 reader는 page metadata의 encoding enum을 따라야 하며, 추측으로 다른 decoder를 선택하면 안 된다.

  1. Writer가 상태를 소유한다. Column page 표본에서 distinct 수, 평균 run 길이, min/max, 인접 delta를 관찰하고 지원 가능한 encoding을 고른다.
  2. Dictionary: dictionary page에 고유값을 PLAIN으로 저장하고 data page에는 dictionary ID를 RLE/bit-packing hybrid로 저장한다. Dictionary가 커지면 writer는 이후 page를 PLAIN으로 fallback할 수 있다.
  3. RLE와 bit packing: 긴 반복은 RLE run, 짧고 범위가 작은 정수는 packed run이 유리하다. Parquet의 RLE hybrid는 두 run을 한 stream에서 섞는다.
  4. Delta: 첫 값을 기록한 뒤 차이들의 최소값과 miniblock bit width를 기록한다. 일정한 증가라면 상대 delta가 0이 되어 아주 작아진다.
  5. Reader가 성공을 확정한다. Page를 decompress하고 metadata에 선언된 decoder로 value count만큼 복원해 logical type을 적용했을 때 해당 batch가 사용 가능해진다.

4. CS 내부 동작

Dictionary: 문자열 비교를 작은 정수로

고유값 수를 D라 하면 ID 폭은 대략 ceil(log2(D)) bits다. 8개 값이면 3 bits, 256개면 8 bits다. 하지만 dictionary 자체의 bytes, offsets, hash table 구축, cache miss도 비용이다. Page 경계를 넘는 사전의 소유 범위를 reader가 혼동하면 다른 값으로 복원되는 치명적 corruption이 된다.

RLE와 bit packing: branch 대 density

RLE는 run 하나를 읽고 같은 값을 batch에 채우므로 긴 반복에 강하다. Bit packing은 word 단위 shift·mask 또는 SIMD 연산으로 여러 정수를 풀어내며 random-like한 작은 값에 강하다. Run이 짧으면 RLE header overhead와 branch가 늘고, bit width가 커지면 packing 이득이 줄어든다.

Delta: absolute magnitude가 아니라 변화량

[1,000,000, 1,000,001, 1,000,002]는 원값은 크지만 delta가 [1,1]이라 작다. 정렬이 깨져 큰 jump가 많으면 bit width가 커진다. Parquet의 DELTA_BINARY_PACKED는 block 안의 최소 delta를 빼고 miniblock별 bit width로 상대 delta를 pack한다.

Encoding과 compression의 경계

Data path는 logical values → encode → page bytes → compress 순서다. Reader는 반대로 range read → decompress → decode한다. Encoding은 값의 type·분포를 활용하고, Snappy·ZSTD 같은 codec은 결과 bytes의 반복 패턴을 활용한다. 둘의 효과는 독립적이지 않으므로 최종 파일과 실제 query로 함께 측정해야 한다.

정렬되어 긴 반복RLE평균 run 길이가 핵심이다. 같은 cardinality라도 섞인 순서는 불리하다.
작은 정수 범위Bit packing최대값이 bit width를 결정한다. 드문 큰 outlier가 page 전체 폭을 키울 수 있다.
증가 ID·timestampDelta + packing인접 차이가 작고 안정적일수록 좋다. 정렬 비용과 query pruning 효과도 함께 본다.
  • Best practice: dataset 전체 평균이 아니라 page/column chunk 단위 분포를 측정하고, bytes/value·decode rows/s·CPU cycles·peak memory를 함께 기록한다.
  • Anti-pattern: “문자열이면 dictionary”처럼 type만 보고 강제한다. UUID·고유 URL은 dictionary가 원본보다 커질 수 있다.
  • Edge case: null은 value stream과 별도의 definition/present stream으로 표현될 수 있다. Null 수와 value count를 혼동하면 decode 위치가 밀린다.
  • Version/engine 차이: Parquet의 독립 BIT_PACKED enum은 deprecated이며, 현재의 dictionary IDs와 levels는 RLE/bit-packing hybrid 문맥을 구분해야 한다. DELTA_* 또는 새 encoding은 reader 지원표를 확인한다.
  • Format 차이: ORC도 dictionary/direct 선택과 RLE를 사용하지만 stream 구조와 RLE 버전이 Parquet과 다르다. 이름이 같다고 byte layout이 호환되는 것은 아니다.

7. 30분 실습: 분포가 encoding 선택을 뒤집는 순간

사전 조건: Python 3 표준 라이브러리만 필요하다. 아래 계산은 Parquet 파일 writer가 아니라 각 encoding의 선택 신호와 대략적 payload bits를 비교하는 재현 모델이다.

먼저 예측: (1) 반복된 country는 dictionary와 RLE이 작다. (2) 섞인 0~7은 RLE보다 3-bit packing이 낫다. (3) 증가 ID는 delta 폭이 작다. (4) 고유 문자열은 dictionary overhead가 plain보다 커진다.

python3 - <<'PY' import math def bits_needed(max_value): return max(1, max_value.bit_length()) def dictionary_cost(values): dictionary = list(dict.fromkeys(values)) ids = {v: i for i, v in enumerate(dictionary)} width = bits_needed(len(dictionary) - 1) payload = sum(len(v.encode()) * 8 for v in dictionary) return payload + len(values) * width, len(dictionary), width def rle_cost(values): runs = 1 + sum(a != b for a, b in zip(values, values[1:])) width = bits_needed(max(values)) return runs * (8 + width), runs def packed_cost(values): width = bits_needed(max(values)) return len(values) * width, width def delta_cost(values): deltas = [b - a for a, b in zip(values, values[1:])] shifted = [d - min(deltas) for d in deltas] width = bits_needed(max(shifted, default=0)) return 64 + len(shifted) * width, width country = ["KR"] * 32 + ["US"] * 16 mixed = [i % 8 for i in range(48)] ids = [1_000_000 + i for i in range(48)] unique = [f"user-{i:03d}" for i in range(48)] print("country_dictionary(bits, distinct, id_width)=", dictionary_cost(country)) print("sorted_country_id_rle(bits, runs)=", rle_cost([0] * 32 + [1] * 16)) print("mixed_rle(bits, runs)=", rle_cost(mixed)) print("mixed_pack(bits, width)=", packed_cost(mixed)) print("ids_delta(bits, width)=", delta_cost(ids)) dict_bits, distinct, width = dictionary_cost(unique) plain_bits = sum(len(v.encode()) * 8 for v in unique) print("failure_high_cardinality=", {"plain": plain_bits, "dictionary": dict_bits}) assert dict_bits > plain_bits print("SAFE_FALLBACK: choose plain/auto, preserve original") PY

예상 관찰: country dictionary는 distinct 2와 1-bit ID, 정렬된 ID는 run 2개다. Mixed 값은 run 48개라 RLE가 불리하지만 packing은 3 bits/value다. 연속 ID의 relative delta는 0이라 폭이 최소다. 고유 문자열의 dictionary는 ID stream만큼 plain보다 커진다.

실패 주입: 마지막 unique 데이터가 high-cardinality 강제 dictionary 상황이다. Assertion은 비효율을 검출하고 PLAIN/auto fallback을 선택하게 한다.

자주 나는 오류와 해결: 음수 delta에 단순 bit_length를 쓰지 말고 minimum delta나 zigzag 규칙을 적용한다. 이 실습의 bits는 header·alignment를 단순화한 모델이므로 실제 파일 크기로 오해하지 않는다.

Cleanup: heredoc은 파일을 만들지 않으므로 삭제할 것이 없다. 파일로 저장했다면 본인이 만든 실습 파일만 제거한다.

8. 놓치기 쉬운 함정

  • Dictionary와 compression을 같은 말로 부르지 않는다. Dictionary ID stream도 다시 codec 압축될 수 있다.
  • Cardinality만 보지 않는다. RLE는 값 종류보다 연속 run 길이, delta는 전체 범위보다 인접 차이가 중요하다.
  • 독립 BIT_PACKED enum과 RLE hybrid 안의 bit-packed run을 구분한다.
  • Writer가 page 중간에 임의로 decoder contract를 바꾸지 않도록 page metadata와 fallback 경계를 검증한다.
  • 압축률이 좋아도 decode CPU·temporary buffer·cache behavior가 나쁘면 query 비용은 커질 수 있다.

9. 대기업 기술 면접 질문

Q1. 10억 행의 country_code와 UUID column에 encoding을 각각 설계하라.
좋은 답변 구조: distinct ratio·평균 길이·정렬성 가정 → country dictionary와 ID RLE/packing → UUID의 plain/direct 후보 → page 단위 fallback → bytes/value·decode throughput·memory 측정 → 호환 reader 확인.

Q2. Dictionary를 켰는데 파일이 커졌다. 원인과 안전한 변경 절차는?
좋은 답변 구조: 증상 수치화 → dictionary page와 ID overhead → cardinality·page size·fallback 가설 → representative A/B rewrite → logical equality 검증 → 새 경로 publish와 metadata 전환 → 이전 snapshot rollback.

Q3. RLE, bit packing, delta 중 하나만 고르라는 요구를 어떻게 반박할 것인가?
좋은 답변 구조: 세 방식의 데이터 가정 → column/page마다 분포가 다름 → hybrid와 adaptive 선택의 내부 흐름 → branch·SIMD·cache·I/O trade-off → engine 지원 한계 → 실제 workload benchmark로 결정.
