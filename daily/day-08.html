FILE FORMAT · WEEK 2 / DAY 08

delimiter, quote, escape, multiline CSV

쉼표 분할에서 streaming state machine까지 · 예상 학습 45분 + 실습 30분
한 줄 요약
CSV는 “한 줄을 쉼표로 split”하는 형식이 아니라 quote 안의 delimiter·quote·newline을 구분하는 상태 머신 문법이며, dialect와 schema·오류 정책을 명시하지 않으면 parser 성공조차 데이터 정합성을 보장하지 않는다.

1. 선수 용어 사전

용어쉬운 설명과 정확한 정의
DelimiterField 사이 경계를 나타내는 문자다. Comma가 흔하지만 tab, semicolon, pipe도 사용되므로 “CSV=항상 comma”는 아니다.
Quote characterField를 감싸 그 안의 delimiter와 newline을 일반 data로 취급하게 하는 문자다. 보통 double quote(")다.
Escape문법 문자 자체를 data로 표현하는 규칙이다. CSV dialect에 따라 quote를 두 번 쓰는 "" 또는 별도 escape character를 쓴다.
RecordSchema의 한 row에 해당하는 field sequence다. Quoted field 안에 newline이 있으면 물리적인 여러 줄이 하나의 logical record다.
Physical line파일에서 newline byte로 끝나는 문자 구간이다. CSV record와 항상 1:1이 아니다.
DialectDelimiter, quote, escape, double-quote 방식, newline, header 유무 등을 묶은 CSV 문법 계약이다.
Finite State Machine현재 상태와 다음 문자에 따라 동작·다음 상태가 결정되는 계산 모델이다. CSV parser는 quote 안/밖을 상태로 기억한다.
Tokenization문자 stream을 field, delimiter, record terminator 같은 의미 단위로 나누는 과정이다.
Strict parser닫히지 않은 quote, 잘못된 escape, 예상 밖 field 수를 자동 보정하지 않고 명시적으로 실패시키는 parser mode다.
QuarantineMalformed input을 삭제하지 않고 원본 bytes·offset·오류 이유와 함께 정상 경로에서 격리하는 절차다.

2. 왜 중요한가

1,"Seoul, KR","line1↵line2"에서 첫 comma는 field boundary지만 quote 안의 comma는 data이고, quote 안 newline도 record 끝이 아니다. line.split(',')와 file.splitlines()는 이 문맥을 기억하지 못해 column shift와 row count 오류를 만든다.

가장 위험한 장애는 parser exception이 아니라 성공처럼 보이는 오해석이다. 예를 들어 quote 설정이 틀리면 amount가 다음 column으로 밀려도 모든 값이 string이라 parse될 수 있다. 이후 aggregation·join·billing이 틀어지고 원본 offset을 보존하지 않았다면 재처리도 어렵다.

면접 기준: CSV의 단순함을 “사람이 읽기 쉽다”로 끝내지 말고, state machine, multiline parallelism, schema/type conversion, failure resynchronization, 보안·운영 비용까지 설명해야 한다.

3. 아키텍처 그림과 요청 흐름

① Raw bytes
UTF-8 · BOM · CRLF/LF · checksum
↓ incremental character decode
② CSV state machine
delimiter · quote · escape · multiline
↓ logical records + raw offsets
③ Shape validation
header · field count · max record/field size
↓ strings + declared schema
④ Type & semantic conversion
integer · decimal · timestamp · null · range
↓ valid rows / reject evidence
⑤ Sink + checkpoint
idempotent write · metrics · commit
  1. Byte layer: Reader는 encoding과 newline convention을 적용해 characters를 만든다. Multi-byte UTF-8 문자를 buffer 중간에서 자르지 않도록 incremental decoder가 상태를 가진다.
  2. Grammar layer: CSV state machine은 현재 quote 안인지 기억한다. Delimiter와 newline의 의미는 현재 상태에 따라 달라진다.
  3. Shape layer: Header와 expected field count, record/field 최대 크기를 검사한다. 문법상 유효해도 column 수가 다르면 계약 위반이다.
  4. Schema layer: 모든 CSV field는 처음에는 문자 sequence다. Decimal scale·timestamp timezone·null marker는 외부 schema와 명시적 변환 규칙이 결정한다.
  5. Commit layer: Valid rows의 sink write와 rejects 기록이 완료된 뒤 source checkpoint를 commit한다. Reject를 버리고 성공 처리하면 silent loss다.

Data path와 control path

Data pathRaw bytes → decoded chars → fields → typed values → sink rows.
Control pathDialect version, encoding, schema, file identity, limits, reject policy, checkpoint와 metrics.
핵심 불변식입력의 각 logical record는 정확히 valid 또는 quarantined 하나로 귀속되고, input_records = accepted + rejected가 성립한다.
성공 시점전체 file의 quote state가 정상 종료되고 shape/schema/invariant와 sink/reject write가 성공한 뒤 checkpoint가 확정될 때다.

4. CS 내부 동작: CSV parser는 상태 머신이다

4.1 핵심 상태와 전이

현재 상태입력 문자동작 → 다음 상태
START_FIELDquoteField 시작, quote는 data에 넣지 않음 → IN_QUOTED
START_FIELDdelimiter빈 field 확정 → START_FIELD
START_FIELD일반 문자문자를 buffer에 추가 → IN_UNQUOTED
IN_UNQUOTEDdelimiter / newlineField / record 확정 → START_FIELD
IN_QUOTEDdelimiter / newline일반 data로 buffer에 추가 → IN_QUOTED 유지
IN_QUOTEDquote닫는 quote 후보 → AFTER_QUOTE
AFTER_QUOTEquoteEscaped quote 하나를 data에 추가 → IN_QUOTED
AFTER_QUOTEdelimiter / newlineField / record 확정 → START_FIELD
AFTER_QUOTE그 외Strict mode에서는 malformed record로 거부

Parser는 입력 문자 수 n에 대해 보통 O(n) 시간에 동작하지만, quote·escape·delimiter마다 branch가 있고 variable-length field buffer를 관리한다. Memory는 전체 파일이 아니라 보통 최대 record/field 크기에 비례하도록 streaming할 수 있다. 따라서 최대 크기 제한이 없으면 하나의 거대한 quoted field가 memory exhaustion을 일으킬 수 있다.

4.2 Multiline이 병렬 split을 어렵게 하는 이유

Columnar file은 metadata가 split 위치를 제공하지만 CSV newline은 quote 밖일 때만 record boundary다. 임의 byte offset에서 시작한 worker는 자신이 quote 안인지 밖인지 모른다. 앞에서부터 quote parity를 계산하거나 safe boundary index를 먼저 만들고, dialect의 doublequote/escape 규칙까지 고려해야 한다.

단순히 N등분 후 다음 newline부터 읽으면 quoted multiline record 중간에서 시작할 수 있다. 일부 고성능 parser는 block별 quote mask를 SIMD로 계산해 prefix state를 합성하지만, 이는 splitlines()보다 훨씬 복잡하다. 작은 파일 다수는 이런 pre-scan·open·task scheduling 비용까지 더해진다.

4.3 Encoding과 newline은 grammar 전에 처리한다

CSV grammar는 characters를 대상으로 하지만 storage에는 bytes가 있다. Reader는 BOM과 UTF-8/UTF-16을 판별·계약하고 multi-byte sequence를 정확히 decode해야 한다. CRLF(0d 0a)와 LF(0a) 차이는 quoted field 안/밖 상태와 함께 처리한다. Text mode가 newline을 자동 변환할 수 있으므로 language library의 권장 file-open mode를 따른다.

4.4 Shape와 type은 별도 단계다

CSV parser가 ["001", "", "2026-08-08"]을 만들었다고 integer·null·date 의미가 확정된 것은 아니다. 001은 상품 코드일 수 있고, empty string은 값·null·missing column과 다르다. Type inference는 sample에 없던 큰 값, locale decimal, timezone, leading zero에서 실패할 수 있으므로 production은 declared schema와 explicit null marker를 우선한다.

4.5 오류 후 resynchronization은 안전하지 않을 수 있다

닫히지 않은 quote를 만난 parser는 다음 newline이 record 경계인지 알 수 없다. “다음 줄부터 계속”하면 여러 정상 row를 하나의 field로 삼거나 column을 밀 수 있다. 확실한 record framing을 회복할 수 없다면 file 또는 bounded chunk 전체를 quarantine하고 원본 byte offset과 parser state를 보존하는 편이 안전하다.

4.6 Formula injection은 serialization 이후의 위험이다

CSV field가 =, +, -, @로 시작하면 spreadsheet application이 수식으로 실행할 수 있다. CSV 문법상 완전히 유효해도 사람이 Excel/Sheets로 열 때 외부 호출이나 데이터 노출이 생길 수 있다. Export 목적과 소비 도구를 알고, 원본 의미를 훼손하지 않는 별도 안전 표현·경고 정책을 설계한다.

5. 실무 설계 판단

판단Best practice와 이유
Dialect contractEncoding, delimiter, quote, escape/doublequote, line ending, header, null marker를 versioned contract로 고정한다. Sniffer 결과만으로 운영 의미를 결정하지 않는다.
Writer직접 문자열을 이어 붙이지 말고 검증된 CSV library를 사용한다. Newline·quote·delimiter가 있는 field의 quoting을 library에 맡긴다.
Reader명시적 dialect+schema+strict mode로 읽고, expected field count와 최대 record/field bytes를 제한한다.
Multiline허용 여부를 계약에 적는다. 허용하면 physical line count를 row count로 쓰지 않고, parallel split의 safe-boundary 전략을 검증한다.
Reject policy원본 bytes, file/version, byte/record offset, raw field, dialect/schema version, error code를 보존한다. Accepted/rejected 총계를 대조한다.
ObservabilityPhysical lines와 logical records를 분리하고, field-count histogram, quote/escape errors, max record size, reject ratio, type/null conversion을 producer version별로 본다.
Format choice사람·범용 도구 교환에는 CSV가 좋다. Nested data, 강한 schema evolution, 대규모 selective scan에는 Avro/Parquet/ORC 같은 대안을 workload와 함께 검토한다.

Anti-pattern·edge case·engine 차이

  • split(',') 사용: Quoted delimiter·escaped quote·multiline을 처리하지 못한다.
  • 한 physical line=한 row: Multiline field에서 row count, parallel split, reject offset이 모두 틀어진다.
  • Auto-detect 결과를 contract로 저장: Sample에 따라 delimiter/header/type 추론이 달라질 수 있다.
  • Bad row skip만 켜기: Accepted+rejected 총계와 reject sample이 없으면 조용한 손실이다.
  • Header를 이름으로 무조건 신뢰: Duplicate/blank/BOM-prefixed header와 column reorder를 검증한다.
  • Whitespace 자동 trim: ID·고정폭 코드·사용자 입력의 의미가 바뀔 수 있다. Field별 정책으로 둔다.
  • Parser portability 가정: Quote/escape strictness, duplicate header, invalid UTF-8, trailing delimiter, empty line 처리는 Python·DuckDB·Spark 등 engine/version마다 다를 수 있다.

6. 장애 대응

증상Row count 급감/증가, 특정 row 이후 column shift, unexpected end of data, quote error, field 수 분산 증가, multiline text가 여러 row로 분리, amount/date 변환 실패, engine별 결과 불일치.
먼저 수집할 증거/지표원본 file version·checksum, 앞/문제/뒤 byte hex, encoding/BOM/newline, declared·effective dialect/schema, writer/reader version·strictness, physical line/logical record/accepted/rejected count, field-count histogram, 첫 실패 byte/record offset과 parser state.
가능한 가설Unescaped delimiter/newline, unclosed/doubled quote 오류, dialect drift, wrong encoding/BOM, CRLF 처리 차이, header reorder/duplicate, truncated upload, max field limit, auto-detect sample 오류, permissive parser의 silent skip.
안전한 첫 조치해당 producer/file version을 격리하고 checkpoint를 멈춘다. 원본을 보존해 명시적 dialect+strict parser로 offline 재현하고 첫 실패 전후 bytes와 정상 file을 비교한다.
Rollback / 복구Last-known-good writer/dialect로 rollback한다. Correct library writer로 새 immutable file을 생성·검증하고, accepted+rejected=count와 downstream count/sum을 대조한 뒤 idempotent replay·checkpoint한다.
하지 말아야 할 조치문제 comma/quote를 수동 삭제, arbitrary newline에서 resume, 원본 덮어쓰기, strictness 해제, bad rows 무기록 skip, 모든 empty를 null 처리, auto-detect 재시도로 우연히 성공시키기, 실패 batch checkpoint commit을 하지 않는다.

7. 30분 실습: naïve split과 state-machine parser 비교

목표: Delimiter·quote·escaped quote·multiline을 가진 CSV를 생성해 물리 line과 logical record가 다른 것을 확인하고, unclosed quote 실패를 strict parser로 재현한다. 먼저 naïve parser가 몇 rows/fields를 만들지 예측한다.

사전 조건: Python 3 표준 library만 필요하다. 정확한 임시 경로 /tmp/file-format-day08만 사용한다.

7.1 올바른 writer로 tricky CSV 생성

mkdir -p /tmp/file-format-day08 cd /tmp/file-format-day08 python3 - <<'PY' import csv rows = [ ["id", "name", "note"], ["1", "Alice", "hello, world"], ["2", "Bob", 'He said "hi"'], ["3", "Carol", "line1\nline2"], ["4", "Dana", ""], ] with open("tricky.csv", "w", encoding="utf-8", newline="") as f: w = csv.writer(f, delimiter=",", quotechar='"', doublequote=True, lineterminator="\r\n") w.writerows(rows) print("logical rows written:", len(rows)) PY xxd -g 1 -l 240 tricky.csv nl -ba tricky.csv

예상 관찰: hello, world는 quote로 감싸지고 내부 quote는 ""로 표현된다. Carol의 note 때문에 logical 1 record가 두 physical lines에 걸친다. nl의 line 수와 CSV record 수가 다르다.

7.2 naïve split 실패와 표준 parser 성공

python3 - <<'PY' import csv from pathlib import Path p = Path("tricky.csv") naive = [line.split(",") for line in p.read_text(encoding="utf-8").splitlines()] print("naive physical rows:", len(naive)) for i, row in enumerate(naive, 1): print("naive", i, "fields=", len(row), row) with p.open("r", encoding="utf-8", newline="") as f: parsed = list(csv.reader(f, delimiter=",", quotechar='"', doublequote=True, strict=True)) print("strict logical rows:", len(parsed)) for i, row in enumerate(parsed, 1): print("strict", i, "fields=", len(row), row) assert all(len(row) == 3 for row in parsed) PY

예상: Naïve 결과는 quoted comma에서 field 수가 늘고 multiline에서 row가 갈라진다. 표준 parser는 5 logical rows와 각 3 fields를 복원한다. Python에서 CSV file은 newline=""로 여는 권장 방식을 따른다.

7.3 실패 주입: 닫히지 않은 quote

python3 - <<'PY' from pathlib import Path Path("malformed.csv").write_bytes( b'id,note\r\n1,"unterminated\r\n2,looks-valid\r\n' ) PY python3 - <<'PY' import csv try: with open("malformed.csv", "r", encoding="utf-8", newline="") as f: for record_no, row in enumerate(csv.reader(f, strict=True), 1): print(record_no, row) except csv.Error as e: print("QUARANTINE:", type(e).__name__, str(e)) PY

예상: Header 뒤 quote가 EOF까지 닫히지 않아 strict reader가 거부한다. Physical line 2,looks-valid에서 임의 재시작하면 그것이 quoted field 내부인지 새 record인지 확증할 수 없으므로 파일 전체를 원본과 함께 quarantine한다.

7.4 실패 정책 기록

다음 필드를 가진 reject record를 종이에 설계한다: source_uri, object_version, checksum, byte_offset, logical_record_no, physical_line_range, dialect_version, schema_version, parser_state, error_code, raw_bytes_reference, retry_count. 경계를 확증할 수 없으면 record가 아니라 file/chunk 단위 reject임을 표시한다.

자주 나는 오류와 해결: Shell에서 quote가 깨지면 heredoc 경계를 그대로 사용한다. Windows editor가 CRLF를 바꿔도 CSV library는 계약에 따라 처리하지만 hex 결과는 달라질 수 있다. strict=True 지원·동작은 library마다 다르므로 운영 engine의 실제 옵션과 golden files로 재검증한다.

8. 놓치기 쉬운 함정

  • Quoted field는 모두 string: Quoting은 grammar 경계를 보호할 뿐 type을 지정하지 않는다.
  • Backslash가 보편 escape: RFC 계열 CSV는 doubled quote를 흔히 쓰며 dialect마다 다르다.
  • Line number=record number: Multiline 때문에 source 위치를 둘 다 기록해야 한다.
  • Trailing delimiter 무시: 마지막 empty field일 수 있다. Expected field count로 판단한다.
  • Empty line과 empty record 혼동: Engine option에 따라 skip되거나 1개 empty field로 해석될 수 있다.
  • UTF-8 decode error replace: 대체 문자로 조용히 진행하면 식별자·delimiter 인접 byte가 변할 수 있다.
  • Excel에서 안전: 문법상 정상인 field도 formula injection 위험이 있으므로 export 소비 맥락을 고려한다.

  3. 확장자-content 불일치 사고의 안전한 첫 조치와 금지 조치를 말하라.
짧은 정답: ① 선언 → signature → 구조 decode → contract identity → domain meaning 순서다. ② Immutable version/ETag/checksum을 manifest에 고정하고 consumer도 같은 identity를 확인한다. ③ Producer/file version을 격리하고 checkpoint를 멈춰 원본 증거를 보존한다. Rename·overwrite·silent drop은 금지한다.

오늘 내용 확인 3문제

  1. Quoted multiline CSV를 newline 기준으로 병렬 분할하면 왜 잘못될 수 있는가?
  2. State machine의 IN_QUOTED와 AFTER_QUOTE에서 delimiter·quote의 의미가 어떻게 다른가?
  3. Unclosed quote 뒤 다음 physical line부터 재시작하면 안 되는 이유와 안전한 복구를 말하라.
정답/채점 기준: ① Newline은 quote 밖일 때만 record boundary이며 임의 split worker는 시작 quote state를 모른다. ② IN_QUOTED의 delimiter/newline은 data이고 quote는 닫기 후보다. AFTER_QUOTE의 두 번째 quote는 escaped quote, delimiter/newline은 field/record 종료다. ③ Record boundary를 확증할 수 없어 column shift·silent loss가 생기므로 원본 file/chunk를 quarantine하고 correct dialect/writer로 새 version을 재생성·idempotent replay한다. 문제당 3점: 문법 1, 내부 상태 1, 장애/복구 1. 총 7점 이상 통과.

11. 공식 자료

  • RFC Editor — RFC 4180 — common CSV format과 text/csv 등록의 기준을 확인한다.
  • Python 공식 csv 문서 — dialect, quoting, strict parsing과 newline="" 사용법을 확인한다.
  • DuckDB 공식 CSV Import 문서 — sniffing, explicit options, faulty CSV와 engine 동작을 확인한다.
  • W3C Tabular Data Model — CSV 문법과 tabular metadata/model의 경계를 확인한다.

RFC 4180은 informational 문서이며 현실의 모든 dialect를 단일 표준으로 만들지 않는다. 실제 producer와 reader의 versioned dialect 계약과 golden files가 최종 기준이다.
