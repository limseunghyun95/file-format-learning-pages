FILE FORMAT · WEEK 1 / DAY 02

UTF-8, newline, BOM, endian 기초

텍스트 byte 계약과 streaming decode · 예상 학습 35분 + 실습 30분

한 줄 요약
디스크의 “텍스트”는 문자가 아니라 byte다. UTF-8은 문자를, newline은 record 경계를, endian은 multi-byte 수의 byte 순서를 정한다. BOM은 UTF-8의 byte 순서를 정하지 않으며, 이 네 계약을 경계에서 명시해야 조용한 데이터 손상을 막을 수 있다.

1. 선수 용어 사전

Code pointUnicode가 문자에 부여한 추상 번호다. 예: A는 U+0041. 화면의 글자 하나가 code point 여러 개로 구성될 수도 있다.
Code unit문자 encoding이 처리하는 고정 크기 단위다. UTF-8은 8bit code unit, UTF-16은 16bit code unit을 사용한다.
Octet / Byte정확히 8bit인 저장·전송 단위다. 오늘 문맥에서는 byte와 같은 뜻으로 쓴다.
UTF-8Unicode code point를 1~4byte로 바꾸는 가변 길이 encoding이다. ASCII 범위는 같은 1byte 값을 사용한다.
Newline줄 끝을 표현하는 byte convention. LF는 0A, CR은 0D, CRLF는 두 byte 0D 0A다.
BOMByte Order Mark. UTF-16/32에서는 byte 순서를 알리는 표식으로 쓸 수 있다. UTF-8의 EF BB BF는 순서가 아닌 “UTF-8 서명” 역할만 한다.
Endian2byte 이상 값을 byte로 나열하는 순서. Big-endian은 가장 큰 자리(MSB)를 먼저, little-endian은 가장 작은 자리(LSB)를 먼저 둔다.
Framing연속 byte stream에서 record의 시작과 끝을 알아내는 규칙. newline delimiter, length prefix, page header가 예다.
Streaming decoderchunk 단위로 byte를 받되, 끝에 덜 들어온 multi-byte 문자를 내부 상태에 보관했다가 다음 chunk와 이어 해석하는 decoder다.

2. 왜 중요한가: “텍스트 파일”에도 네 개의 계약이 있다

사람은 승현,42라는 한 줄을 보지만 storage와 network는 byte만 본다. Reader가 같은 결과를 복원하려면 최소한 ① 문자 encoding, ② 줄 경계, ③ 파일 앞 표식 허용 여부, ④ binary field의 endian을 producer와 합의해야 한다. 확장자 .csv나 MIME type은 힌트이지 검증된 계약이 아니다.

핵심 구분: UTF-8은 “문자 → byte” 규칙이고 newline은 “record 경계” 규칙이다. Endian은 “multi-byte 수/code unit → byte 순서” 규칙이다. 서로 다른 계층이므로 하나를 안다고 나머지가 자동으로 결정되지 않는다.

비용 관점: Encoding 오판은 보통 decode 단계에서 빨리 실패하지만, newline·BOM·endian 오판은 parser가 성공한 채 첫 column 이름이 달라지거나 숫자가 엉뚱해지는 silent corruption을 만들 수 있다. 그래서 “오류가 없었다”보다 byte-level 불변식과 데이터 품질 지표가 중요하다.

3. 아키텍처: logical value가 다시 값이 되는 경로

① Logical values
문자열 “승현”, 정수 0x01020304, row 경계
↓ control path: charset · newline · endian 계약
② Encoder + Framer
UTF-8 encode · LF/CRLF 추가 · integer pack
↓ data path: byte stream
③ File / Object / Network
chunk 경계는 문자·line 경계와 무관
↓ read chunks + 검증
④ Stateful Decoder + Line Framer
BOM 정책 · carry byte · newline 상태
↓ parse + schema/data-quality validation
⑤ Consumer values
문자열 “승현”, 정수 0x01020304, 완전한 row
  1. Writer가 의미를 소유한다. Application은 문자열·정수·record를 갖고 있지만 아직 byte layout은 없다.
  2. Control path가 해석 규칙을 전달한다. API option, schema, protocol version, content-type metadata가 charset/newline/endian을 결정한다. 파일 내용인 data path와 혼동하지 않는다.
  3. Encoder와 framer가 byte를 만든다. “승현”은 UTF-8에서 EC 8A B9 ED 98 84 여섯 byte다. 뒤에 LF를 붙이면 0A가 추가된다.
  4. I/O는 임의 크기로 자른다. 4KB buffer, TCP segment, object range는 code point나 line 경계를 보장하지 않는다. 세 byte 문자의 두 번째 byte에서 chunk가 끝날 수 있다.
  5. Reader는 상태를 이어야 한다. Decoder가 incomplete sequence를 carry하고, CR을 본 line framer는 다음 byte가 LF인지 확인한다. 마지막에는 decoder와 framer를 flush해 불완전 입력을 검출한다.
  6. 성공은 parse 이후에 확정한다. Decode 성공만으로 row 의미가 맞았다고 할 수 없다. column 수, header, numeric range, row count와 checksum까지 검증한 뒤 publish한다.

4. CS 내부 동작

4.1 UTF-8: prefix bit가 길이를 말한다

ASCII 영역 U+0000~U+007F는 0xxxxxxx 한 byte다. 더 큰 값은 선두 byte의 bit pattern이 전체 길이를 나타내고, 이어지는 continuation byte는 10xxxxxx 형태다. Decoder는 byte를 모아 code point를 복원하면서 잘못된 continuation, 허용 범위 밖 값, 불필요하게 긴 표현(overlong encoding)을 거부해야 한다.

문자UTF-8 byte관찰
A411byte
승EC 8A B93byte
현ED 98 843byte

불변식: byte offset와 character index는 같지 않다. 따라서 byte로 자른 preview, offset 기반 재시작, 병렬 split은 문자 경계를 다시 찾아야 한다. errors="ignore"로 깨진 byte를 버리면 offset과 checksum이 바뀌고 원인 증거가 사라진다.

4.2 Chunk boundary와 decoder state

EC 8A | B9 ED | 98 84처럼 “승현”의 byte가 나뉘어 도착할 수 있다. 각 chunk를 독립적으로 decode()하면 첫 chunk가 incomplete sequence라 실패한다. Streaming decoder는 EC 8A를 내부 carry로 보관하고 다음 B9를 받아 “승”을 완성한다. EOF에서는 final=true로 flush해 남은 carry가 있으면 truncated input으로 실패시켜야 한다.

상태 소유자: Reader가 아니라 decoder instance가 carry byte와 오류 위치를 소유한다. 병렬 worker끼리 decoder를 공유하면 상태가 섞이고, range read를 임의 offset에서 시작하면 첫 code point를 복구할 경계 탐색 규칙이 필요하다.

4.3 Newline은 문자이면서 framing protocol이다

Unix 계열은 보통 LF, Windows text는 CRLF를 쓴다. Parser가 “줄”을 record로 취급한다면 newline은 data와 control delimiter의 두 역할을 가진다. CSV처럼 quote 안 newline을 허용하는 format에서는 단순 split('\n')이 record를 파괴한다. Line delimiter 인식은 CSV quote state와 함께 동작해야 한다.

  • CRLF는 원자적 두 byte 규칙: chunk가 CR 직후 끝날 수 있으므로 framer가 pending CR 상태를 보관해야 한다.
  • 마지막 줄: EOF 앞에 LF가 없어도 하나의 line으로 인정할지 protocol이 정해야 한다. POSIX text file 관점과 실제 parser 관용성은 다를 수 있다.
  • 빈 줄: LF LF는 empty record인지 무시할 whitespace인지 schema가 결정한다.
  • 정규화: CRLF→LF 변환은 byte checksum과 signature를 바꾼다. 원본을 보존한 뒤 파생본으로 수행해야 audit/replay가 가능하다.

4.4 BOM: UTF-8에는 byte order가 없다

UTF-8 code unit은 1byte이므로 byte 내부의 순서를 바꿀 일이 없다. 따라서 UTF-8 BOM EF BB BF는 endian 표시가 아니라 optional signature다. 일부 도구는 이를 자동 제거하지만, 다른 parser는 첫 header를 \uFEFFid로 읽거나 executable script의 #! 앞을 가로막을 수 있다.

정책: “BOM이면 무조건 지운다”가 아니라 protocol별로 allowed/required/forbidden을 선언한다. 허용할 때도 offset 0의 정확한 세 byte만 처리하며, 데이터 중간의 U+FEFF는 일반 문자일 수 있으므로 제거하지 않는다.

4.5 Endian: 같은 네 byte, 다른 수

값Big-endianLittle-endian
0x0102030401 02 03 0404 03 02 01

Endian은 file format 또는 protocol이 정한다. CPU native endian을 그대로 쓰면 다른 architecture나 language 구현에서 호환성이 깨진다. 예를 들어 Protobuf의 fixed32는 specification에 little-endian으로 정의되어 있다. 반면 network byte order는 관례적으로 big-endian이다. Format field별 계약을 따르고 “network니까 항상 big-endian” 같은 추측을 금지한다.

4.6 Data path, control path, 성공 시점

구분책임과 불변식
Data path실제 byte가 writer→storage/network→reader로 이동한다. 원본 size/checksum과 byte offset을 보존한다.
Control pathcharset, newline, endian, schema/version을 전달한다. metadata와 실제 byte가 일치하는지 reader가 검증한다.
Decode 성공모든 byte가 유효한 character가 됐다는 뜻일 뿐 record와 값은 아직 미검증이다.
Ingest 성공decode·framing·schema·quality 검증 후 결과를 atomic publish하고 재시작 cursor를 commit한 시점이다.

5. 실무 설계 판단

판단권장안과 이유
입력 경계Binary mode로 원본을 받고 size·checksum·앞뒤 hex를 기록한다. Text mode의 자동 newline 변환이 증거를 바꾸지 않게 한다.
CharsetProtocol에 UTF-8을 명시하고 strict decode한다. 외부 legacy 입력은 탐지 결과를 신뢰하지 말고 신뢰도·producer 계약·sample 검증으로 quarantine한다.
BOM입력별 allowed/forbidden 정책과 metric을 둔다. 허용 시 offset 0에서 한 번만 제거하고 원본 checksum은 별도로 보존한다.
NewlineWriter는 하나로 고정한다. Reader의 관용성은 명시하고 mixed newline count를 metric으로 남긴다. CSV는 format-aware parser를 사용한다.
Endian각 numeric field의 width·signedness·endian을 schema에 고정한다. Golden byte fixture로 language 간 round-trip을 CI에서 검증한다.
StreamingStateful incremental decoder를 connection/file마다 하나씩 둔다. EOF flush, max line length, malformed byte budget을 설정한다.
Publish원본→검증된 staging→atomic pointer/rename 순으로 전환한다. 실패 시 consumer가 부분 변환본을 보지 않게 한다.

Version·engine 차이를 다루는 법

Language runtime은 text mode, newline normalization, 기본 charset, replacement policy가 다르다. 같은 runtime도 OS에 따라 기본값이 달라질 수 있다. “우리 서버에서 됐다”가 아니라 explicit option + golden byte fixture + cross-language test로 계약을 고정한다. Standard가 허용해도 target engine이 BOM·마지막 newline·quoted multiline을 지원하는지는 실제 지원 matrix와 integration test로 확인한다.

6. 장애 대응

증상첫 header가 id와 매칭되지 않음, 한글 decode error, row 수 급증/감소, chunk 크기에 따라 간헐 실패, 정수 값이 비정상적으로 큼.
먼저 수집할 증거/지표원본 checksum·size, 첫 16/마지막 16byte hex, 실패 byte offset과 주변 byte, chunk size, BOM 유무, LF/CRLF/CR 개수, 마지막 newline, producer/runtime/version, numeric field raw byte와 schema.
가능한 가설UTF-8 BOM이 header에 남음, 실제 charset 불일치, multi-byte 중간에서 stateless decode, CRLF를 두 line으로 계산, quoted newline을 단순 split, EOF truncation, signedness/width/endian 불일치.
안전한 첫 조치해당 object와 downstream publish를 격리하고 원본을 immutable 보존한다. 한 sample을 strict decoder와 hex로 재현하고, BOM/newline/endian 계약을 producer metadata와 대조한다.
Rollback / 복구마지막 검증된 manifest/pointer로 rollback한다. 수정한 explicit option으로 원본에서 새 output을 idempotent 재생성하고 checksum·row count·range를 검증한 뒤 atomic publish한다.
하지 말아야 할 조치errors="ignore"로 byte 삭제, 운영 원본 직접 수정, 모든 CR/LF 무차별 치환, 숫자가 그럴듯해 보일 때 endian 추측, 증거 없이 전체 backfill, 실패 cursor를 성공으로 commit하지 않는다.

7. 30분 실습: byte를 직접 보고 경계 실패 주입하기

목표: 같은 logical text가 BOM/newline에 따라 다른 byte가 되고, multi-byte 경계에서 stateless decode가 실패하며, endian을 잘못 읽으면 값이 달라짐을 재현한다.

사전 조건: Python 3가 설치된 shell. 아래 명령은 /tmp/file-format-day02만 사용한다. 실행 전 결과를 먼저 종이에 예측한다.

mkdir -p /tmp/file-format-day02 cd /tmp/file-format-day02 python3 -c "from pathlib import Path; Path('lf.txt').write_bytes('id,name\n1,승현\n'.encode('utf-8')); Path('crlf-bom.txt').write_bytes(b'\xef\xbb\xbf' + 'id,name\r\n1,승현\r\n'.encode('utf-8'))" od -An -tx1 -c lf.txt od -An -tx1 -c crlf-bom.txt python3 -c "from pathlib import Path; b=Path('lf.txt').read_bytes(); print('bytes=',len(b),'LF=',b.count(b'\n'),'CR=',b.count(b'\r'))" python3 -c "from pathlib import Path; b=Path('crlf-bom.txt').read_bytes(); print('bytes=',len(b),'BOM=',b.startswith(b'\xef\xbb\xbf'),'LF=',b.count(b'\n'),'CR=',b.count(b'\r'))"

예상 관찰: 두 파일은 화면의 행이 같지만 두 번째는 앞에 EF BB BF가 있고 각 줄마다 0D 0A가 있다. “승현”은 여섯 byte다. 따라서 character 수와 file size는 같지 않다.

실패 주입 A: multi-byte 문자 중간 절단

python3 -c "b='승'.encode(); print(b.hex()); print(b[:2].decode('utf-8'))" python3 -c "import codecs; b='승현'.encode(); d=codecs.getincrementaldecoder('utf-8')('strict'); print(repr(d.decode(b[:2],False))); print(repr(d.decode(b[2:4],False))); print(repr(d.decode(b[4:],True)))"

예상: 첫 명령은 UnicodeDecodeError를 낸다. 두 번째는 decoder가 앞 두 byte를 보관해 최종적으로 “승”, “현”을 순서대로 복원한다. 출력이 chunk마다 꼭 한 글자일 것이라고 가정하지 말고 합친 결과와 final flush를 검증한다.

실패 주입 B: endian 뒤집기

python3 -c "import struct; v=0x01020304; le=struct.pack('<I',v); be=struct.pack('>I',v); print('LE',le.hex(),'BE',be.hex()); print('wrong',struct.unpack('>I',le)[0],'right',struct.unpack('<I',le)[0])"

예상: LE는 04030201, BE는 01020304다. LE byte를 BE로 읽으면 16,909,060이 아니라 67,305,985가 된다. Parser는 오류 없이 잘못된 수를 반환하므로 range validation이 필요하다.

자주 나는 오류와 해결

  • od가 없으면 xxd -g 1 파일명을 사용한다.
  • Shell에서 <, >는 redirection 문자다. 위 HTML의 escape가 보일 경우 실제 명령에는 각각 단일 기호를 입력한다.
  • 첫 실패 명령의 non-zero exit는 의도한 관찰이다. 이를 파일 생성 실패로 오해하지 않는다.
  • Editor로 저장하면 BOM/newline이 자동 변환될 수 있으므로 실험 파일은 byte API로 다시 만든다.

Cleanup: 실습 결과를 확인한 후 정확한 경로만 삭제한다.

rm -rf /tmp/file-format-day02

8. 놓치기 쉬운 함정

  • 기본 charset 의존: 개발 laptop과 production container의 locale이 달라 같은 코드가 다른 byte를 만든다.
  • UTF-8 BOM을 endian 탐지로 오해: UTF-8에는 바꿀 byte 순서가 없다. BOM은 signature일 뿐이며 허용 여부는 protocol 정책이다.
  • splitlines()의 관용성을 계약으로 착각: Library가 여러 line ending을 받아도 원본이 규격을 지켰다는 뜻은 아니다. mixed newline metric을 남긴다.
  • Text mode checksum: 읽는 과정의 newline 변환 뒤 checksum을 계산하면 원본 object checksum과 비교할 수 없다.
  • Character 단위 offset 저장: 재시작 cursor가 byte offset인지 decoded character offset인지 명시하지 않으면 seek가 multi-byte 중간에 들어간다.
  • 무제한 line buffer: newline이 없는 corrupt file 하나가 memory를 고갈시킨다. max record/line size와 quarantine이 필요하다.
  • 전체 파일 encoding 탐지: 통계적 탐지는 정답 보장이 아니다. 짧은 ASCII-only sample은 여러 encoding과 동시에 호환된다.
  • Endian만 확인: width와 signedness도 계약이다. 같은 byte를 32-bit signed/unsigned 또는 64-bit로 보면 값이 달라진다.

9. 대기업 기술 면접 질문

Q1. 8GB UTF-8 로그를 16개 worker로 병렬 처리할 때 split 경계를 어떻게 잡겠습니까?

좋은 답변 구조: 요구사항(한 line=record인지, quoted newline 허용 여부, 정확히 한 번 처리) → 평균/최대 line 크기와 object range read 비용 가정 → byte range를 나누되 각 worker가 시작 offset 이후 첫 유효 newline까지 버리고 끝은 다음 newline까지 확장 → UTF-8 incremental decode와 CRLF state → record ID/offset으로 dedupe → oversized line·truncated EOF quarantine → splittable container format 전환 대안과 비용까지 설명한다.

Q2. 특정 협력사 CSV에서만 첫 column이 누락됩니다. 어떻게 진단하고 복구합니까?

좋은 답변 구조: 장애 범위와 최근 producer 변경 확인 → 원본 checksum, 첫 16byte, header의 Unicode code point, parser 옵션 수집 → UTF-8 BOM이 \uFEFFid로 남았다는 가설과 대안 가설 비교 → 원본 immutable 보존·해당 batch 격리 → 명시적 BOM 정책으로 idempotent 재처리 → row/header validation 후 atomic publish → producer contract와 golden fixture 추가. 운영 원본을 직접 고치는 방식은 배제한다.

Q3. Binary header의 4byte record count가 가끔 수십억으로 보입니다. 설계를 리뷰해 보세요.

좋은 답변 구조: 정상 범위·file size·field offset 가정 → raw four bytes와 schema/version 수집 → endian, signedness, width, offset misalignment, partial write 가설 → magic/version/length/checksum 검증 → explicit endian unpack과 range invariant → 이전 manifest rollback·원본 replay → schema-generated reader 또는 self-describing header 대안, 추가 metadata 비용과 backward compatibility까지 방어한다.

10. 회상·확인 문제

어제 내용 회상 3문제

  1. 파일 확장자가 실제 format을 보장하지 않는 이유는?
  2. Encoding과 serialization의 책임을 한 문장씩 구분하라.
  3. write() 성공과 durable publish가 같은 시점이 아닌 이유는?

오늘 내용 확인 3문제

  1. UTF-8 BOM이 byte order를 정하지 않는 이유와 실무 위험 하나를 말하라.
  2. 세 byte 문자가 두 chunk에 나뉠 때 decoder가 지켜야 할 상태와 EOF 불변식은?
  3. 04 03 02 01을 32-bit little-endian과 big-endian으로 읽으면 왜 값이 달라지는가?
짧은 정답·채점 기준
  1. 어제 1: 확장자는 이름의 suffix이며 byte layout을 강제하지 않는다. 실제 parser/schema/magic/metadata 검증을 언급하면 정답.
  2. 어제 2: Encoding은 값·문자와 byte의 표현 규칙, serialization은 구조화된 값과 저장/전송 표현의 계약. schema/framing까지 말하면 만점.
  3. 어제 3: user buffer, kernel page cache, durable media/object commit은 서로 다른 상태. atomic publish 또는 fsync/manifest를 언급하면 만점.
  4. 오늘 1: UTF-8 code unit이 1byte라 byte order가 없고 BOM은 signature다. 첫 header/shebang 오염을 예로 들면 만점.
  5. 오늘 2: incomplete continuation byte를 carry하고 EOF final flush에서 잔여 byte를 오류로 처리한다. chunk별 독립 decode 금지를 말하면 만점.
  6. 오늘 3: byte significance mapping이 반대이므로 LE는 0x01020304, BE는 0x04030201로 해석된다. width/signedness 계약까지 언급하면 만점.
